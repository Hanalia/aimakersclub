## *나는 진심으로 오픈모델이 승리하길 바라지만, 아직은 충분하지 않다* 핵심 요약

- 영상은 최신 오픈소스 AI 모델(예: Kimi, GLM, DeepSeek 등)이 뛰어난 수치 성능을 공개하며 상업용 ‘프론티어’ 모델(GPT, Claude 등)을 능가한다는 주장과 실제 사용 간의 괴리를 집중적으로 설명함
- 제작자는 오픈모델의 성능이 벤치마크에서는 매우 인상적이지만, 실제 실무(특히 장기/복잡한 작업)에는 한계가 뚜렷하다고 경험적으로 증명함
- 단기·단순 업무 자동화, 기업 내 AI 에이전트의 90% 일처리에는 오픈모델이 프론티어 모델 대체 가능하고, 실제로 엄청난 비용 절감 효과가 있음
- 그러나 복잡한 규칙·장기 맥락 유지가 필요한 ‘소프트웨어 공장(Factory)’형 업무에서는 오픈모델의 ‘주의력 부족’(작업 맥락·규칙 잦은 망각) 한계가 두드러진다고 지적
- 실험적으로 같은 비디오 게임(‘Northstar’)을 Claude Opus, GPT-6 Astra, Kimi K 3.1 Pro로 구축해 보니, Claude가 12개 작업을 모두 성공, 신뢰성·비용·효율성에서 압도적
- GPT-6 Astra는 11개 작업 성공, 시간·비용은 Claude의 2배 이상 소요되어 실무 적합도가 낮음
- Kimi는 반복적 오류로 인한 재작업이 많아 12개 중 5개 작업만 완성, 작업당 실제 비용도 높은 편임
- 결론적으로 "혼합 운용": 프론티어 모델로 계획·리뷰(고비용/고성능), 오픈모델로 실제 코드 실행(저비용), 이 조합이 현재 최적 솔루션임을 제시
- 오픈모델의 미래 성장 가능성은 매우 크지만, 아직 모든 고난도 실무 자동화에 완전히 적용하기에는 부족한 점이 존재함
- 영상 끝에서 실제 세팅 방법, 상세 데이터 공개 등 추가 콘텐츠 예고

## 세부 요약 - 주제별 정리

### 오픈모델의 벤치마크 성능과 실제 사용 경험에는 괴리가 존재함

- 매번 Kimi, GLM, DeepSeek 등 새로운 오픈모델이 출시될 때마다 진행자는 ‘드디어 프론티어 모델을 대체하나?’ 기대감을 가졌음
- 공개 지표(Terminal Bench 4.0 등)에서 오픈모델이 Claude Opus, GPT-6 Astra 등 프론티어 모델을 앞서는 사례도 있음
- 그러나 실제로 코드 작성 등 본격적인 작업에 투입해 보면 번번이 실망스럽게 결과가 무너짐
- 수치와 현실의 차이 분석이 본 영상의 주요 주제임

### 단기·간단한 업무에는 오픈모델이 프론티어 못지않게 뛰어나며 비용 면에서 유리함

- 짧고 비교적 단순하면서도 깊은 사고가 필요한 ‘에이전트 단기 작업’에서는 오픈모델과 프론티어 모델 성과가 거의 대등함
- 본인이 맡겼던 각종 단기 작업 결과, 에이전트로 검토한 뒤 결과가 ‘본질적으로 동일’하다고 판단됨
- 오픈모델을 쓸 경우 단가 측면에서 압도적인 금전적 이점이 있음
- 2~5년 내 대부분의 기업 에이전트 업무의 90% 이상을 오픈모델이 담당할 것이란 연구 및 현업 평가가 다수 존재
- 실제 기업 내부 데이터 민감도, 자체 운영 비용 절감 요구에서 오픈모델 채택이 늘어나고 있음

### 오픈모델의 치명적 약점은 장기·복잡한 코드 작업에서 드러남

- 대기업 코드베이스, 복잡한 규칙 기반의 ‘AI 소프트웨어 공장(Factory)’ 등 장기적·다단계 워크플로우에서는 오픈모델이 급격히 성능 저하
- Kimi K 3.1 Pro 등 최신 오픈모델조차도 복수의 규칙, 문맥 정보, 장기적 논리 유지에 반복적으로 실패함
- 한 가지 예: PRD(제품 요구사항 문서)는 읽기 전용이므로 건드리지 않아야 한다는 명시적 규칙도 반복적으로 어기고 시도함
- 명확한 가이드와 프로세스가 있음에도 이상한 반복실수, 규칙 망각 현상이 지속됨
- 결과적으로 재시도, 수정 필요성이 늘어나 작업 실질 단가와 시간 소비가 늘어나게 됨

### 벤치마크 지표별로 장기적 작업 안정성에 큰 차이가 발생함

- Terminal Bench 4.0처럼 단기적·기초적 과업을 측정하는 벤치마크에서는 오픈모델이 종종 프론티어 모델을 능가함
- 하지만 Terminal Bench Science Frontier Code 2.0 등 장기 문맥·설계 연속성을 요구하는 벤치마크에서는 Claude Opus, Gemini 4 Carbon 등 프론티어 모델이 압도적 우위
- 예시: Frontier 연구에서 GPT-5.6 Soul이 41.6% 달성, KimiK 3는 단 22.1%로 큰 격차 발생
- 즉, 오픈모델이 특정 벤치마크에서 우수하다고 해서, 모든 실제 개발 워크플로우에서 우수함을 보장하지 못함을 실증함
- 프론티어 모델도 여전히 장기 업무에서 완전한 해결책은 아니지만, 오픈모델 대비 월등히 적은 오류 발생

### 실제 소프트웨어 공장(Factory) 워크플로우에 투입시 오픈모델의 한계는 더 뚜렷해짐

- AI Factory 방식: ‘계획 → 실행 → 검토/테스트 → 배포’의 다단계 자동화, 각 단계별 명확한 Skill/Rule/Agent 분할 구조임
- Claude Opus 사용시, 규칙·맥락 준수, 독립적 판단 능력, 오류 최소화 측면에서 실무에 가장 충실함
- Kimi K 3.1 Pro는 범위가 조금만 넓어져도, 지정한 규칙·맥락을 잊거나 엉뚱한 행동(읽기 전용 파일 수정 등)을 반복함
- 반복적 수정 요구가 많아지면서, 총 Token 요금 기반으로 산정할 때 오히려 Claude보다 Kimi가 더 비쌀 수 있음
- 실험적으로 다양한 평가 항목/벤치마크 결과 역시 이 경향 명확

### 실험: 동일 게임(‘Northstar’) 구축 실전 테스트에서 프론티어, 오픈모델 차이가 극명하게 드러남

- Claude Opus, GPT-6 Astra, Kimi K 3.1 Pro로 동일하게 ‘Northstar’ 비디오 게임을 AI Factory 체계에서 구축하는 테스트 실시
- 동일한 시작 그래픽, 12개 작업 티켓 기반의 설계
- Claude Opus: 12개 작업 전부 성공, 약 14시간 소요(작업별 시간 약 1시간), 퀄리티·안정성 매우 높음, UI·게임 기능 완성도 우수
- GPT-6 Astra: 11개 작업 완수, 약 28시간(2배), UI 품질이나 안정성 Claude보다 낮음, 디테일 미흡, 남은 버그 존재, 최종 완성도 Claude 대비 떨어짐
- Kimi: 44시간 동안 5개만 완성, 잦은 멈춤/반복 작업, 결정적 기능(예: 게임 상점, 캐릭터 업그레이드 등) 미구현, 도중 서버 멈춤/오류 빈발
- 실험적 데이터 수집(수 천만 Token 소모)에 근거하여 오픈모델의 ‘효율 한계’, 반복적 오류/규칙 무시 현상 직접 관측

### 동일 작업에서 실제 비용과 품질도 프론티어 모델이 더 우위임

- Claude Opus: 총 255달러(12개 전부 성공, 개별 작업당 21달러, 실전 API 예상 단가 기준)
- GPT-6 Astra: 635달러(11개만 성공, 개별 작업 63달러), 시간/비용 모두 2~3배 비효율
- Kimi K 3.1 Pro: 180달러(5개 완성, 작업당 36달러), 겉으로 보기에 저렴하지만, 작업당 효율성과 품질 기준에서는 오히려 불리
- 반복작 업무, 미완성, 재작업 발생 시 오픈모델의 이점이 사라짐, 담당자 개입 필요 빈도도 오픈모델이 월등히 높음

### 외부 에이전트의 블라인드 코드 품질 평가에서도 오픈모델이 뒤쳐짐

- 외부 독립 리뷰어의 블라인드 검토 결과 Claude Opus: 8/10, GPT: 7/10, Kimi: 6/10의 점수 기록
- Kimi도 최종적으로 ‘그럭저럭’ 동작하는 코드 산출, 하지만 결과에 이르기까지 반복적 고생이 많음, 코드 신뢰도·독립성에서 뒤쳐짐

### 오픈모델로 전체 워크플로우를 대체하는 것은 현시점에서 한계가 있음

- 중·장기 자동화, 대규모 워크플로우에서는 오픈모델 성능·안정성 미달로 전체 전환이 비효율적이라는 결론 도출
- 오픈모델의 장점(비용, 단기 업무 효율)에도 불구하고, 실제 장기 복잡한 업무에는 산업 프론티어 모델이 더 신뢰성·효율성 높음
- “최종 목표는 전부 오픈모델로 자동화”이나, 현재 기술·시장 현실상 “혼합 활용”이 유일한 실용 해법임

### ‘계획/리뷰=프론티어, 실행=오픈모델’의 조합이 현시점 비용·품질 최적 솔루션임을 실험적으로 입증함

- ‘계획(Planning)/검토(Review)’ 파트를 Claude Opus 등 프론티어 모델, ‘구현/실행’은 Kimi 등 오픈모델로 분리 적용시 실질 결과 동등
- 복잡한 맥락·규칙 유지, 전략 수립 등은 프론티어 모델에 맡기고, 실제 반복적 코드 작성은 저렴한 오픈모델이 수행하면 비용 드라마틱 절감
- 실제 실험서 간단/복잡 티켓 모두에서 같은 품질 산출, 단 비용은 Opus 전용 대비 절반 이하로 떨어짐
- 적용 예시, 상세 데이터, 구체적 셋업 방법은 향후 별도 콘텐츠로 설명할 예정

### 오픈모델의 미래 발전 가능성은 매우 크며, 혼합 활용 경험은 앞으로 표준이 될 전망임

- 제작자는 오픈모델의 장기적 발전 가능성을 국한하지 않으며, 조만간 프론티어 모델 전체 대체가 가능할 것으로 예상
- 당장 모든 코드를 오픈모델로 이전하지는 못하지만, 혼합운용 파이프라인은 이미 상당한 효율과 비용절감 효과를 실무에서 거둘 수 있음을 강조
- 시청자의 데이터/경험 피드백과 추가 요구(데이터, 세팅법, 추가 실험)에 따라 후속 콘텐츠 계획 존재
