## *슬롭(느슨함)에 슬롭으로 맞서다 — Vaibhav Gupta, Boundary* 핵심 요약

- 영상은 Boundary의 Vaibhav Gupta가 "슬롭"이라는 소프트웨어 내 느슨함(코드의 혼돈과 비효율)에 맞서 혁신적인 엔지니어링 방법론을 적용한 경험과 실천 과정을 소개함
- "코드 리뷰 없음, 병렬 작업 강제, AI 활용 방식 표준화 없음" 등 전통적 개발 문화를 탈피한 실험적 개발 프로세스를 실제 도입함
- 3년 전 자체 프로그래밍 언어(BAML)를 개발했으며, 이는 변경이나 느슨함(sloppiness)에 허용이 없는, 항상 일관되어야 하는 시스템임
- '슬롭'의 개념을 "읽지 않는 코드"로 정의하고, 이를 대치하기 위해 엔지니어 팀 내에서 일련의 여러 도구(디자인 문서 툴, 아키텍처 시각화 툴, AI 에이전트 기반 점검 등)를 구축함
- 코드 표준화 대신 본질적으로 변하지 않을 핵심만을 추출한 architecture.md 파일 작성, 디자인 문서는 슬롭을 허용하지 않는 강력한 규칙 적용
- 디자인 문서 프로세스를 자동화 및 활성화하기 위해 슬랙(Slack) 알림 연동, CLI 스크립트 자동화 등 사내 협업 도구 직접 제작
- 코드베이스 아키텍처의 결합도 및 의존성 관리를 위한 시각화 및 불변(invariant) 자동 점검 도구 구축
- 에이전트가 실제로 코드를 생성·실행·검증하며, 성능 · 효율성 · 버그 탐지에서 인간보다 AI가 어느 부분에서 더 나은 분석을 할 수 있음을 시연
- 코드 실행 시 코드 전체를 읽지 않고 시각화, 트레이스, CLI 명령어 연동 등 인간과 에이전트 모두 효율적으로 이해하고 활용할 수 있는 개발 경험 소개
- BAML은 TypeScript 및 기존 언어들의 태생적 한계를 극복하기 위해 근본부터 새롭게 설계됐으며, 에러 처리가 타 언어(Rust 제외)와 차별화된 자동 추론 기능 제공
- BAML 함수는 파이썬, 타입스크립트, 러스트 등 외부 언어에서 즉시, 타입 안정적으로 호출 가능하며 람다 및 클로저도 언어 간 호환 지원
- 결론적으로, 기존 코드 리뷰, 표준화, 직렬작업이 아닌 새로운 방법으로도 고품질 코드와 시스템을 만들 수 있음을 증명하며, 개발 문화의 진화 필요성을 강조함

## 세부 요약 - 주제별 정리

### 전통 개발 관행을 깨고 병렬·자율·비표준화된 엔지니어링 체계를 도입함

- Boundary 팀은 "코드 리뷰 없음", "개별 엔지니어의 병렬 작업 의무화", "AI 활용 표준화 없음" 등 기존 소프트웨어 엔지니어링의 통념을 뒤집는 정책을 실제 도입함
- "우리는 Zoomer YC 스타트업이 아니다, 나는 밀레니얼이다"라는 언급으로, 실험적이지만 의도적으로 선택된 전략임을 강조
- 프로그래밍 언어를 자체 개발하면서, 결코 느슨함(sloppiness)이 허용되지 않는 환경 조성을 중요시함
- 실전에서의 슬롭은 코드가 아니라 "읽지 않는 코드"임을 정의함

### architecture.md를 최소한의 변화 없는 표준서로 삼아, 자율성을 보장하면서도 핵심 불변성을 관리함

- 기존 표준(예: Claude.md 등)을 대체해, 코드베이스 내에서 오랜 기간 변하지 않는 본질만이 남는 architecture.md 파일을 작성
- 이 문서는 '컴파일러의 레이어' 등 회사 시스템의 변하지 않을 핵심 구조만 기술하며, 예측 불가능한 변화나 개인적 선호를 배제함
- 엔지니어가 각자 자신만의 프레임워크, LLM(Claude, Codex 등)을 사용하더라도 전체 구조의 불변성만은 architecture.md로 보장
- 협업 속도를 일부 조율하기 위해 각 에이전트가 최종적으로 다른 동료 1명 이상과 소통하도록 룰을 부여

### 디자인 문서의 품질은 엄격한 규칙과 도구화, 실시간 알림 시스템으로 유지함

- "코드는 슬롭이어도 되지만, 문서는 절대 슬롭이면 안 된다"라는 팀의 명확한 원칙이 강조됨
- Notion, GitHub를 대체하는 자체 디자인 문서 도구를 개발
  - 버전 관리, 코멘트, 구조화, 마크다운 기반 설계
- 자동으로 슬랙(Slack)에 디자인 문서 업데이트가 알림되는 연동 시스템 구축
  - 가장 인기 많은 채널로 발전(새벽 2시에 설계 문서가 올라와도 즉시 팀원들이 읽음)
- CLI 스크립트와 마크다운 기반으로 GitHub-like 환경 제공
- 단점: 문서가 너무 많아져 "내가 만든 슬롭을 다시 동료가 맞서 싸우는 상황"이 발생
- 궁극적으로, 문서를 만들면 반드시 타인이 직접 읽어야 한다고 최종적으로 강제함

### 코드베이스 아키텍처의 변화 감지를 위한 시각화 도구 및 자동 점검 시스템을 구축함

- 코드베이스 내부 및 외부 의존성을 시각화하는 도구 개발
- 단일 패키지, 시멘틱(의미론적) 경계를 시각화함
- CLI 도구를 통해 일부 불변값(architecture invariants)이 자동으로 깨지지 않도록 감시
- CI/CD, Git 커밋 히스토리 등과 연동하여 구조적 오류 발생 시 즉각 감지 및 위치 파악 가능
- 3~4개월 이상의 아키텍처 유지, 빈번한 구조 변화 차단

### 에이전트 기반 자동 점검·테스트·A/B 테스트로 품질 관리 방식을 체계화함

- 에이전트가 BAML 코드를 지속적으로 생성 및 실행하며, 수행 결과를 전체 트랜스크립트(주로 Claude output)를 바탕으로 도구 사용 내역, 문제점 등을 분석
- 타겟은 코드의 문법적 오류뿐 아니라, 예를 들어 "3번 툴 호출이면 1번이면 충분했을 사항" 등의 비효율까지 자동 탐지
- 사람이 직접 확인하지 않은 이슈 중 실제 결함, 오탐, 미묘한 품질(‘taste’)을 구분함
- 에이전트가 문제점을 자동으로 수정 및 반영
- A/B 테스트 시스템 도입: 툴 호출 수, 에러율, 결과의 정확성 등을 수치로 비교해 어느 기능·구현이 우수한지 데이터 기반으로 선택
- 이런 자동화로 "한줄도 직접 코딩하지 않고도 데이터 기반 시스템 설계" 가능

### 기존 언어의 기저(특히 TypeScript, JavaScript)의 한계는 인간 생산성을 중심으로 설계된 이유임을 지적함

- TypeScript는 '정확성'과 '생산성'의 균형(실제로는 "인간 생산성"에 방점)을 목표로 설계됨
- 예시로 '코드가 언어 레벨에서 이미 이상한 동작(예: sort시 암묵적 문자열 변환, 타입 안정성 약화 등)'을 내재하고 있다고 지적
- CoffeeScript→TypeScript의 레이어식 개선은 '밑단이 이미 깨져있음'을 해결하지 못함
- "에이전트가 코드를 쓰는 시대, 인간이 한줄도 안 쓸 수도 있는 환경"에서 기존 언어의 완전한 재설계 필요성을 역설

### BAML은 근본부터 에이전트·추상화·자동화에 적합하도록 재설계됨

- BAML에서는 코드를 모두 읽지 않고 곧바로 "시각화", "노드·엣지 연결", "구조 확장·축소", "중요 부분에 곧바로 점프" 등이 즉시 가능
- 전체 코드 읽기 없이, 흥미로운 지점만 선택적으로 이해·깊이 파고드는 워크플로 선사
- 실행 트레이스(Execution Trace) 시스템: 코드 실행 당시 시간 소모, 함수 호출 흐름, 결과까지 전체적으로 시각적으로 파악 가능
- 퍼포먼스 오버헤드 없는 트레이스 아키텍처 도입으로 인간, AI 양쪽 모두 효율적 유지 관리 가능
- Claude(에이전트)가 코드 구조 내 상호참조, 버그·비효율 탐색을 위한 탑재된 네비게이션 기능

### 에이전트-퍼스트 환경에서는 코드 검색·도큐먼테이션도 명령 기반으로 즉시 통합·자동화됨

- 전통 명령어(grep, ripgrep)를 통한 코드 검색의 한계를 넘어서, "calculate"라는 함수·기능 자체를 한 명령어로 전체 설명+도큐먼트+사용처까지 자동화된 결과 도출
- 외부 라이브러리 API까지 해당 코드 베이스에서 바로 설명 호출 가능
- '코드만이 실제 진실', '문서나 아키텍처 파일은 거짓말할 수 있다'는 원칙 아래, 코드 검색-분석-도큐먼트 자동 통합 툴 강조

### CLI 함수 자동화로 코드의 실행과 배포가 OS·아키텍처 무관하게 신속하게 이루어짐

- 작성한 함수(add, multiply 등)는 곧바로 독립적 CLI 명령어로 노출됨 (A, B 파라미터 포함)
- CLI 툴(binaries)을 각 OS(Windows, Mac, Linux), WASM 등으로 신속히 번들링·배포 가능
- 타입 안정성(Type safety), 결정론(Determinism) 구현, 오작동 여지를 최소화함
- 에이전트가 코드 내부 동작 탐색 필요 없이 바로 활용할 수 있도록 설계됨
- OS·배포 환경과 무관하게 극단적으로 빠른 개발→배포→테스트 사이클 실현

### BAML의 에러 처리 체계는 타 언어와 비교해 근본부터 자동화·엄격화된 방식으로 설계됨

- divide(나눗셈) 함수 등에서 'division by zero' 등 에러 타입 자동 유추
- 상위 함수에서 하위 함수가 throw하는 에러 타입을 자동 인지, 전체 호출 트리까지 에러 추정보장
- 에러 핸들링 시, 처리가 누락된 에러에 대해 컴파일 단계에서 명확하게 오류 통지
- 에러 catch의 영향이 호출 체계 전반에 자동 전파되며, API가 항상 안전함을 컴파일러가 보증함
- Rust와 유사한 "에러 exhaustiveness(누락 없는 처리)" 구현, JavaScript/TypeScript와 근본적으로 차별화

### BAML은 다양한 언어와 즉시 통합 가능하며, 타입 시스템이 언어 경계를 투명하게 연결함

- BAML 함수는 파이썬, 타입스크립트, 러스트, Go, Ruby, Java 등 어느 언어에서도 동기-비동기(Async) 타입 안정적으로 호출 가능함
- 람다, 제네릭, 클로저 등도 언어 경계를 넘어 투명하게 전달
- 타입 시스템이 '유일한 절대 진실'이 되어, 코드 내 invariant(불변식) 붕괴를 방지함

### 기존 시스템(코드 리뷰, 표준화, 직렬작업 등) 없이도 혁신과 품질을 양립할 수 있음을 실증함

- 여러 도구와 자동화·투명화된 프로세스 만으로 고품질, 대규모 시스템(LANG, C 컴파일러 등) 개발 실적 보유
- 과거의 CI/CD 도입 초기에는 느려지나, 장기적으로 목적 달성시 생산성이 급상승하는 패턴을 거듭 확인
- 본질은, 기존 프로세스의 한계를 기술적으로 극복하는 근본적 도전과 문화적 혁신임
- 마지막으로 "슬롭의 최소치"에서 싸움을 시작해 각자가 더 강인한 도구와 프로세스를 직접 만들어볼 것을 독려하며 마무리함
