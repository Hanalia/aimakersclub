## *AI가 코드를 작성한다면, 엔지니어의 역할은 무엇이 남는가?* 핵심 요약

- 본 영상은 "AI가 코드를 작성하는 시대에 엔지니어는 무엇을 해야 하는가?"라는 질문을 중심으로, 소프트웨어 개발 직업의 변화와 미래 역할을 상세히 분석함
- AI 에이전트의 등장으로 코드 작성은 사실상 무료(저렴화)로 변해, 개발의 병목이 "코드 리뷰"와 같은 후속 단계로 이동함
- 자동화 코딩 도구 도입 시 개발자는 평균 741% 더 많은 코드를 작성하지만, 실제 출시 속도는 30%만 빨라짐
- GitHub Copilot 등 AI 리뷰어는 전체 코드 리뷰의 20% 이상을 담당하고 있으나, 아직 신뢰성 및 정확성의 한계를 보임
- 코드 리뷰 자동화가 완전히 해결되어도, 이후에는 운영·보안 등 새로운 병목이 발생할 것이며, 이마저도 미래엔 AI가 상당 부분 대체할 것이라고 전망함
- 최종적으로 인간 엔지니어에게 남는 역할은 “무엇을 만들지 결정하고(문제 정의), 무엇이 좋은지 정의하는 것(품질 및 가치 명세)”이라고 주장함
- 소프트웨어 개발의 본질적(’essential’) 복잡성, 즉 “문제 파악과 명세화”는 여전히 인간의 몫으로 남음
- 이러한 변화 때문에, “프로덕트 엔지니어(제품 엔지니어)”라는 통합적 역할이 부상하며, 기존의 프로그램 작성 기술은 점차 AI에 이관됨
- 엔지니어 채용시장에서는 신입(주니어) 개발자의 고용이 크게 감소하고, 문제 정의 및 고객 이해 역량이 중시되는 경향이 두드러짐
- 앞으로의 개발자는 단순 코드 타이핑이 아니라, 고객 문제를 파악해 명확한 사양(스펙)을 작성·전달하고, 이를 기반으로 AI가 제품을 만들게 하는 '구조 설계자' 역할을 해야 함

## 세부 요약 - 주제별 정리

### Swyx의 ‘AI 엔지니어’ 개념은 모든 엔지니어의 직무 변화를 포괄하지 못함

- Swyx가 3년 전 "AI 엔지니어의 부상"이라는 에세이에서 제품 배포에 있어 연구자보다 엔지니어가 중요하다고 주장함
- 이 에세이가 “AI 엔지니어”라는 직함을 탄생시켰고, 기업 채용에 반영되었음
- 발표자는 “AI 엔지니어” 혁명을 넘어, 전통적 소프트웨어 엔지니어 전체의 직무가 급변한다고 강조함
- AI 에이전트의 도입으로 기존 개발 직업군 대부분에 근본적 변화가 불가피해졌음을 알림

### AI 에이전트의 도입으로 코드 작성이 사실상 ‘무료’화됨에 따라, 개발 병목이 코드 생산에서 코드 리뷰로 이동함

- AI 코딩 에이전트 도입 시, 개발자 1인당 코드 작성량은 741% 증가(기존 대비 8배), 하지만 실제 출시 속도는 30%만 빨라짐
- 이 괴리의 주 원인은 코드 리뷰의 속도 차이에서 발생함
- Cisco의 연구(20년 전): 인간의 코드 리뷰 한계는 시간당 450라인, 대형 코드 변경(diff, 예: 10,000라인 이상)은 사실상 리뷰 불가
- 최근, AI 코딩 도구(예: Copilot 등) 사용 시 방대한 양의 코드가 빠르게 생성되지만, 인간은 이 모두를 검증할 능력이 부족함

### AI 코드 리뷰어는 이미 실무에 도입 중이나, 아직 신뢰성 부족으로 최종 검토자 역할을 완전히 대체하지 못함

- GitHub Copilot은 전체 코드 리뷰 중 20% 이상을 맡고 있으며, 옵션에 따라 PR(풀 리퀘스트) 최종 승인권도 부여 가능
- OpenAI의 경우, PR 리뷰를 인간이 선택적으로 수행, 의무는 아님
- 여러 AI 리뷰어(총 4개 평가): 모두 각각 버그를 발견하였으나, 동일한 버그에 대해 일치하지 않아 신뢰도 한계 존재
- 인간 코드를 아예 리뷰하지 않는 실험(예: Dexter Horty의 6개월 실험) 결과, 시스템 전면 교체라는 실패를 겪음
- 아마존 역시 AI가 검증하지 않은 채 출시한 코드 때문에 장애가 발생, 현재는 시니어 엔지니어의 최종 리뷰를 의무화
- Anthropic도 기계/인간 양쪽 리뷰를 모두 거쳤으나 버그 유출 사례 보고

### AI가 리뷰 병목을 넘어서더라도, 새로운 병목(운영∙보안 등)이 연이어 등장할 것이며 미래엔 모두 자동화될 가능성이 높음

- 엘리야후 골드렛의 '제약 이론(The Goal)' 인용: 한 시스템은 반드시 하나의 병목을 가지고, 그 병목을 해소하면 다른 곳으로 이동할 뿐임을 설명
- 코드 리뷰 자동화 완성 시, 차기 병목은 배포(operation), 확장성(scaling), 보안(security) 등 시스템 운영 영역이 될 것으로 전망됨
- 운영과 보안 역시 이미 풍부한 데이터셋, 매뉴얼, 현업 규정 등이 존재해 AI 학습 및 자동화의 기반이 마련되어 있음
- 현 단계의 문제(코드 리뷰)는 단기(12개월 이내)에 일부 해결 가능성이 있지만, 운영·보안의 완전 자동화는 5~10년이 소요될 것으로 예측됨
- AGI(일반 AI) 도래 전망에 회의적 의견 제시, 점진적 자동화 발전을 예상

### 생산할 수 있는 소프트웨어의 양이 사실상 ‘무한대’로 늘어나 개발 병목은 결국 사람의 요구·문제 정의로 귀결됨

- “필요한 소프트웨어의 개수는 사실상 무한대”라는 가정 아래 논리 전개
- 대부분의 레거시 웹사이트(미용실, 은행, 정부기관 등)가 품질이 떨어지는 주 원인은 “시간과 예산·인력이 부족”해서임
- AI의 도입으로 소프트웨어 생산이 ‘공짜’가 되어도, 요구 정의와 문제 구체화는 사람이 직접 해줘야 함

### ‘무엇을 만들지’, ‘좋음이란 무엇인지’ 정의하는 능력이 AI 자동화의 최후의 영역으로 남음

- 소프트웨어 개발과정 분석: 코딩, 코드 리뷰, 배포, 확장, 보안 등 여러 단계로 구분
- 미래에 AI가 모두 맡게 되더라도, “무엇을 만들지 결정”, “좋음(품질, 가치)의 정의”, “사용자 경험 최적화” 등의 영역은 남을 것으로 봄
- 실제로 사용자의 개별 요구(예: 제과점, 자동차 부품상, 대규모 기업 등)는 같은 “주문 관리” 요구도 전혀 다른 해법을 필요로 함
- 이런 요구 사항 및 “좋음의 정의”는 훈련 데이터나 매개변수(Weights)에 실리지 않고, 실제 비즈니스 담당자의 머릿속에 있음
- 사람 간의 대화(인터뷰)를 통한 요구 정의는 기계 학습이 쉽게 대체할 수 없음
- ‘사용자 맞춤화’된 소프트웨어의 품질 기준은 매우 다양하며, 단순 기능 명세로 환원 불가

### 본질적(essential) 복잡성인 ‘문제 정의’는 자동화로 극복할 수 없는 난제로 남음

- 프레드 브룩스(Fred Brooks)의 ‘The Mythical Man-Month’(1986) 인용: 개발에는 ‘우발적 복잡성’(도구, 문법, 타이핑 등)과 ‘본질적 복잡성’(문제 자체의 난이도) 구분
- 도구가 발전해 타이핑 등은 8배 빨라졌지만, 제품 출시 속도는 8배 빨라지지 않음(30%에 그침)
- 이는 ‘본질적 복잡성’인 문제 정의/사양화가 생산성과 혁신의 진짜 병목임을 데이터로 뒷받침함
- Shawn Grove(OpenAI) 역시 “코드는 사양(spec)의 손실 압축본(lost projection)”이라며, 사양 작성자가 사실상 프로그래머 역할을 수행한다고 언급

### 명시적 지식(룰화, 테스트, 규칙)이 쌓일수록 AI 자동화 영역이 넓어지나, 명시화 불가능한 부분이 곧 인간의 일임

- Cognition(Devin 제작사)은 “이 PR을 실제로 머지할 것인가?”라는 질문에 기반한 새로운 벤치마크를 고안함
- 기존 자동화 코드는 테스트만 통과하면 87% 성공, 실제 머지 기준으로는 54%로 떨어지는 현상 발견
- Cursor의 Reviewer BugBot: 팀원 불합격(thumbs down)을 모두 규칙화해 44,000여 개 룰을 현업에 적용
- 지식을 룰화·명시화해 데이터로 만들 수 있으면, AI가 해당 업무 자동화 가능 → 향후 자동화 확장이 가능한 이유임

### ‘프로덕트 엔지니어(Product Engineer)’ 개념의 부상과 개발자 직군의 경계 변화가 빠르게 진행 중임

- 1960년대의 “시스템 분석가(System Analyst)” 포지션처럼, 문제 파악에 초점을 두던 역할이 중시됨
- 시스템 분석가는 현재의 “제품 관리자(PM)” 역할로 변모함, 향후에는 프로덕트 엔지니어로 역할이 재통합될 전망
- Gergo Orosz(Pragmatic Engineer)는 “제품 지향적 엔지니어(product-minded engineer)”를 2019년 언급, 발표자는 이 특성이 ‘필수적(primary)’ 역량이 되었다고 주장
- 포워드 디플로이 엔지니어(Forward Deployed Engineer) 직군은 2025년 9개월 만에 공고 수가 800% 증가, 평균 연봉 24만 달러(시니어급) 기록
- 시장에서 명칭이 아직 통일되지 않았으나, 모두 ‘프로덕트 엔지니어’ 유형에 속함
- “프로그래밍=소프트웨어 개발자”라는 등식이 붕괴, AI가 타이핑 업무를 대체하는 시대가 도래함

### 주니어 개발자 고용 급감과 신입 개발자 양성 체계의 재정립 필요성이 대두됨

- 과거에는 “잘 정의된 사양”을 주니어 개발자에게 맡기고, 시니어들이 리뷰하며 역량을 키움
- 지금은 AI가 대부분의 단순/명확 업무를 대체, 신입 개발자 채용 및 성장 루트 붕괴
- 미국 노동통계(2023.1~): 22~25세 엔지니어 고용 급감, 41~49세 시니어 엔지니어 고용 대폭 증가
- Google의 APM(Associate Product Manager) 프로그램은 연간 50명의 ‘제품 엔지니어’ 배출, 시장 수요(연 1만 명 이상)와 큰 격차
- 대학은 “자료구조”, 부트캠프는 “React”만 가르치나, 정작 중요한 “고객 니즈/문제 분석 및 명세화”는 훈련하지 않음
- IBM 등 일부 기업은 신입 엔지니어의 역할을 고객 인터뷰·사양 작성 중심으로 재설계 중

### 프로그래밍의 ‘장인정신’은 취미·예술로 남고, 실무에선 고객 문제 정의·명세가 유일한 ‘핵심 역량’이 됨

- 많은 개발자들은 “프로그래밍 자체의 재미”를 좇아 입문했으나, 미래에는 직접 코딩이 실무의 주요 부분이 아닐 수 있음
- “고객 인터뷰”나 “사양서 작성” 같은 역할을 꺼리는 개발자 증가, 그러나 실질적 임금·실무 기회가 해당 역량 중심으로 이동
- 프로그래밍의 예술적 측면(취미, 창작욕구)은 앞으로도 남지만, 연간 수십~수백만 달러의 가치 창출은 ‘제품 정의’ 업무에 집중될 것

### 개발 직업의 패러다임 변화는 이전에도 반복됐으며, 장기적으로 더 큰 소프트웨어 생태계로 이어질 것임

- 컴파일러, 프레임워크, 오픈소스의 발명 이후마다 ‘타이핑’ 중심 직업은 사라지고 더 많은 소프트웨어 개발자가 등장
- 변화의 시기는 항상 “혼란·과도기”가 있었으나, 결과적으로 소프트웨어 산업은 성장해 왔음
- 향후 10년 이내, “제품 엔지니어링” 중심의 더 크고 풍요로운 직종이 탄생할 것으로 전망함

### 실무 엔지니어가 당장 준비해야 할 조치와 ‘평가(평가 지표)’의 변화 제안을 제시함

- 현업에서는 “리스크가 높은 코드”에만 직접 리뷰 투입, 나머지는 자동화 리뷰에 위임할 것 권장
- 검증·평가(verification)가 쉬운 영역은 철저히 자동화, 사람은 “좋음의 기준”을 명확히 정의(스펙·룰·평가·템플릿화)해야 함
- 실질적 생산성 지표는 “코드 양(741% 증가)” 아닌 “실제로 출하되는 소프트웨어”이며, 리뷰 코멘트가 얼마나 반영되었는지 등을 측정
- 최종 리뷰어는 “실제 배포(Production)”, 그 현장에서의 성능 모니터링 및 후속 평가가 중요
- 제품 엔지니어의 임무: “문제의 본질을 이해·문서화하여” 에이전트가 구현 가능한 명세로 내려주는 것

### ‘AI 엔지니어’ 시대를 넘어 ‘제품 엔지니어’ 시대, 이제 모든 개발자가 프로덕트 엔지니어가 되어야 함을 결론으로 제시함

- 3년 전 Swyx의 ‘AI 엔지니어’ 논의가 “모델을 활용할 줄 아는 엔지니어” 중심이었다면,
- ‘제품 엔지니어’의 부상은 “모델이 직접 제품을 만드는 시대에 남는 일”이 무엇인지로 초점을 옮김
- 이제 모든 엔지니어는 고객이 원하는 것 파악, 품질 정의, 즐거운 사용 경험을 만드는 역할로 전환해야 함
- “우리 모두는 이제 제품 엔지니어이다”라는 강한 메시지로 강연을 마무리함
