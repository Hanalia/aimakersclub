## *벤치마크가 없는 환경에서 AI 에이전트 평가법* 핵심 요약

- **Air Canada에서 벤치마크 없는 환경에서 AI 에이전트 테스트 방법을 다룸**
- **내부 도메인 지식 부족과 전문가 접근성 장애로 인해 기존 공개 벤치마크 활용이 불가능한 상황 설명**
- **과거 통신사 QA 에이전트 개발 경험을 바탕으로 반복적인 전문가 평가와 복잡성 증가가 해결책이 되지 않음을 확인**
- **시험 평가 사이클이 느리고(주 1회), 전문가 의견 불일치 및 피드백 속도 한계가 큰 문제였음**
- **문제를 뒤집는 방식(질문→정답 대신 정답→질문 생성)으로 평가 자동화, 코드 기반 그레이딩 도입**
- **1주일 1회 평가에서 하루 수십 회 테스트로 대폭 전환, 정확도 개선과 빠른 실험/검증 문화 확립**
- **Air Canada 공급업체 계약 분석 에이전트 프로젝트에서는 공개 벤치마크 부재와 고가의 전문가 자원을 극복하기 위한 5가지 자동화 평가 기법을 적용**
- **계약 조항 탐지, 지원 문서 매칭, 변경안 작성, 최종 분류 등 실제 업무 단계를 위한 각기 구체적인 평가 전략 제시**
- **LLM을 판정자로 쓰는 방식은 노이즈가 심해 최대한 코딩 자동화·정확 매칭 중심 테스팅을 선호**
- **자동화된 벤치마크와 테스트 셋 구축이 없는 팀은 성능 개선과 신뢰 확보가 사실상 불가능함을 강조**

## 세부 요약 - 주제별 정리

### 도메인 지식 부족과 벤치마크 부재가 에이전트 평가의 최대 난점임을 체감함

- AI 에이전트 적용 분야가 Air Canada 내 다양한 비즈니스 부서(운영, 코퍼레이트, 상업, 로열티 등)로 나뉘어 매우 구체적임
- 각 부서 별로 도메인 전문가가 분리, AI 전문가와 물리적/조직적 거리가 존재해 지식 전달이 느림
- 공개 벤치마크가 존재하지 않아 외부 평가지표를 바로 적용 불가
- 데이터 사이언티스트·AI 엔지니어가 기술은 전담하나, 실제 답을 아는 전문가 없이는 테스트 자체가 어려움
- 전문가 자원은 여유가 없고, 확보 자체가 비용 및 속도의 병목이 됨

### 기존 RAG(검색·생성 혼합형 QA 에이전트) 프로젝트에서 자동화 평가를 통한 실험 가속 경험

- 전 직장에서 통신 엔지니어용 QA 에이전트(RAG) 개발: 1만여 문서, 수많은 공급사 설명서 기반 복잡한 시스템
- 세 팀이 유사한 조건에서 경쟁 형태로 프로젝트 진행, 최종 결과는 자사 솔루션만 실제 업무에서 채택
- 초기에는 복잡한 파이프라인(문서 처리, 검색, 생성 등)으로 성능 향상 시도 → 복잡성 증가가 되레 결과를 악화시킴
- 도구 변경(임베딩, 청킹, 쿼리 라이터 등)은 실제로 성능에 큰 영향 없음
- 복잡성 추가 시 기존 잘 동작하던 부분이 망가지는 현상 빈번
- 개발팀이 에이전트 변경은 신속(수분~수시간), 실제 전문가 등급 평가 사이클은 주 1회로 느림
- 주 1회 대형 회의 통해 각 팀 챗봇 답변을 전문가가 직관적 선호로 평가: 일치도 낮고, 의견 분분
- 전문가가 정답을 바로 알지 못하고 조회까지 하며, 평가 비용·속도가 큰 부담

### 평가 자동화(정답→문제 유도, 코드로 등급화)로 실험 속도·정확성 모두 상승시킴

- 기존 방식의 비효율 → 문제를 뒤집어 평가 자동화로 전환
- 문서 페이지를 먼저 선정, LLM을 활용해 해당 페이지를 기반으로 문제(질문) 생성
- 에이전트가 해당 질문에 답하도록 해, 실제 답변이 원래 문서 내용과 일치하는지 코드로 판단(Automated grading)
- 전문가 주관이 아닌 자동화 평가로 다수 실험 가속: 주 1회 → 하루 수십 회 테스트 체계로 변환
- 임베딩 모델, 청킹, 검색 알고리즘 등 시스템 구성요소에 집중, 실질적인 성능 개선
- 자동화 평가는 기존 전문가지표와 정합성이 높아졌으며, 실험 반복에 따라 맞춤형 모델링 가능
- 경쟁팀은 테스트셋 없이 느린 전문가 루프 반복, 최종적으로 성능·사용성에서 뒤쳐짐

### "평가하지 못하면 개선도 불가능"이라는 원칙이 핵심 교훈임

- 테스트셋, 평가 메트릭이 없는 한, AI 에이전트의 개선이 불가능하다는 확신 획득
- 평가 자동화 경험을 Air Canada 등 새로운 도메인에 확장 적용할 수 있음을 깨달음

### Air Canada 공급업체 계약서 검토 자동화 프로젝트에서도 평가 자동화 원칙을 적용

- Air Canada는 다수의 공급업체와 연간 계약 체결, 각 조항 검토는 고가의 법률 컨설턴트가 매번 수행
- 조항 누락・오분석 가능성은 금전적 손실, 공급망 지연 등 리스크로 이어짐
- AI에이전트에 의한 계약서 자동 검토·수정안 추천 시스템 요구 발생
- 문서 수집, 규정 파악, 다양한 평가포인트 등 복잡한 요구조건
- 외부 벤치마크 없음, 법조 전문가 접근도 매우 어렵고 비용이 큼

### 각 업무 단계(조항 인식, supporting docs 검색 등)에 다른 평가기법 적용 필요함

- 에이전트는 크게 네 단계: ①계약 각 섹션 조항 감지, ②수정 지원 근거자료 검색, ③수정안 작성, ④최종 분류(수용/거절)
- 조항 감지는 계약 섹션의 도메인 분류, 결함 탐지 등 수행
- supporting document 검색은 기존 RAG 자동화 평가(정답 역생성) 원리 적용
- 조항 작성, 분류 등 후속 단계에는 별도의, 정교한 평가체계 개발 필요

### 테스트셋 구축을 위한 5가지 접근법을 실제로 시도함

1. **과거 계약 변경 이력 활용**  
   - 원본-수정본 쌍을 비교(diff), 변경 포인트(플래그) 자동 추출 후 에이전트가 정확히 감지하는지 평가
   - 실제로는 이력 관리가 되어있지 않아 대량 구축 불가
2. **비즈니스 룰 기반 생성형 평가**  
   - 예: 100만 달러 초과 금액 cap 등 명시적 규칙을 문서로 평문화, 이를 위반하는(또는 준수하는) 샘플 생성
   - 규칙 목록을 일일이 파악해야 하며, 커버리지 보장이 항상 가능하진 않음
   - 전문가/문서에서 룰 추출, 자체 정의 등으로 최종 275개 테스트셋 생성
3. **계약 조항 누락·위조를 통한 anomaly testing**  
   - 정상이었던 계약의 일부 조항을 삭제, 에이전트가 “결정적 조항 누락”을 감지하는지 평가
   - 공급사마다 템플릿/내역 상이, 판단에 도메인 지식 필요하나, 성능 압박/벤치마크로 매우 유용
   - 이 방식으로 생성된 샘플 대부분 에이전트가 제대로 잡지 못해 성능 개선 트리거로 활용
4. **비영향 요소 변동(회사명, 주소 등) 무시 테스트**  
   - 영구 불변적 요소 변경(공급사명, 주소 등)→정상시 결과 변화 없음을 코드로 검증
   - 섹션 재정렬 등 랜덤 변화를 줘도 결과가 달라지지 않아야 신뢰 확보
   - 반복실행, 변이 등 일관성(Determinacy) 체크에도 활용
5. **템플릿 확장 통한 다양한 문서 조합 자동 테스트**  
   - 전문가들이 실제로 사용하는 계약 템플릿의 “빈칸”을 다양한 값으로 채워 조합별 케이스 생성
   - 위반 조합과 정상 조합을 구분, 자동적으로 breach flag, 정상 판정 등 라벨링 가능
   - 테스트셋 확장성이 크고, 템플릿 졍보 완비시 빠른 구축·평가가 가능함

### 코드 기반, 패턴 매칭 등 자동 그레이딩이 LLM 판정자 방식보다 노이즈가 훨씬 적음

- 가능한 한 자동화된 일치(Exact match), 코드 기반 판정 등을 활용
- LLM이 자동 판정자가 되는 순간, 답변 일관성·노이즈 이슈가 급증함을 경험
- "LLM as a judge"는 프롬프트 최적화, 하네스 세팅, 팩트체킹 등 부가작업이 많고, 판정 노이즈가 실제 에이전트 성능 노이즈보다 커질 수 있음
- 특정 상황에선 어쩔 수 없이 LLM-기반 평가 사용 필요, 하지만 될 수 있으면 코드화된 규칙 추천

### 업무 목적, 데이터 특성에 따라 평가 전략도 재설계가 불가피함

- Test2SQL 등 다양한 원천 데이터 셋에 적용 가능한 평가법 존재(정답 명확, 자동화 용이)
- 본래 문제설계(예: 입력/출력, 프로세스 단계 등)에 따라 평가 가능 모델로 “문제 자체”를 변형/재설계한 경험
- 평가 자동화가 불가하면 아예 솔루션 자체 구조도 조정

### 전문가 피드백은 에이전트 직접 개선이 아니라 테스트셋 또는 평가 설계 개선에 활용함

- 에이전트 성능 평가는 반복된 테스트셋 자동화로 주도되고, 전문가 의견은 새로운 테스트셋, 프롬프트, 평가 시나리오 개발에 사용
- 1회성 정답 제공–에이전트 수정에서 벗어나, 점진적 자동화 검증 루프 구축

### "정답을 미리 생성해두고 에이전트가 찾아내도록" 설계하는 평가법이 AI 에이전트 신뢰확보에 핵심임을 결론

- 평가 자동화는 제품 출시와 그/부 결정의 절대적 조건은 아니나, 성능 최적화 및 오류 사전 방지에 필수 툴임
- 현장의 반복적이고 신속한 실험, 신뢰할 수 있는 정확도 상승을 위해서는 “정답 우선(Answer-first)” 테스팅, 테스팅 자동화가 사실상 필수임
