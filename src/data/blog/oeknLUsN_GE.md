**영상 링크:** [Agents Made Code Free. Maintaining It Didn't Get Cheaper. - Dmitry Buykin, Maersk](https://www.youtube.com/watch?v=oeknLUsN_GE)  
**채널명:** AI Engineer

## *에이전트가 코드 생성 비용을 낮췄지만 유지 비용은 절감되지 않았다* 핵심 요약

- 이 영상에서는 Maersk의 Dmitry Buykin이 AI 코딩 에이전트 활용 경험을 바탕으로, 대규모 코드베이스 유지 관리의 실제 문제와 해법을 공유함
- 코딩 에이전트 덕분에 ‘코드 생성’은 저렴해졌으나, ‘코드 및 시스템 유지’는 오히려 복잡·고비용화되는 딜레마를 직접 경험함
- 처음엔 불필요한 테스트 및 보일러플레이트 코드를 대량 삭제(‘Thanos의 스냅’에 비유)하는 대수술을 감행했으나, 이는 문제를 완전히 해결하지 못함
- 재작성 이후에도 에이전트가 코드를 계속 생성하며 혼란이 반복되어, ‘코드 성장+혼돈’ VS ‘유지 관리 위해 시스템을 깨뜨림’이라는 두 선택지만 있었음
- 최종적으로 ‘소규모 주기적 클린업+피드백 루프 내재화’라는 ‘제3의 선택지’를 통해 시스템을 유지함: 매주 작은 정리와 증거 기반 관리가 핵심
- 영상은 6개의 핵심 질문(‘인피니티 스톤’에 비유됨)을 단계별로 탐구하며, 각각 코드/프로스 관리의 파운드리를 다룸
- 코드와 텍스트(프로스)의 통합적 품질 관리, 전문가(사람)와 에이전트의 역할 분배, 자동화와 인간적 판단의 경계 정의 과정이 구체적으로 소개됨
- 검증·관제 자동화, 증거(에비던스) 기반 결론, 코드 성장과 분기(브랜치) 관리 방법 등 실제 사례와 경험을 상세히 제시함
- 영상은 대규모 AI 코드 시스템 유지 관리를 담당하는 리드 엔지니어나 아키텍트가 흔히 마주치는 번아웃과 책임 집중 문제도 직접적으로 다룸
- 전체 구조는 실제 과제, 실제 문제, 해결 실험, 프로세스 내면화 순으로 체계적으로 제시됨

## 세부 요약 - 주제별 정리

### 코드 생성은 싸졌지만 무분별한 성장과 혼돈이 커지는 딜레마에 직면함

- 코딩 에이전트의 도입으로 대규모 프로젝트에서 ‘코드 작성’이 빠르고 저렴해졌음
- 그러나 코드가 빠르게 성장하면서 불필요한 테스트, 보일러플레이트(반복적 코드)도 함께 늘어나 ‘엔트로피’ 증가
- 마블 영화 ‘타노스’가 균형을 위해 반을 쓸어내듯이, 프로젝트에서 대규모 코드와 테스트 삭제를 단행함
- 삭제 과정에서 유익한 코드도 함께 사라지는 부작용 경험(“무엇이 살아남아야 하는가”라는 근본적 고민)
- 전면 삭제 대신 “익사 혹은 필요 코드 파괴” 외의 제3 선택지를 모색하게 됨

### 코드와 프로스(텍스트 지시문)가 섞인 복합 시스템의 품질 관리는 더욱 어려워짐

- 실제 업무 사례로 한 주문의 결제금액 변경 요청을 예시로 듦
- 시스템은 110개국에 걸쳐 약 10,000개 시나리오와 국가별 ‘프로스’로 구성됨
- 대부분의 업무 지침(약 3/4)은 코드가 아닌 ‘텍스트 설명(프로스)’에 내포
- 처음엔 ‘mutation testing(돌연변이 테스트)’ 방식을 차용했으나 프로스에서는 제대로 동작하지 않음(수정해도 테스트가 붉게 변하지 않음)
- ‘코드-지침-테스트’가 모두 프로스라면, 에이전트는 쉽게 재작성하고, 뭘 남겨야 할지 구분이 더 어려움

### 프로스(텍스트)는 컴파일러가 없고 일관성 유지가 어려워 검증 체계를 새로 구축해야 했음

- ‘프로스’는 컴파일러가 없어 일관성 검증이 어렵기 때문에, 변경 파일마다 사람이 린트(검사)를 수행하고 기록(ledger)에 남김
- ‘walk’란 하나의 에이전트가 프로스를 따라간 실행경로를 의미, 경로가 반복되면 이를 워크플로우 툴로 전환하고, 남은 프로스를 정리함
- 워크플로우 툴 초기 구현이 오히려 상황을 악화시키기도 함(프로스가 단계명만 남기고, 에이전트가 다시 실행)
- 결국 여러 국가에서 동일 반복이 확인되면 코드화, 다르면 계속 프로스로 남김

### 사람(전문가)의 판단과 자동화(에이전트)의 역할을 구체적으로 구분하는 프로세스가 필수적임

- 전문가들은 각 업무 단위(슬라이스)에서 한 번씩 판단하며, 에이전트는 하루 종일 반복 작업을 수행
- 판단이 요구되는 곳과 아닌 곳의 경계를 구체적으로 시험하면서 노력을 최적화
- 실제 사례: 한 업무에서 프로스엔 한도(1,500)가, 코드엔 다른 값(a,000)이 정의되어 국가마다 결과상이 다르게 나옴(문제 식별)
- 전문가들은 자신이 볼 수 있는 부분만 수정할 수 있으므로, 코드도 반드시 평이한 설명이 첨부되어야 함(전문가-에이전트 협업)
- 비로소 전문가의 검토 내역이 곧 다음 코드·테스트 생성의 기준이 됨

### 컨텍스트(상황)를 제한하고, 에이전트의 행동 영역을 명확히 통제해야 함

- ‘컨트롤’이란 에이전트의 권한 제한이 아니라, 무엇을 보고 무엇을 인식하는지(모델 컨텍스트) 제어하는 것임을 설명
- 초기에는 모델이 데이터를 무제한으로 불러오며, 불필요한 ‘가격 체크’ 규칙까지 자동발견 및 실행하는 문제가 발생
- 최적의 방법은 런타임이 보여주는 세 가지 정보만 모델이 접근하게 하여 오작동 및 예측 불가 행동을 최소화
- 큰 데이터셋의 경우 ‘핸들(핸들 네임)’ 방식으로 필요한 정보만 전달, 런타임이 검증하고 쓰기 전에 재확인

### 시스템의 모든 변경 사항과 검증 과정이 ‘증거(ledger, 증적)’에 기록되어야 함

- 모든 피드백 루프(무한 반복)는 시스템에 내재화하고, 결과는 ledger(기록)에 저장
- 시스템은 각 세션이 끝나면 모든 기억을 잊어버리기 때문에, 결과/불변사실 두 가지 파일을 남김
- 모든 이슈는 반드시 루트코즈에 연결되어야만 함(원인 추적 없는 건 의미 없음)

### ‘실사용된 증거’만이 변경의 정당성을 담보하며, 자동화 체크 기준도 명확히 세움

- 그린 신호(이상이 없음)에만 의존하는 것은 오히려 위험, 실제 데이터로 재현·검증된 증거(에비던스)만 신뢰함
- 새로운 체크 로직은 반드시 의도적으로 한 번 실패시켜 보는 데이터를 먼저 확보(테스트 검증)
- 에이전트 리팩터 후 분기(Branches)별로 실제 요청이 모두 도달하는지, 못 가는 분기는 증거 없음(evidence 없음)으로 판정하고 폐기
- 다른 에이전트가 체크리스트 기반으로, 작성자 논리와 무관하게 객관 검증

### 코드의 분기(branch)와 시스템 성장의 자연스러운 혼돈을 도구와 수치로 관리함

- 코드의 각 분기는 매주 실제 사용 데이터에 의해 존폐가 결정됨
- 실사용되지 않는 분기(branch)와 그에 딸린 테스트는 주기적 청소를 통해 폐기
- ‘래칫(ratchet)’과 같은 지표 도입: 해당 수치는 오직 감소만 허락, 더 이상 사용되지 않는 코드가 계속 존재하지 않게 함
- 매주 수십 개(10~20개) 오픈 루프가 유지 관리되고, 피드백은 모두 자동화되어 있음

### 시스템 유지관리의 궁극적 책임이 한 사람에게 집중되는 순간이 번아웃의 경계임

- 초기에 본인이 모든 변경사항을 읽어야 했으나, 시스템 성장과 함께 불가능해짐
- 자신의 ‘주의력’이 소모·고갈되는 순간이 위험 신호, 그린대시보드를 맹신하면 안되고 내부 게이지로 감지해야 함
- 시스템 내에 판단, 검증, 피드백 등 모든 루프를 내재화하여 책임을 분산(‘메시지 버스’를 자기가 담당해서는 안 됨)

### 시스템 설계 및 증거 체계에 설계자의 습관, 편향이 축적되며, 이는 발전과정에서 인식해야 할 가격임

- 본인의 엔지니어링 원칙 및 습관, 편견까지 시스템 내부에 자연스레 녹아듦
- Conway’s Law(조직 구조가 시스템 구조를 닮는다) 언급 : 시스템은 결국 ‘수정한 사람의 흔적’을 따라감
- 6개의 핵심 질문(각각 3개씩 소계 18개)으로 이 프로세스를 점검하며, 각 스톤(핵심 원칙)이 실무에 도움을 줌

### 실무자는 본인의 시스템에 답하지 못하는 질문을 찾아 개선의 시작점으로 삼아야 함

- 영상 후반에 18개의 체크리스트를 제시하며, 자신이 답할 수 없는 질문에서 개선의 실마리를 찾으라고 권고
- 해당 프로세스는 팀 오너십이 집중되어 있는 상황(모든 변경이 한 사람을 경유하는 체계)에서 ‘번아웃’에 도달하기 전에 도입해야 함
- 매주 모든 변경을 소규모, 증거 기반으로 관리하는 루프야말로 ‘한 번에 크게 쓸어내는(스냅)’ 위험을 피하는 유일한 방법임
