## *허술한 소프트웨어를 생산하지 않는 소프트웨어 팩토리의 12가지 원칙* 핵심 요약

- **소프트웨어 팩토리의 기본 구조**는 예전부터 이어진 좋은 엔지니어링 관행을 기반으로 하며, AI 도입 전과 크게 다르지 않음
- **AI와 에이전트 활용**은 ‘사람이 만드는 단계’를 ‘에이전트가 만드는 단계’로 대체해 자동화 및 효율을 높이지만, 여전히 인간의 검토·관리 필요
- **Slop(허술한 코드)의 문제점**을 실증적으로 분석하기 위해 Slop Code Bench 벤치마크 및 관련 연구 데이터를 공유
- **최근 모델(Slack, GPT-4/Astra 등)의 Slop 발생률**은 낮아지지 않고 있으며, 복잡도·코드 품질 지표상 개선 여지 많음 (예: GPT-5.5 15%, Astra 16.3%)
- **AI가 코드를 진화시킬 때의 한계**: 모델은 문제 전체를 명확히 알 때 복제(예: Excel, Redis 클론)엔 강하나, 실제 현업처럼 점진적 관리·개선에는 취약함
- **코드 품질 유지와 Slop 방지**를 위해 철저한 설계/계획, 형식검증, 일관된 규칙(ESLint, SlopBench 등)이 필요하며, 실험적 기능엔 feature flag 적극 활용 제시
- **AI 활용의 핵심 원칙**: ‘빠름’보다 ‘이해’, ‘양’보다 ‘결과와 품질’, ‘AI 초안’보다 ‘인간의 최종 검토’에 가치를 둠
- **‘Anti-Slop Manifesto(안티 슬롭 선언문)’**를 통해 Slop 없는 소프트웨어 및 지식 전달, 인간의 주도권 강화, 책임 강조
- **Slop은 AI 자체가 아닌 책임 없는 통과가 원인**이며, 리뷰 및 관리 없는 남발이 장기적으로 품질 저하, 협업 효율 감소로 이어짐
- **개발문화 변화**: 모든 결정·설계를 중앙화/일원화해 맥락과 기록, 소통, 품질을 높이고, ‘쉬움’이 아니라 ‘가치’에 집중할 것을 촉구

## 세부 요약 - 주제별 정리

### 소프트웨어 팩토리는 AI 이전부터 ‘좋은 엔지니어링 관행’을 계승해 발전해 왔음을 강조함

- 팩토리 개념은 최근 AI 열풍 이전에도 이미 30년 가까이 소프트웨어 엔지니어링에서 표준적 접근법임
- 핵심 구조: 개발자, PM, CEO 등의 공동 기획→트래커 등록→개발→테스트(유닛/자동/로컬)→PR 생성→타인 인터랙션 및 피드백→CI/CD→릴리즈 및 롤아웃→고객 피드백→문제 발생 시 모니터링 및 대응
- 본질적으로 ‘프로세스의 표준화’(공정의 일상화/자동화)에 초점
- 새로운 것은 에이전트가 ‘생산 단계’를 인간 대신 수행하거나 협업하는 부분에 있음

### 소프트웨어 팩토리에서 ‘전진 압력’과 ‘후진 압력’의 균형이 자동화를 성공으로 이끈다고 설명함

- ‘전진 압력’이란 새로운 작업을 착수케 하는 힘(예: 기능요청, 고객 이슈 등)
  - 기능요청·이슈 등을 자동으로 팩토리(에이전트)에 라우팅해 신속 대응 가능
  - 문제 발생 시 새 작업(PR)로 바로 연결되어 3AM 핫픽스 대응도 에이전트가 자동화 가능
- ‘후진 압력’은 작업물의 검증·품질 관리에 필요한 것
  - 예전 방식의 리뷰/테스트를 자동화·에이전트화해 속도와 품질을 동시 확보
  - 에이전트 코드리뷰, 에이전트 테스트, CI/CD, 린트, 형식검증 등 강력투입
- 인간의 개입 없이 ‘점진적 품질 상승’(hill climb)이 가능해야 진정한 생산 자동화가 성립

### Slop Code Bench 벤치마크와 실제 데이터로 AI 코드 생성의 질적 한계를 보여줌

- Slop Code Bench: 위스콘신대 연구진과 협력하여 코드품질을 다각도로 측정하는 벤치마크
- 최근 성능으로 GPT-5.5는 15%, Astra(GPT-4 파생)는 16.3% 기록 (모델의 코드 개선 능력 부족함 시사)
- 벤치마크는 코드 복잡도, 함수별 라인 수, 높은 복잡도 함수 비율 등 200여 맞춤 규칙(50개는 전통 규칙, 150개는 최신 AI 코드 특성 반영)으로 평가
- 최신 LLM들이 코드 스타일에서 퇴보하는 양상(예: 파이썬 F-string 대신 %s 사용 등)도 관찰됨
- 모델은 예전보다 ‘Slop(허술함, 불필요한 복잡성, 나쁜 습관)’을 강화하는 경향 있음

### ‘AI 코드 자동화’는 일부 문제(전체적 복제 등)에 강하나, ‘점진적 코드베이스 진화’에는 취약함을 증명함

- 모델은 문제 전체를 제시받고 단기 집중 작업(예: 엑셀, 레디스 클론)엔 강점
- 실제로 현업 소프트웨어는 ‘기능 추가→개선→수정→리팩터링’ 등 점진적으로 발전하므로, 자동화된 품질 유지가 어려움
- 인간은 개발 도중 ‘잘못된 추상화’, ‘분리 필요’ 등을 인지, 즉시 구조를 개선하지만 모델은 이에 취약

### 체계적 설계·기획과 팀 내 협의가 여전히 중요하다고 밝힘

- 단순 속도만 추구하면 커다란 리워크(rework, 재작업) 위험
- 아키텍처 리뷰, 스프린트 기획, 데이터베이스 스키마 등 변화 어려운 요소는 사전 합의/설계 필수
- 설계 명세/기획의 범위를 ‘얼마나 정성들일 것인가’를 기대 고통(수정확률×수정난이도)에 따라 조정하는 방법 제안
- 시각적 도구 활용(HTML 목업, 표, 차트 등): 영상에서 직접 만든 Show Me 툴(4만 명 사용)로 시각적 설계, 커뮤니케이션 최적화 강조

### 에이전트가 진정한 품질 개선자가 되기 위해 ‘테스트 환경과 검증 체계’를 갖춰야 함을 역설함

- 에이전트의 작업 완료 본인 검증을 도울 도구: 스크린샷·브라우저·동영상·curl 등 최대한 제공할 것
- 플랫폼별(예: iOS)로 빌드, 런, 테스팅까지 자동화 지원해야 품질 보장 가능

### TypeScript/파이썬 등 각 언어별 ‘Anti Slop’ 규칙, 린터, 검증도구를 적극 적용해야 Slop을 억제할 수 있음을 제시함

- Cloudflare 기술리더 Dylan Moroy가 만든 Anti Slop 레포: 100+, TypeScript용 코드 품질 자동점검 룰 제공
- Factory ESLint 플러그인, Slop Code Bench의 코드 품질 규칙 등 활용 권장
- Slop 자체가 항상 나쁜 건 아니며, 프로토타입·사이드프로젝트의 빠른 실험 단계에선 feature flag(Launch Darkly, PostHog 등)로 관리하고, 파생 코드의 프로덕션 유입 이전까지 선별적 품질관리 필요

### 좋은 소프트웨어 팩토리는 ‘지속적 평가·학습과 결정 이력의 일원화’를 통해 지식과 품질을 축적해야 함

- 모든 설계/결정/삭제/토론/실험 결과를 중앙 저장(예: GitHub·Notion·Google Docs 통합)
- Slack·이메일 내 LLM결과 공유 등 분산작업을 일원화해서 맥락 손실, 의도불명 위험 방지
- 모든 작업물이 어떤 결정의 결과물인지 명확히 추적 가능하게 해야 협업 혼선 최소화

### 소프트웨어 팩토리엔 ‘제품화 불가한’ 영역도 존재하며, 각 팀·조직의 개별적 기준과 역할이 절대적임을 밝힘

- 인프라/개발환경 등은 외부 서비스화 가능하나, 코드 검증·테스트 기준 등은 각 조직 특수성에 맞춰 직접 정립 필요
- 빌드 시스템, 협업 컨트롤 플레인, 자동화 등은 제품화(Frontier harness, open code, pie 등) 가능
- 그러나 코드 평가/검증 기준(특히 대규모 조직)에 ‘범용 블랙박스 솔루션’은 실효성 낮음

### ‘Anti-Slop Manifesto(안티 슬롭 선언문)’를 통해 Slop 없는 지식·코딩 문화를 촉구하고, 인간 주도 경계와 책임을 분명히 함

- 선언문 주요 가치: 결과(Outcome) 우선, 이해 중시, 속도보다 숙의, 인간 고유의 판단과 책임 강조
- AI는 역대급 도구이나, Slop(허술함)은 리뷰보다 생산이 더 쉬워진 AI 환경에서 반복되며, 장기적으로 코드/지식/커뮤니케이션 품질 악화 초래
- ‘AI의 초안’을 그대로 통과시키면 Slop 유발, 책임지고 검토·관리·의도·후과를 온전히 소유할 것
- PR·문서·코드 배포 시 ‘AI가 작업함’을 투명하게 표시, 슬랙/이메일 전 공유 전 스스로 최종 확인 필요
- Slop을 받으면 친절하게 재리뷰 요청, 이런 문화를 양방향으로 강화
- 에이전트·린터·형식 검증은 ‘필요’하나 ‘충분’하진 않음—결국 최종 승인·검토는 인간의 몫
- Slop이 나쁘다는 건 ‘결과를 생산자보다 소비자가 더 많은 노력을 기울여야 이해하거나 사용할 때’를 뜻함. 생산 시에는 책임감을 가져야 함

### Slop은 단순히 AI 사용 때문이 아니라, 책임 없는 검증/관리가 문제이며, Slop이 쌓일수록 장기 품질 저하와 동기 하락으로 이어짐

- Slop의 비대칭성: AI로 1000줄 PR·10페이지 문서 생성은 거의 무제한, 리뷰·이해 비용은 늘 일정
- Slop(허술함)이 쌓이면 다음 세대 에이전트·팀원이 이를 다시 참조하며 더 심해짐
- 단기 생산성보다 협업/품질/의사소통 저하 압력이 크므로 ‘항상 Slop 방지’ 노력 필요
 
### ‘인간의 역할’은 AI 제작물의 기획-검토-의도 소유로 귀결되며, AI는 인간의 판단을 강화하는 도구로 엄격히 활용해야 함

- 품질·효율·책임·절차 중심의 원칙에 따라 AI/에이전트를 운영
- 지속적인 반성, 관리, 판별, 후과 책임을 강화: “내가 보내는 모든 코드는 내가 의미와 Taste를 소유”, “AI는 도우미이나 판단의 대체자가 아님”
- 생산 과정에서 도구와 지식, 기존 코드, 협업 결정을 적극 활용·참조하여 문제를 본질적으로 이해해야 함
- 최종 제품의 사용처·가치가 코드라인수, PR수, 병렬 실행 에이전트 수보다 중요함
