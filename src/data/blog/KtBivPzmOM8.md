## *메모리 인지 에이전트 하니스가 자금세탁방지에 어떻게 활용되는가 — Nacho Martinez, 오라클* 핵심 요약

- 영상 제목: *메모리 인지 에이전트 하니스가 자금세탁방지에 어떻게 활용되는가*
- 발표자는 오라클의 AI 개발자 에반젤리스트 Nacho Martinez로, 주제는 AI 에이전트 하니스의 실제 설계와 자금세탁방지(AML) 워크숍에 초점을 맞춤
- 세션의 실습 환경은 GitHub Code Spaces와 워크숍 참여 웹사이트(WorkshopWaitingRoom.com) 연동으로 구성되며, 실질적 에이전트 구축을 목표로 함
- 오늘 다루는 주요 개념은 ‘에이전트 스택’의 구조, AI 애플리케이션의 다양한 형태, AI 에이전트의 정의, 그리고 에이전트 하니스(도구, 메모리, 인지 설계)
- Frontier LLM(예: OpenAI 제공)에 직접 개입하는 대신, 하니스 레이어(메모리/도구/인지) 커스터마이즈에 집중하는 것이 실제 성능에 큰 영향을 미침
- 은행의 실제 예시를 기반으로 다양한 이상 거래 탐지를 AI 에이전트가 자율적으로 실행하며, 이때 사람 개입을 최소화하면서 초기 분류·Flagging 작업을 효율화 함
- 하니스를 이루는 핵심 구성요소로는 저장소(파일/DB), 인코딩·검색, 메모리 분류(단기/장기/일화/절차/의미기억), 에이전트 루프, 컨텍스트 엔지니어링 등이 있음
- 메모리 한계(컨텍스트 윈도우) 극복을 위해 요약, 컴팩션, 벡터 임베딩, 하이브리드 검색(키워드+의미) 등 다양한 기법을 활용하며, 실제 예제와 워크플로우가 소개됨
- 실제 도구·스킬 관리는 벡터 임베딩 기반 검색으로 구성되어, 요청마다 최적의 여러 개 도구/기술이 동적으로 맥락에 삽입됨 (‘스킬 디스틸레이션’ 등도 설명)
- 워크숍을 완료하면 자율적 의사결정과 실시간 이상거래 분석이 가능한 데이터베이스 연동 AI 에이전트 구축 능력 함양이 목표

## 세부 요약 - 주제별 정리

### 세션은 자금세탁방지 은행 사례를 통해 메모리 중심 에이전트 하니스를 실습하는 구조로 설계됨

- 워크숍 실습을 위한 GitHub 연동 안내가 초기에 제공됨(WorkshopWaitingRoom.com 접속, QR코드로 워크숍 리포지토리 자동 접수)
- 참가자는 Code Spaces에서 제공되는 환경에 접속하여 실제 AI 에이전트의 하니스 구성과 데이터 흐름을 실습
- 모든 실습 데이터와 트랜잭션은 예제용 가상 데이터임을 명시
- 발표자는 오라클 AI 개발자 에반젤리스트이자 데이터 과학자로, 최근 Andrew Ng와 Developing Adaptive AI Agents 강좌를 공개(딥러닝AI 플랫폼, 1시간 무료 수강 가능)
- 실습 환경에서 Fraud(이상 거래) 자동 감지, 인간의 업무 부담 감소 등이 실제 주요 결과물로 제시됨
- 참가자는 실습 중 직접 각 하니스 요소(메모리, 도구, 컨텍스트 등)를 수정·확장해볼 수 있음
- 세션 후 오라클 부스에서 추가 Q&A 가능

### 에이전트 스택 구조는 ‘데이터 레이어’ 중심으로 제어 가능하며 이는 실질적 커스터마이즈의 핵심임

- AI 에이전트 스택은 (1) 애플리케이션 계층, (2) 모델/LLM, (3) 인프라/컴퓨트, (4) 데이터 계층으로 구분됨
- LLM(모델) 자체는 오픈AI 등에서 제공, 직접 수정 불가하나 데이터 계층(메모리, 입력, 검색, 도구 등)은 개발자 재량으로 설계
- 의사결정 및 워크플로우의 유연성은 데이터 및 에이전트 루프 설계에 좌우됨
- 예시로 LLM 챗봇, RAG(검색 기반), 워크플로우 자동화, 완전자율 에이전트 등 다양한 형태의 AI 애플리케이션이 언급됨
- 우수 시스템(Cloud Code, CodeX, Pi, OpenClaw, Hermes 등)은 자동화(Automation)와 자율성(Autonomy)을 조합한 에이전틱(Agentic) 구조임

### AI 에이전트는 인간의 인지 구조(메모리, 인지, 툴 사용)를 모방하며, 하니스가 실질 기능 대부분을 결정함

- AI 에이전트는 LLM의 추론(Reasoning)을 핵심 두뇌로 하며, 데이터베이스(메모리), 도구(액션), 입력(센서), 컨텍스트 제한 등 인간과 유사한 기능 구조를 채택
- Frontier LLM(추론)의 동작은 블랙박스이나, 메모리·도구·인지(perception)는 하니스(harness)에서 전적으로 제어 가능
- 동일한 모델도 하니스 설정에 따라 업무수행 효율과 품질이 현저히 달라짐(실제 실험 결과 인용)
- 하니스의 세부 구성요소: 모델, 저장소(파일/DB), 인코딩·검색(벡터 임베딩), 메모리 구조, 의미 계층, 에이전트 루프, 컨텍스트 엔지니어링 등
- “의미 계층”(semantic layer)은 맥락·전제가 주어지지 않아도 인간처럼 암묵적 정보를 제공하는 구조

### 파일·데이터베이스 선택, 멀티에이전트 동시성 문제 등 실무적 딜레마와 해법이 논의됨

- 다중 에이전트가 하나의 파일에 동시에 쓰는 경우 ‘워크트리(Work Trees)’ 등이 현 솔루션이나, 트랜잭션 일관성 문제로 데이터베이스가 더 적합한 상황 다수
- 예전부터 데이터베이스는 ACID(원자성, 일관성, 고립성, 지속성) 제공으로 병렬 처리 안정성을 확보하고 있음
- 실제 하니스 설계 시 용도에 따라 파일과 데이터베이스를 혼용할 수 있고, 업무 동시성 고려가 중요함

### 메모리 레이어는 단기·장기·에피소드·절차·의미기억 등 다층 구조로 설계되어야 함

- 단기메모리(short-term memory)는 기존 LLM의 컨텍스트 윈도우(사용자-에이전트 단발 세션)에 해당, 컨텍스트 창 크기는 매우 제한적
- 장기메모리(long-term memory)는 에피소드(과거 대화·이벤트·로그), 절차(기술, 워크플로우 지식), 의미(사용자 취향·경험·기초지식)로 분류 저장
- 예) 클라우드와 코드엑스는 대화가 끝나면 모든 컨텍스트가 사라지는 구조, 장기기억은 별도 벡터스토어나 DB에 보관
- 의미기억(semantic memory)은 사용자가 명시하지 않아도 추론 가능한 선호·배경지식 등을 담음

### 컨텍스트 윈도우 한계와 모델 성능 희생 문제를 극복하려 다양한 요약, 컴팩션, 임베딩 기법 도입됨

- LLM 모델은 컨텍스트 창이 커질수록 성능이 악화됨(논문 및 실험적 수치: 0~256,000토큰 대와 1백만 토큰 한도 비교)
- 컨텍스트 요약(context summarization): 이전 맥락을 짧게 요약하여 다음 대화의 시작점으로 삼는 방식
- 컴팩션(compaction): 대화 청크(chunk)를 세그먼트로 저장, 필요시 식별자(ID)로 신속 조회
- 적절한 설계가 없으면 성능이 극단적으로 저하되므로, 주요 설계 포인트 중 하나로 작용

### 에이전트 루프(Loop)는 도구·기술·기억 등 각 요소를 동적으로 조립·호출하는 ‘플로우’의 핵심임

- 에이전트 루프는 ‘컨텍스트 어셈블리(조립) → 추론(Reasoning) → 행동(도구/스킬 실행) → 재귀’ 구조
- 루프는 최대 반복 횟수, 시간 제한 등 엔지니어가 설정(예제 워크숍에서는 8회·60초 제한)
- 각 단계마다 도구 및 기술은 벡터스토어에 임베딩된 토큰 유사도 검색으로 동적으로 삽입
- 도구 및 기술이 컨텍스트 창의 50% 이상을 차지할 수 있음—효율적 선택·벡터화 필수

### 도구와 스킬 관리는 임베딩, 유사도 검색, 디스틸레이션 등 최신 기법을 도입해 ‘핵심만 삽입’ 원칙을 따름

- 기술 및 도구 각각을 벡터 임베딩 처리 후, 현재 요청과 가장 유사한 Top-N만 컨텍스트 창에 동적 할당
- 예) code base에 100가지 스킬이 있어도 매 요청마다 연관성 높은 3종만 로드(유사도 검색→재랭커 적용 가능)
- 과거 대화나 성공 사례를 반영해 ‘스킬 디스틸레이션(skill distillation, 요약 스킬 저장)’ 전략 적용
- 디스틸레이션 예시: 프론트엔드 작업에서 사용자가 선호하는 스타일이 있을 때, 해당 스킬을 벡터화 저장 → 다음 프론트엔드 작업 요청 시 유사 스킬 자동 선택
- 하이브리드 검색(RRF): 임베딩 기반 의미 검색+키워드 검색 결합, 검색 질 개선

### 프론티어 모델의 한계(‘프리징’)는 하니스의 데이터/임베딩 측면 커스터마이징으로 극복이 가능함

- ‘프리즌 모델’(frozen model)은 Frontier Labs(예: OpenAI) 모델처럼 사용자는 파라미터 조정 불가
- 지속학습(Continual Learning)의 유형: 파라메트릭(Fine-tuning), 임베딩/표상 기반(Representational), 비파라메트릭(메모리 레이어)
- 워크숍은 비파라메트릭(데이터, 임베딩, 메모리 레이어) 전략이 중심
- 파라미터튜닝/RA(저차원 보정), 커스텀 임베딩 모델 등 다른 전략은 별도 온라인 강의에서 상세히 다룸

### 시스템 프롬프트, 유저 프롬프트, 도구·스킬 등 각 구성요소는 ‘지시 계층’ 내에서 가중치가 다름

- LLM의 입력에는 시스템 프롬프트(최고 가중치, 규정 및 전제), 유저 요청(중간), 도구·스킬/문서(가장 낮음)가 계층적으로 포함됨
- 실제 요청의 80% 이상이 도구·스킬/DB 연동 문서를 차지(실제 토큰 수치: 10,000~100,000 토큰)
- OpenAI 등은 ‘시멘틱 캐시’를 통해 동일한 프롬프트에 대한 비용 상승을 억제함
- 효율성이 중요한 경우 첫 system prompt 최소화(예: Pi는 6,000토큰, 일부는 3~4만 토큰)

### 워크숍 환경에서는 실제 자금세탁방지(AML) ‘프랫 리스크’ 사례에 자동화 에이전트가 적용됨

- OCI 기반 Groq 모델이 중심, 자율 실행되는 에이전트가 은행 거래를 24/7 감시
- 이상 거래 감지는 사람이 결정하기 전 자동 Flagging 및 분석 결과 생성, 이후 사람이 직접 검토함
- 실시간 데이터베이스 연동, 컨텍스트 창 시각화, 이벤트 이력 확인 및 각종 도구 연동(툴박스 내 자산 탐색)
- 학생 노트북에는 각 영역별 투두(To-Do)가 준비됨—참가자별 맞춤 실습 플로우 구성

### 실무 메모리 관리와 도구 효율화는 단순 구조, 벡터화, 요약·기억 저장, 컨텍스트 윈도우 제어가 핵심임

- 메모리 레이어는 가능하면 단순하게(단기, 장기 2구조 → 기준에 따라 장기로 승격) 설계 권장
- 장기기억은 벡터 임베딩 후 필요시 쿼리 유사도 기반 검색/호출, 관찰-추론 단계 간 ‘리콜’ 방식 적용
- 도구·스킬은 일괄 임베딩 후 lean하게 Top-k만 로드, 필요시 reranker나 하이브리드 검색 도입
- 데이터베이스용 MCP는 쿼리 프리셋 제공으로 AI의 SQL 고정·오류 방지 효과

### 맞춤 하니스 설계는 복잡하지 않게, 문제 특화 최소구성에서 시작할 것을 제안함

- 최신 에이전트 하니스 솔루션(Pi, CodeX, Cloud Code 등)이 있지만, 실제 엔지니어링에서는 문제/고객별 맞춤 소형 하니스 설계가 현실적임
- 컨설턴트 등 고객 별도 요구, 데이터 구조에 따라 하니스 설계 변경(예: 증권, AML, 자동화)
- 모든 작업은 결국 Chat Completions API 기반으로 구축됨 (OpenAI/Anthropic 등 포함)
- 하니스 구조 간소화·불필요 기능 배제 → 관리·성능 최적화가 관건임
