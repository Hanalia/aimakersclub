## *AI 에이전트가 감독 없이 독자적으로 일할 수 있는 시점 판단 방법* 핵심 요약

- 본 영상은 Coinbase의 Evan Kormos가 엔터프라이즈 내에서 정책 기반 워크플로우에 AI 에이전트를 신뢰하며 적용하는 방법을 설명함
- 조직 정책(Policy)을 “본래 시스템 프롬프트”에 비유하며, 실제 운영 시스템과 분리해 정의하는 것이 핵심임
- 엔터프라이즈 환경에서는 사람, 프로세스, 기술의 3요소에 에이전트가 가로지르는 운용 모델로 관여함
- DAG(Directed Acyclic Graph, 방향성 비순환 그래프)와 DCG(Directed Cyclic Graph, 방향성 순환 그래프)를 활용해 복잡한 워크플로우와 반복 루프, 예외 흐름을 모델링함
- 소프트웨어 배포, 상업 대출 승인, 토큰 상장 등 다양한 도메인 사례로 에이전트와 프로세스의 융합을 구체적으로 설명
- 워크플로우 성능 개선시 각 단계별 병목, 작업량 변동 발생이 중요한 이슈이며, 운영 가시성(Metrics, Traces) 확보가 필수적임
- 에이전트 품질 평가는 입력(컨텍스트) 품질 관리와 더불어 반복적 평가 및 통계적 신뢰(Repeated evaluation, representative data set 등) 메커니즘이 필요함
- 에이전트 자동화 적용의 적합성 판단을 돕는 기준(정책 준수 용이성, 반복적 루프 적합성, 추적 가능성, 휴먼 백업 등)을 제시
- AI/에이전트를 처음엔 사람이 감독하며 점진적으로 “샘플링 검사 → 예외 처리 중심 관리”로 신뢰와 자동화 수준을 끌어올리는 단계적 도입 전략을 제안함
- 에이전트 기반 운영모델 확장은 소프트웨어 품질 향상, 팀 협업 강화, 신뢰 구축 효과를 가져온다고 결론짓고 있음

## 세부 요약 - 주제별 정리

### 조직 정책과 실제 시스템은 분리해 설계되어야 신뢰성이 확보됨

- 조직 내 모든 워크플로우는 반드시 분명한 정책(Policy)을 기반으로 설계돼야 하며, 해당 정책은 업무수행 규칙, 위험관리, 컴플라이언스 규정 등을 정의함
- “정책” 자체는 제도적 의도이자, 시스템 최초 프롬프트에 비유할 수 있음
- “must/should/may”와 같은 용어로 정책 적용 범위와 필수성 명확하게 서술
- 정책 정의(빌드 단계)와 실제 시스템 실행(런 단계)은 시간적으로 항상 분리되어 있음
- 정책이 변경되더라도, 실제 운영계에서는 워크플로우가 끊임없이 변화·진화하므로 디자인과 운영을 분리하고 상시 일치시키는 노력이 중요

### 에이전트는 사람·프로세스·기술을 가로지르며 기존 운영 모델을 재구성함

- 엔터프라이즈 모델 3요소(사람, 프로세스, 기술) 모두에서 AI 에이전트가 교차적으로 개입함
- 에이전트는 사람과 협업하고 프로세스의 특정 부분을 직접 실행하며, 스스로 기술로 만들어짐
- 본 발표는 에이전트와 프로세스가 만나는 지점, 즉 업무를 어떻게 배분하고 경계(경험, 결과 신뢰성)를 어떻게 설정할지에 초점

### 워크플로우 구조는 DAG로 병렬화·효율화가 가능하며, 코드로 모델링하는 것이 효과적임

- 워크플로우 진행 방향이 “순환 없는 방향성 그래프(DAG)”로 모델링될 때, 병렬 처리가 용이해짐
- 예시: 소프트웨어 배포 승인, 고객 인증 및 계좌 개설, 상업 대출 등 절차에서 여러 단계가 병렬 처리로 최적화될 수 있음
- Apache Airflow와 같은 오픈소스 툴이 DAG 구조를 코드(Python 등)로 표현하는 대표적 사례
- DAG 형태로 워크플로우를 모델링하면, 업무 병목/병렬 조건·의존성·결과 통합 관리가 과거보다 더 쉽고 유연하게 이루어짐

### 반복 루프와 예외 처리까지 아우르려면 DCG 및 상태관리 라이브러리 활용이 중요함

- DAG 안의 각 노드는 실제로 “반복 루프(순환)”를 포함하는 경우가 많음(예: 코드리뷰 - 수정 반복)
- 이런 반복은 DCG(Directed Cyclic Graph)로 표현하며, LangChain의 LangGraph 등 오픈소스 도구로 각 노드의 상태를 관리할 수 있음
- 루프 구조가 커지고 복잡해질수록 예외 플로우, 에이전트·사람의 조합, 정책 경계 설계의 어려움이 커짐
- 모든 예외 케이스를 미리 설계할 수 없으므로, 정책 이탈·작업 중단 등 예외 흐름 감시 체계를 갖출 필요 있음

### 입력(컨텍스트) 품질이 결과 품질 결정에 핵심적 역할을 하므로 관리가 필수적임

- AI 엔지니어링에서 가장 큰 도전 중 하나는 “입력/출력 변동성(variability)”임
- “고품질 입력”을 설계함으로써, 더 적은 연산/비용으로 고품질 결과를 얻을 수 있음
- 입력 품질은 주로 컨텍스트 모델링(정보 범위, 풍부함, 적시성 등)에서 영향을 받음
- DAG의 상태(State)를 에이전트에 주입하여, 각 단계에서 자신이 전체 프로세스에서 어디에 위치하는지 알 수 있도록 하는 것도 유효함

### 정책과 신뢰의 기준인 ‘체크(평가/검증)’를 명확히 해야 에이전트의 품질을 보장할 수 있음

- 실제 업무에서는 반복적 루프의 “통과 조건”을 정의하는 체크 포인트가 품질 결정에 본질적
- 어떤 작업이 “충분히 좋음(good enough)” 상태인지 전문가(SME, Subject Matter Expert)와 합의된 평가 기준이 필요함
- 체크 기준과 검증 방법이 신뢰할 수 없다면, 반복 횟수를 늘려도 품질은 보장되지 않음
- 결과 평가는 단순 비교가 아닌, 반복 평가·대표 데이터셋 구축, 통계적 분석 등 체계적 방식이 필요

### 에이전트 신뢰성을 확보하려면 인간·AI 협업, 데이터셋, 평가 시스템 구축이 필수적임

- 기존 SW 테스트(유닛 테스트, 케이스 기반)는 결정적(deterministic) 방식이지만, AI 에이전트는 확률적(probabilistic)이므로 결과 다양성 발생
- 동일 요청에도 결과가 다를 수 있고, ‘허용 가능한 여러 답’이 공존할 수 있음
- 대표 평가 데이터셋, 반복적 통계 분석(Repeated evals), 런타임 trace(로그 데이터) 등 혼합 신뢰 메커니즘이 요구됨
- 이 체계는 전통적 SW 품질 관리와 상호 보완적 역할(Confidence mechanism) 수행

### 각 노드·단계별로 에이전트 자동화 적합성을 질문 기반으로 평가할 수 있음

- 예시: 대출 심사 프로세스에서 KYC, 재무 검토 등은 자동화 적합/결정 단계(최종 정책 체크)는 인간이 담당해야 함
- 자동화 적합성 기준 : 정책 기준과 쉽게 대조 가능, 반복적 검증 가능, 기록/추적 가능, 휴먼 백업 체계 존재 등
- 각 노드에서 “에이전트가 담당했을 때의 효과성”을 구체 질문(위 기준)으로 사전 진단함
- 전체 DAG 내에서는 “AI가 부분 지원”에서 “AI가 전체 담당”으로 점진적 권한 이양을 설계 가능

### 감독적용(슈퍼바이즈드)을 시작으로, 점진적 신뢰 임계치(Threshold)에 도달하면 자동화 수준을 높여감

- 자동화 도입 초기는 반드시 사람이 에이전트 결과를 100% 검토(슈퍼바이즈드)해야 함
- 추후 데이터셋·평가지표가 고도화되면, “샘플링 평가(일부만 사람이 확인)”로 전환
- 신뢰 임계치 달성 후에는, 사람은 예외 상황·데이터셋 개선 중심 역할에 집중하고, 반복적 품질 평가(트레이스·통계 기반)로 전체 품질 유지
- 이러한 “감독→부분 검사→완전자동화+예외관리”의 단계적 전략을 통해 신뢰 기반 자동화 전환을 실현

### 외부는 결정적(deterministic), 내부는 적응적(adaptive)으로 프로세스를 설계해야 성공적으로 에이전트를 통합할 수 있음

- 전체 운영 프로세스 외부 경계(정책)는 의도적으로 결정적으로 설계해 일관성 유지
- 내부 노드(에이전트/루프)는 통계적, 적응적으로 동적 변화 허용하여 효율 극대화
- “품질 평가→신뢰 구축→자동화”의 순환 강화로 궁극적 팀 협업, 애플리케이션 품질, 운용 체계가 진화함을 강조

### 품질과 신뢰성은 팀 전체의 과제로, 평가/통계 기반 접근이 신뢰를 높임

- AI 엔지니어는 각종 신호(Signal)와 실사용 데이터, 운영 평가지표(MLOps) 등을 수집해 지속적으로 애플리케이션 품질을 관리함
- 신엽이 “느낌”이 아닌 구체적 평가(Research, Statistics)에 기반해 신뢰 메커니즘을 구축함을 강조
- 궁극적으로, 에이전트 도입은 모든 운영체계의 병목 해소, 업무 병렬화, 품질·신뢰성 향상을 목적으로 진행되어야 마땅함

### 다양한 도메인 사례 참고자료와 함께 발표 마무리

- 소프트웨어 전달, 대출 심사, 토큰 상장 등 산업별 DAG/DCG 활용 사례 소개 및 범용 원리 강조
- 관련 오픈소스 툴, 논문 등 참고자료 링크 제공하며 강연을 종료함
