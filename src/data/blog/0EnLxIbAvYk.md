**채널명:** AI Engineer

## *당신의 명세서에도 버그가 있다. 에이전트가 코딩하기 전에 잡아라* 핵심 요약

- AWS 자동화 추론 그룹의 Rajat Kotyal이 최근 작업한 ‘Keto Specification Analyzer’ 프로젝트와 그 배경, 동기를 소개
- 명세(스펙) 파일 내에서 발생할 수 있는 문장 간 모순, 애매함, 누락 등은 대형 언어모델(LLM)이 코드를 생성할 때 심각한 문제를 초래함
- 공개 연구 결과, 명확하지 않은 프롬프트의 경우 LLM의 코드 생성 정확도가 20~40% 감소한다는 수치가 있음
- 실제로 LLM이 생성한 코드의 60~90%가 형식적으로는 맞으나 실질적으로는 잘못됨을 확인
- 이렇게 생성된 부정확한 코드는 배포 시 두 배 더 많은 회귀(regression)를 유발함
- Keto Specification Analyzer는 세 단계 과정을 통해 스펙의 모순·애매함을 자동 검출: ① LLM을 활용한 문장 정제 ② SMT(Satisfiability Modulo Theories) 방식 논리공식화 ③ 논리적 군집화와 사용자 개입 요청
- LLM의 다양한 해석 경향을 7~10회 번역 반복과 논리적 군집화로 파악하여, 어떤 부분이 진정한 문제인지 가려냄
- 최종적으로 스펙 검증은 사용자의 도메인 지식과 결정이 필수적임을 강조하며, 도구 활용만으로 완전한 자동 검증은 불가능함
- 주요 사례와 명세 내 불일치·결정 미정 구문(모호한 삭제 규칙 등) 코드화 시의 문제점을 자세히 설명
- 요약: 스펙은 반드시 LLM에 넘기기 전에 꼼꼼히 검증해야 하며, Keto와 같은 툴로 자동화된 검증 지원을 받을 수 있으나 궁극적 책임은 사용자에게 있음

## 세부 요약 - 주제별 정리

### Keto Specification Analyzer는 코드 작성 전 명세의 논리적 오류를 자동화 기법으로 탐지함

- 발표자 Rajat Kotyal은 AWS 자동화 추론(Automated Reasoning) 그룹 소속임
- 최근 직접 참여한 프로젝트로 ‘Keto Specification Analyzer’를 설명
- 이 툴은 LLM 기반 코딩 에이전트에게 명세가 전달되기 전에 오류와 모순을 미리 탐지하는 것을 목표로 개발됨
- 접근법은 형식적 기법(formal methods)과 자동화된 논리추론(automated reasoning)에 기반을 둠
- 명세 단계의 오류 방지로 실제 코드 작성 및 운영 과정에서 발생하는 비용을 줄이고자 함

### LLM이 명세 속 모순 규칙을 코드로 옮기면서 오류가 발생할 수 있음을 실제 사례로 설명함

- “재고가 없을 때 주문을 백오더로 전환한다”와 “어떤 주문도 백오더로 처리하지 않는다”는 두 규칙사이의 모순을 시연
- 각 문장만 따로 읽으면 합리적이지만, LLM이 두 규칙을 동시에 처리할 경우 논리적 모순이 생김
- 이러한 모순은 명확하게 해결되지 않으면 LLM이 잘못된 코드를 생성하게 만듦
- 스펙 파일을 최초로 검토하는 주체가 더 이상 인간이 아니라 LLM이 되면서, 명세상의 애매함이나 상충을 사전에 탐지할 필요가 커짐

### 명확하지 않은 프롬프트로 인해 LLM 코드 정확도가 현저히 하락하는 데이터가 제시됨

- 공개 연구와 최근 실험에 따르면 프롬프트가 명확하지 않으면 LLM이 생성하는 코드의 정확도는 20~40%까지 감소
- 생성된 코드의 60~90% 정도가 문법적으로 타당해도 실질적으로는 잘못된 결과를 내는 경우가 많음
- 이렇게 잘못된 코드가 배포될 경우, 두 배 더 많은 회귀(regression) 문제가 발생함
- 이는 명확한 명세서의 중요성을 데이터로 뒷받침

### 문장 차원, 문단 차원에서 애매함·논리적 충돌이 숨어있는 구조를 LLM이 인식하지 못하는 한계가 있음을 밝힘

- 한 문장 내에서도 모호성(ambiguous wording), 디테일 부족(level of detail)로 해석이 달라질 수 있음
- 여러 규칙·문장이 조합될 때, 단일 규칙만으로는 알 수 없는 갈등(conflict)이나 빈틈(gap)이 드러나기도 함
- 사람의 1차 검토 없이 LLM이 문서를 처리하면 이런 의미적 충돌이 그냥 코딩으로 이어질 가능성이 높음
- 이러한 애매함, 충돌, 누락을 검출하고 표시해주는 자동화 툴의 필요성을 강조

### Keto의 3단계 추론 및 검증 과정: LLM 정제 → SMT 공식화 → 논리 클러스터링 및 사용자 개입

- 1단계: LLM을 통해 명세 문장 자체의 애매함·모호함을 우선 정제(리파인) 시도
- 2단계: LLM이 정제하지 못한 부분은 SMT(Satisfiability Modulo Theories) 라이브러리 포맷으로 형식화, SAT solver(충족가능성 판별기)를 이용해 논리적으로 타당한지 검사
- 3단계: SAT solver가 모순·애매함을 발견하면, 다시 LLM에 해당 문장을 재검토시키며, 이 과정을 반복함
- 논리공식의 판정 결과가 True(유효)라면 그대로 두고, False(유효하지 않음)라면 의심 구문으로 표시
- 이 과정에서 복잡한 수학공식(예시 SMT 포맷)으로 문장 내용이 표현됨

### LLM이 내포한 해석 다양성을 논리 등가 군집화로 식별해 실제 오류와 한계점을 구체적으로 파악함

- 동일 명세를 LLM이 7~10회 번역·해석시켜 다양한 표현과 해석의 분포를 확인
- 각 해석을 논리적 등가(logical equivalence) 단위로 군집화, LLM이 내부적으로 어떤 가정 하에 어떤 결과를 내는지 분석
- 이 과정을 통해 LLM의 한계(오류가 반복되는 맹점) 혹은 실제 명세상의 오해가 발생하는 지점을 분리해냄
- 발생한 군집의 논리적 불일치 여부, 특정 해석이 반복적으로 오답인 이유를 규명할 수 있음
- 특정 규칙의 모순/누락이 확정되면 사용자에게 명시적으로 판단 또는 수정 요청

### 실제 명세 예제를 통해 명확하지 않은 규칙 구문의 위험성과 사용자 개입의 필요성을 실례로 제시함

- 예시: “레코드를 제거한다(Remove the record)”는 매우 모호한 지시로, LLM은 삭제 또는 숨김 등 다양하게 해석할 수 있음
- 해결책: LLM이 임의로 결정을 내리는 대신, 명확한 선택지(삭제 또는 숨김 중 선택)로 사용자의 판단 요청
- 규칙 간 충돌의 정의: 예시로 본 두 규칙(백오더 관련)이 서로 배타적으로 상충하는 상태
- 규칙의 빈틈(gap)의 정의: 예를 들어 유휴 주문(idle order)에 대한 규칙이 아예 명세서에 존재하지 않을 때
- 이런 결함의 존재를 확인하면 사용자 수정, 명시적 보완 없이 코딩을 진행하지 않도록 경고

### 최종적 명세 검증·의사결정은 인간 사용자에게 귀속되며, 도구는 지원 역할에 그침을 강조함

- 아무리 자동화 도구를 활용해도, LLM에게 완전한 도메인 지식(Domain knowledge)을 기대하긴 어려움
- 명세의 각 부분에 대한 적합성과 완전성 보증은 결국 인간 사용자만이 제공 가능
- Keto 등의 툴은 검증 지원·오류 표시 등의 한정적 역할만 하며, 핵심 책임은 사용자에게 있음
- LLM 해석, 논리 판별 결과, 사용자 선택 3단계 루프를 통해 정확성 확보

### Keto Specification Analyzer의 프로세스를 요약함: LLM 번역, 논리 판정, 사용자 판단의 3단계 역할 분담

- 1) LLM이 명세를 다양한 방식으로 번역 및 해석
- 2) SMT 판정기가 논리적으로 가능·불가능을 판정
- 3) 모순 또는 불일치 발견 시, 사용자가 직접 수정·결정 내려야 함
- 자동 해결이 불가능하면, LLM의 판단 혹은 해당 구현을 보류(Abstain)하는 방식을 채택
- 이 워크플로우는 반복적으로 다양한 명세 조각에 적용 가능함

### 현재 형식적 명세 자동 검증 분야는 도입 초기 단계임을 밝히며, 참조자료 및 추가 정보 공유로 마무리함

- 형식화 및 자동화 검증이 실제 코딩 에이전트, LLM 활용 맥락에서 어떻게 자리잡을지는 초기 연구 단계
- 현재로서는 ‘자동화된 명세 검증’이 실무 적용에 있어 연구·실험이 병행되고 있음을 언급
- 발표 마지막에 팀 블로그 및 웹사이트 참조자료, 추가 읽기 리소스 링크를 안내하며 종료
