## *당신의 에이전트 수정이 다른 문제를 야기했습니다 - Sofia Jakovcevic, Arize AI* 핵심 요약

- 이 영상은 AI 에이전트 시스템의 디버깅 및 회귀(Regression) 테스트를 체계화하는 방법과, Arize AI 플랫폼을 통한 구체적 접근법을 설명함
- 에이전트 기반 AI 시스템은 블랙박스 특성이 강해 런타임에서 예기치 않은 실패가 자주 발생하며, 이는 코드 수정만으로는 발견하기 어렵다고 지적
- 단순한 자연어 프롬프트 한줄 추가도 실제 동작에 미묘하고 광범위한 영향을 끼칠 수 있으며, 보안 정책 개선이 동시에 업무 완료율 저하로 이어질 수 있음을 실제 사례로 시연
- 회귀 테스트를 위해서는 코드의 diff(변경 내역)만 볼 것이 아니라 실제 동작 로그, 즉 트레이스(trace)를 중심으로 평가해야 한다고 강조
- 체계적인 회귀 프로세스를 위해 5단계 과정을 제안: 실제 생산 데이터셋 선정, 평가 지표 설정, 베이스라인 실험 실행, 변경 적용 후 평가 반복, CI/CD 파이프라인에 통합 자동화
- 여러 평가 지표(예: 할루시네이션, 정확도, 도구 활용 효율, 작업 완료 여부 등)는 LLM 활용, 코드 평가, ML 기반 방식 등으로 정량화 가능
- 실험 및 평가 자동화는 Arize 플랫폼 내 플레이그라운드(UI)와 SDK, CI/CD 시스템을 통해 실제 적용 가능함을 데모로 시연
- “실패 케이스”를 자동으로 새로운 회귀 테스트에 추가하는 루프 구조로, 테스트 및 개선이 점차 탄탄해진다는 점을 시사
- 미래 관점에서 궁극적으로는 인간이 아닌 에이전트 스스로가 관찰·분석·개선하는 ‘에이전트 자기개선’ 패러다임으로의 전환을 강조하며 마무리함

## 세부 요약 - 주제별 정리

### 단순한 코드/프롬프트 변화도 예측 못한 런타임 문제로 이어질 수 있음을 실제 사례로 보여줌

- 지원(agent) 시스템에 보안 엔지니어가 ‘행동 전 확인’ 문구 한 줄을 프롬프트에 추가하도록 요청
- 자연어 프롬프트 변경이기 때문에 개발자들은 ‘직관’에 따라 별 생각 없이 변경 적용
- 실제로 이 변경 후 평가를 돌려보니 ‘행동 안전성(action safety)’은 17포인트 상승
- 그러나 작업 완료율(task completion)은 17포인트 하락. 이유: 매번 확인 요청 시, 사용자가 세션을 떠나 미완성 task가 발생하는 우려
- 결과적으로 평균점수는 변화 없음(0점), 즉 부분 최적화로 전체 성능에는 영향 없거나 오히려 악화 가능
- 이 사례는 개선 의도의 사소한 변경도 운영 실제에서는 전혀 다른 결과를 낳을 수 있음을 강조

### 에이전트 실패는 코드가 아닌 런타임에서 일어남을 분명히 함

- 코드 변경(diff)은 코드리뷰 상에서 쉽게 파악 가능하나, 실제 동작상의 변화는 ‘실행(traces)’에서만 확인 가능
- 에이전트는 수백~수천 가지 경로, 도구 호출, 서브에이전트 협업 등 ‘런타임 행위’에 거대한 변화가 발생할 수 있음
- 전통적 소프트웨어는 논리가 코드에 명확히 담겼으나, 에이전트 시스템의 실제 논리는 실행 로그(traces)에 오히려 포함됨
- 따라서 회귀 테스트의 출발점은 트레이스(실행 기록)에서 찾아야 하며, 코드 리뷰만으론 이해 불가능

### 트레이스 기반의 5단계 회귀 테스트 프로세스를 구체적으로 제시함

- (1) **실제 생산 데이터셋 선정**: 사용자 입력/도구 호출/실패 케이스/엣지케이스/성공 경로 등 모든 유형을 엄밀히 포함해야 함
- (2) **평가 지표(Scoring Mechanism) 구축**: 할루시네이션, 정확도, 도구 경로, 효율성, 작업 완료 등 엔지니어와 제품팀이 중시하는 값들을 가시적으로 정의
- LLM(거대언어모델) 활용 ‘LLM as a judge’로 비정형 평가 항목도 0~5점, 0/1 등 정량화 가능(예: LLM에게 Task가 완수됐는지 평가 맡김)
- 코드 기반 평가, ML 기반 평가도 결합 가능
- (3) **베이스라인 실험 실행**: 생산 데이터셋 전체로 실제 에이전트 동작을 실행, 평가 스위트로 점수화
- (4) **정책/모델/프롬프트 등 변경 후 재실험 및 비교**: 모든 중요한 변경사항에 대해 반복적으로 자동 비교
- (5) **CI/CD 자동화 연동**: 예를 들어 GitHub Actions와 연결, PR 생성 시 매번 실험과 평가 자동 수행→ 성능 기준 미달시 merge 차단→ 안정성 확보

### 다양한 평가 지표 및 자동화 방법이 실무에 적용 가능한 형태로 설명됨

- 트레이싱 기반 평가는 Arize UI의 ‘Prompt Playground’(단일 에이전트 실험), ‘Agent Playground’(다중 에이전트/서브에이전트/원격 에이전트 포함)에 적용
- 예시: Prompt Playground에서 각 프롬프트 버전별 불릿 추가, 데이터셋(실제·엣지·실패·성공 모두 포함) 적용, 점수 비교 가능
- 평가 항목: 할루시네이션, 사용자 불만, 보안, 코드 에러, 사용자 정의 항목 등 수십종 제공/커스터마이즈 가능
- 결과 데이터셋에서 개별 기록별로 평가점수, 레이턴시, 비용, 에러율 등 시각화 가능

### UI와 프로그래밍 방식(코드·CLI·CI/CD) 모두 지원되며, 실제 실무 흡수성이 높음

- UI 외에도 SDK, Rest API, CLI 등으로 실험 자동화 가능
- 특히 코딩 에이전트(Agent Skill) 활용시 Arize의 Public Repo를 통해 모든 기능을 IDE와 연동 가능
- 에이전트가 생산·수정한 코드와 실제 운영 환경 트레이스가 연결되어 루프 구조의 개선 프로세스 가능

### 실패 케이스는 곧장 회귀 테스트 데이터로 축적되어 품질을 강화함

- “모든 실패는 테스트가 되어야 한다”는 원칙 하에, 새로 발견된 실패 작업은 자동으로 다음 회귀 데이터셋에 포함
- 이 반복/누적적 루프를 통해 시스템은 점점 더 강해지고 깨지기(a.k.a. break) 힘들어짐

### CI/CD 파이프라인 통합을 통한 ‘공감 기반 shipping’에서 ‘데이터 기반 shipping’으로 전환을 강조

- 기계적으로 코드를 리뷰하고, ‘잘 될 것 같은 기분’(vibes)으로 배포하는 관행이 문제의 핵심으로 지적
- 정량적 평가 및 자동 회귀 테스트를 CI/CD에 완전히 녹여 안정성을 비약적으로 높일 수 있음을 반복 강조

### 최종적으로 인간 엔지니어가 아닌 에이전트 스스로가 관찰·수정·개선을 담당해야 한다는 새로운 패러다임을 제시함

- 현재는 인간이 대시보드 모니터링, PR 리뷰, triage 등 병목(수동 조사/대응) 역할을 하고 있음
- 궁극적으로는 에이전트가 자기 관찰, 자기 진단, 자기 패치(자체 PR 생성 등)까지 담당하는 ‘Self-Improving Agent’ 체계로의 전환 필요
- 즉, 관찰성(Observability)은 “인간이 에이전트를 이해”하는 단계를 넘어 “에이전트가 자기 자신을 이해하고 개선”하는 단계로 진화 중임
- 자기 트레이스, 실제 성능, 원인-결과를 직결하여, 에이전트가 ‘실패에서 배우기’→‘자체 고치기’로 이어지는 자율적 개선 구조를 형성함

### Arize 플랫폼이 이러한 체계적 회귀 및 자기개선 루프 실현을 위한 실제 도구임을 명확히 데모로 보여줌

- Arize 플랫폼 사례 시연을 통해 에이전트 회귀 실험, 평가, 실패 케이스 관리, 자동화 실험 등이 실제 가능한 경로로 자세히 설명
- 엔지니어/AI 운영팀/에이전트 개발자 모두 즉시 접목 가능함을 실제 UI와 기능 설명으로 연결

### 영상 결론부에서, 최고의 에이전트는 실패에서 배우고 스스로 개선하며 미래 관찰성의 방향이라며 마무리됨

- “가장 뛰어난 에이전트는 실패로부터 배우는 데서 멈추지 않는다. 스스로 고친다”라는 결론으로 미래 지향성을 강조
- 즉, 안정적 성능·자동화·자기개선이 조화되는 완성형 AI 관찰성 체계가 중요함을 다시 상기시킴
