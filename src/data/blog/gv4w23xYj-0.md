## *나만의 AI 평가(Eval) 첫 작성 방법* 핵심 요약

- **SallyAnn DeLucia(Arize AI의 제품 총괄)가 Arize 제품에서 AI 에이전트 평가(evaluation, eval)를 직접 설계하는 실전 과정을 워크숍 중심으로 안내함**
- **AI 평가(Eval)의 명확한 정의와 용도, 그리고 기존 소프트웨어 테스트와의 차이점을 자세하게 설명**
- **Eval의 필요성: 단순한 ‘감(feel) 평가’로는 프롬프트/모델 변화 효과 파악, 회귀(성능 저하) 감지, 공식 품질 기준 정립, 버전 비교 등이 불가능함을 사례와 함께 강조**
- **Eval의 유형 및 활용 가능성: LM as a judge, Decision model, Code eval, Annotation, Agent as a judge 등 다양한 평가 방식과 주요 기능들을 구체적으로 구분해 소개**
- **데모 프로젝트(여행 계획 에이전트) 기반으로 Arize 플랫폼에서 실제 트레이스 데이터 탐색 및 평가 기준 정의 실습 진행**
- **‘좋음’(성공)과 ‘나쁨’(실패) 조건을 구체적인 기준으로 정의하는 방법, 한 번에 한 가지 품질 기준만을 eval에 넣는 것이 효과적임을 강조**
- **Eval 작성 순서: 트레이스 데이터 확인/추출 → 구체적 평가 기준 체계화 → 데이터셋 구성 → 프롬프트 기반 평가 템플릿 작성 및 테스트 → 반복적 개선**
- **플랫폼 기능(트레이스, 데이터셋 필터링, 프롬프트 플레이그라운드, Alex 도우미 등)들을 활용한 실제 적용 예시와 실습 과정 안내**
- **평가 자동화, 온·오프라인 평가, 다양한 이해관계자가 개입하는 ‘정렬(alignment)’ 방식 등 실무 적용 전략과 미래 발전 방향 제언**
- **평가 기준은 작게 시작해 사용 데이터와 경험에 맞춰 계속 발전시키는 것이 중요하며, 아웃 오브 박스 템플릿을 출발점으로 개별화해야 함**

## 세부 요약 - 주제별 정리

### Arize의 AI 평가(Eval)란 소프트웨어 테스트와 다르게 꼭 필요하며 에이전트의 성능 파악에 필수적임

- SallyAnn DeLucia는 Arize에서 실제 AI 평가 도구 개발·운영까지 주도했고, 초기 AI 에이전트 ‘Alex’도 담당함
- 워크숍 목표: (1) Eval의 개념과 비/포함 사항 명확히 이해 (2) 나만의 평가 기준 작성법 습득 (3) 실전 평가(judge) 구축 및 개선 방법 실습
- AI에이전트 환경에서는 입력 대비 출력이 단 하나의 정답이 아니고, 에이전트의 ‘로직’은 코드처럼 명확히 읽을 수 없음
- 트레이스(trace)는 AI의 내부 처리 단계(스텝)별 기록이며, eval은 이런 복잡도를 공식적으로 검증·측정해줌
- 프롬프트 변경, 모델 교체 등 주요 업데이트 후 효과를 단순히 ‘느낌’으로만 판단할 경우, 회귀나 부작용이 있는지 입증 불가능함
- 객관적 평가 없이선 품질 관리를 위한 공식 기준(quality gate)을 CI 프로세스에 삽입할 수도 없음
- 전통적 유닛 테스트는 한 입력에 하나의 정답만을 맞추지만, 에이전트에서는 다양한 출력을 여러 기준으로 평가해야만 함

### 평가(Eval)의 여러 가지 유형들이 서로 다른 목적과 장점으로 활용됨

- **LM as a judge**: LLM(대형언어모델)을 심판/평가자로 삼아, 에이전트의 특정 응답을 등급(라벨) 및 설명과 함께 평가함(QA, 요약, 관련성 등)
- **Decision Model**: 최근 OpenAI 등이 공개한 의사결정 모델 API. 빠르고 저렴하며 일반적으로 ‘맞다/틀리다’ 식 이진 또는 다중 분류로만 결과 반환, 설명 없이도 합목적성 높은 평가 가능
- **Code eval**: 실질적으로 명확한 정답이 존재하는 경우(특정 단어 포함, JSON 형식 여부 등)에 코드로 평가, Rouge나 BLEU 등 공식 평가 모델도 포함
- **Annotation**: ‘골든 데이터셋’ 레이블링, 종종 합성(synthetic) 데이터도 활용
- **Agent as a judge**: 6개월 전부터 등장, 한 분야의 복잡한 성공/실패를 또다른 에이전트가 검증하며, 까다로운 평가 기준에 적합
- **User Feedback & Business Metric**: 실제 사용자 피드백, 비즈니스 지표 등은 실서비스 환경에서 주로 사용되나, 개발 단계에서는 앞선 네가지(중간 네가지) 평가 위주로 활용 권장

### Arize 플랫폼에서 트레이스 데이터 탐색으로 에이전트 동작을 시각적으로 분석할 수 있음

- 데모 프로젝트 ‘여행 계획 에이전트’를 활용하여 실제 사용자 요청 → 에이전트의 답변 전체 과정을 트레이스(단계별, 장소별)로 확인
- 트레이스 구조: ‘root span’(최상위, 입력/최종출력 위치) → 여러 하위 span(작업 단위) 연결, 각 스팬(스텝)별로 agent, tool 등 역할과 입출력 따로 존재
- 실제 예시: 사용자 요청(프라하 3일, 800달러, 로컬한 경험 등), 각 일자별 일정 제안 상세 답변 → 입력, 출력, 툴 호출 이력 등을 트리 형태로 확인 가능
- 여러 유형의 agent, 도구, LLM 호출 결과를 펼쳐가며 각각 데이터와 변환 과정을 점검

### 트레이스의 개별 스팬(작업 단계) 구조를 분석해 정밀한 평가 지점과 방법을 식별할 수 있음

- Root span과 하위 스팬(Research agent, Tool call, LLM call 등)의 연쇄 작용이 어떻게 최종 응답을 생성하는지 실시간으로 디버깅
- LLM 호출이 두 번 일어나는 사례: 1차 LLM이 사용할 툴을 결정, 2차 LLM이 툴에서 얻은 정보를 요약/최종 출력 생성
- Arize 플랫폼은 다양한 멀티에이전트 구조·프레임워크 환경에 유연하게 연동 가능하도록 설계(프레임워크 agnostic, 다양한 오픈 소스 tracing 지원)
- 트레이스 탐색 과정이 실제 평가 지점(성공/실패 판정 위치) 선정의 기초가 됨

### 평가 기준 정의 시 성공/실패를 구체적이고 명확한 항목별로 구분해 작성해야 함

- “도움 됨, 정확함” 등 모호한 기준 대신, 입력 정보와 요청에 맞는 구체 기준(예: 사용자의 follow-up 반영, 요청 여행 일수·예산 엄수 등)으로 ‘무엇이 좋음(good)인가’부터 명시
- 평가 항목은 가능하면 한 번에 한 가지 품질(quality)만 다루는 것이 좋음(LM as a judge의 경우 가장 적합)
- 반복적으로 새 기준을 추가하며 eval 체계를 점진적으로 발전시켜야 함
- 대표적 예시: Alex 에이전트에 처음 3종 QA·정확도·유저 불만·jailbreak·toxicity 등으로 시작해 최근엔 32개 기준까지 확대
- 아웃 오브 박스 템플릿(QA, 헛소리 hallucination, session coherence 등)은 활용 가능한 출발점이지만, 결국 각 사례별 맞춤화 필수

### 효과적인 평가 기준 항목 작성을 위해 6개 구성요소로 체계화하는 것이 실습의 핵심임

- 평가할 테스크(목표), 성공 정의, 실패 정의, 판별 대상, 성공 세부 조건(패스 불릿), 실패 세부 조건(페일 불릿)으로 구성
- 예시: “사용자가 여행 추가 요청 시, 답변에 여행 정보를 구체적으로 반영해주면 성공, 예산만 제시하는 등 일반화된 답일 경우 실패”
- 불릿 개요로 만드는 것이 추후 LLM 프롬프트(평가 프롬프트)화에 용이하고, 명확성·일관성 유지에 효과적
- 동료/이해관계자가 명확히 이해할 수 있을 만큼 수치, 예시 등 포괄적·구체적으로 작성 권장

### Arize에서 실제로 평가 데이터셋을 선정, 구축, 필터링하는 방법이 상세하게 안내됨

- 평가하고자 하는 트레이스를 span 단위로 구체적으로 선별(루트 스팬, 특정 툴 호출 스팬 등)
- 강력한 필터링(예: parent_id=null, 툴 명으로 검색)으로 필요한 데이터셋 대상 추출
- ‘데이터셋으로 저장’ 기능 활용해 평가 대상 구성

### 프롬프트 플레이그라운드에서 평가 프롬프트 작성, 테스트, 반복 개선 프로세스를 실습함

- 프롬프트 플레이그라운드에서는 평가 프롬프트 템플릿을 입력, 미리보기/테스트 가능
- 템플릿 작성 시: LLM의 역할(심판임을 명시), 입력 정보 요약, 구체적 pass/fail 조건 명시, 변수 매핑에 유연성 부여(서로 다른 데이터셋/트레이스 호환)
- 개별 라벨(정답/오답/부분정답 등)과 “Not applicable”, 최적화 방향 등도 자유롭게 설정 가능
- 실제 입력-출력 데이터셋을 연결해 평가 반복 실행, 결과를 토대로 프롬프트 내용 계속 조정·개선
- 최종 평가 템플릿은 플랫폼 내 여러 프로젝트, 에이전트에 공유·재사용 가능

### Arize의 자동화 도구(Alex 등)를 활용하면 평가 기준 생성-적용-개선이 한층 더 효율적으로 가능함

- Alex는 평가 기준 자동 생성, 평가 실행, 결과 피드백·프롬프트 업데이트까지 반복 자동화
- 신호(signal) 등 관리형 에이전트가 트레이스를 분석하여 이슈 감지, 효과적인 에이전트 개선 지원
- Annotation(샘플 추가 주석), 온라인 평가(실시간 트레이스 자동 평가), 오프라인 평가 등 고도화된 자동화 루프 가능

### 실무에는 다양한 관계자가 참여해 성공 기준을 합의하고, 평가와 메트릭은 함께 병행해야 함

- 평가 결과는 제품, 엔지니어, 전문가, 보안 등 다양한 스테이크홀더의 목적/관점 반영이 핵심
- 메트릭(숫자 지표)은 ‘문제가 있음’을 알려주고, 평가(evals)는 ‘실패 이유/종류’를 명확히 추적해줌
- 의사결정 모델(judge)와 LM as a judge 간 성능/설명력 비교 경험도 추천
- 실제 적용 시 초기엔 20개 이내 트레이스, 한 차원(one dimension), 하나의 심판(judge)을 운영하며 점진 확대가 효율적임

### 평가 시스템은 작은 단위부터 시작해 경험과 데이터에 기반해 지속적으로 확장 및 고도화해야 함

- 아웃 오브 박스 템플릿으로 빠르게 착수 → 사례별 맞춤화, 실제 사용자 데이터 반영 → 필요에 따라 새로운 기준과 자동화 기능 추가
- 다양한 타입의 judge(의사결정 & LM as a judge 등)를 비교·병행해 성능 및 효율성 검증
- Arize에서 제공하는 문서, 벤치마킹 자료 등 참고하며 평가 체계를 내재화할 것 강조

### 발표 마무리 및 추가 자원/실습 연결 안내

- Arize 부스, 심층 문서, Playground, judge docs 등 추가 학습·체험 자원 안내
- 남은 시간 질의 응답 및 심화 상담 가능 안내
