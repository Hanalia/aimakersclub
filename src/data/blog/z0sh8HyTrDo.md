## *여러분의 금융 에이전트 병목은 바로 여러분입니다* 핵심 요약

- 영상 제목은 "*여러분의 금융 에이전트 병목은 바로 여러분입니다*". 발표자인 Siddhant Imani(Auditoria AI 데이터 사이언티스트)가 AI 기반 금융 생산(Production) 에이전트 개발 시 병목 현상의 본질과 해결 방안을 소개
- AI 데모는 쉽게 만들 수 있지만, 실제 프로덕션(운영 환경) 전환 시 예기치 않은 버그와 문제 발생 빈도가 높음
- 주된 병목 원인은 모델, GPU, 프레임워크가 아니라 **개발자 자신(사람 중심의 작업 루프 속도)**에 있음
- 신속한 "개발자 루프 자동화"가 프로덕션 버그를 해결하는 핵심이며, 이를 위해 4가지 프리미티브(기본 요소) ― **서브에이전트, 워크트리, 스킬셋, 최소한의 UX**가 강조됨
- **서브에이전트**로 병렬 작업 가능: 한 대의 맥북(48GB RAM)에서도 50개의 워크트리, 50개 독립 작업 가능
- 각 워크트리에 QA가 발견한 각각의 Jira 티켓 등 별개의 이슈를 독립적으로 부여, 사람이 직접 하지 않아도 프로덕션 문제 수정을 단계별로 자동화
- "사람의 개입"은 문제 정의(시작)와 결과 검증(마무리) 2단계에만 꼭 필요, 중간 단계는 거의 모두 에이전트가 처리 가능함
- **최소한의 UX**(하나의 위젯/대시보드)를 통해 여러 작업과 모니터링을 통합, 개발자의 반복적·기계적 UI 전환 필요성을 최소화
- 금융 분야 특성상 에이전트-에이전트 작업에 대한 책임 소재 등 규제와 인증(SoX 등) 이슈가 존재하며, 사람의 주의력이 최종 병목
- **목표-루프-자동화**를 결합해 점진적으로 사람(개발자) 개입 없이도 시스템이 자기 개선을 반복하며 문제 해결을 고도화할 수 있다고 주장

## 세부 요약 - 주제별 정리

### 프로덕션 에이전트 개발의 병목은 “사람의 반복 작업 속도”에 집중되어 있음

- AI 데모는 간편하게 만들고 시연할 수 있지만, 실제 운영 환경에 배포할 때 다수의 예기치 않은 오류와 버그가 빈번하게 발생함
- 흔히 “모델이 부족하다”, “더 빠른 GPU가 필요하다”, “좋은 프레임워크가 답이다”라고 생각하나, 실상은 개발자가 직접 반복 처리하는 개발 루프 자체가 근본 병목임
- 3~4개월 주기로 새 모델(Fable 5 등)이 출시되고, 1년이면 새로운 GPU/칩셋이 나오는 환경에서는 코드, 프레임워크, 모델의 교체가 매우 쉬움
- 따라서 문제 해결의 본질은 개발자(또는 운영 담당자)가 얼마나 빠르고 자동화된 루프를 구축하느냐에 달려있음

### 병렬 처리를 극대화하는 서브에이전트와 워크트리 활용 전략

- 현재의 도구(harness)에서는 쉽게 여러 서브에이전트를 생성할 수 있음
- “워크트리”(work trees)는 각 서브에이전트가 격리된 폴더/환경에서 독립적으로 코드를 생성, 버그 수정, 로그 분석 등을 하도록 돕는 구조
- 예시: 48GB 램의 Macbook에서 최대 50개의 워크트리 및 50개 작업을 동시 처리 가능
- 각 QA 버그 티켓(Jira 등)을 별도 워크트리로 배정, 에이전트는 각 워크트리별로 서브에이전트까지 추가 파생시켜 문제에 집중

### 조직만의 “스킬셋” 축적과 자동화가 추구할 핵심 역량임

- “스킬”(skills)은 조직 고유의 생산성 레시피, 작업 방식, 노하우가 코드화된 자동화 모듈
- 다양한 스킬을 에이전트에 지속적으로 탑재할수록 에이전트는 규정된 방식에 따라 문제를 정확하게 처리함
- 예: 고유의 TDD 프로세스, log/traces 수집법, 요구사항 분석 등 스킬을 모듈화해서 에이전트 능력을 강화 가능

### 전체 프로덕션 문제해결 과정을 단계별로 에이전트가 자동화할 수 있음

- QA가 버그 티켓을 등록하면, 에이전트가 요구사항 분석, 원인 분석, 시스템 로그 수집, 테스트 코드 및 수정 코드 작성, 로컬 및 종단(end-to-end) 테스트 진행
- 이후 PR(Pull Request) 생성·제출, 팀 코드 리뷰 거친 뒤 master 브랜치 병합 및 도커 이미지 제작, 개발/스테이지 환경 배포·테스트, QA 팀 피드백까지 자동화 루프 지원
- 9단계 중 1번(문제 정의)과 9번(결과 검증)에서만 “사람”의 개입 꼭 필요. 그외 전 과정은 에이전트 자동화가 효율성/정확성에서 우위

### 최소한의 UX가 생산성, 피로도, 작업 속도에 결정적임

- 대시보드(프로덕션 에이전트 위젯) 하나에 Kubernetes 서비스, 시스템 로그, Jira 티켓, GitHub PR 등 모든 작업 정보 통합 표시
- 예시 이미지: macOS 위젯 하나로 서비스 전체 모니터링이 가능, 여러 창 전환/모니터 이동/목 돌림 등 개발자의 번거로움을 획기적으로 줄임
- 그래프 수치로 볼 때 작업 변경 한 번당 목 돌림 횟수 역시 현저히 감소

### 금융 분야에서 서브에이전트 오케스트레이션은 책임성과 규제가 병목을 불러옴

- 금융·회계 산업은 코드 리뷰, 내부통제(SoX 등) 등 강한 규제가 적용되며, 질문: 에이전트간 자동화 루프에서 문제가 발생하면 “책임”은 인간에게 귀속됨
- AI/에이전트들이 실시간 버그를 수정하더라도 “인간 주의력/검토”와 “최종 서명”이 필요한 경우가 많음
- 에이전트 오케스트레이션 과정에서 실제 병목은 “사람이 여러 작업을 병렬로 주시·조정해야 하는 주의력의 한계”임

### 자기 개선 루프와 목표 기반 운영으로 개발자 개입을 점점 줄일 수 있음

- 최신 모델(예: Fable 5, Mythos 5, GPT 5.6 등)은 에이전트가 자기 루프의 병목을 스스로 진단, 개선하는 “재귀적 자기 개선” 가능성을 보여줌
- 반복 작업(하루 5~6 티켓 등) 후 에이전트가 병목 리스트를 생성, 매 루프마다 해당 병목을 제거하는 작업을 실행
- 한 달 반복할 경우, “문제 지시 -> 자체 로그/트레이스/티켓 수집 -> 자동 코드 작성/테스트/배포 -> QA 이동”까지 사람 개입 거의 없는 루프 완성 가능

### 목표(Goals)와 루프(Loops) 결합으로 에이전트의 자율성을 높임

- 사용자는 에이전트에 “목표”만 설정(예: 리포트 데이터 불일치 해결)하고, 내부 루프는 자율적으로 문제 해결 접근
- 모바일 등 원격 환경에서도 상황 파악 및 목표 설정 간단히 가능
- 반복적 패턴(같은 문제 반복 등)이 나올 때 “에이전트 드리밍” 기능으로 배경에서 고객 세션 데이터 집약, 패턴 개선, 시스템 전반 업그레이드로 확장

### 반복/병렬/자동화의 4대 프리미티브 조합이 새로운 개발 생산성 패러다임 제시

- 서브에이전트(병렬 작업), 워크트리(격리 구조), 스킬셋(지식 전수), 최소 UX(효율 인터페이스) 4가지가 결합된 도구/시스템이 필수적임을 제안
- 제3자 시스템(로그 서버, 인증 게이트웨이 등)이 복수일지라도 하나의 패널에서 통합 운영 가능
- 개발자는 검증자·감독자 역할로 전환하며, 반복 작업은 에이전트에게 넘겨야 병목 해소 및 10배 생산성 향상이 가능
- 핵심 메시지: “사람”이 더 이상 생산성의 상한선(ceiling)이 되지 않도록, 개발 루프의 자동화와 사람이 ‘감독자’로 전환하는 체계가 앞으로의 방향임
