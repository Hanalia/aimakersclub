## *11가지 추가 코딩 에이전트 문제와 어이없을 정도로 효과적인 빠른 해결법* 핵심 요약

- 영상은 코딩 에이전트를 사용할 때 자주 마주치는 11가지 문제점과 각 문제에 대한 간단하지만 효과적인 해결책을 다룸
- 각 문제에 대해 문제의 원인, 구체적인 현상, 간단한 해결법(Tip), 그리고 자신의 AI 레이어(skills, rules, hooks)에 실제 적용하는 방법을 설명
- "악마의 변호인" 역할을 하는 리뷰어 에이전트 추가, 실질적인 테스트 증거 내놓기, 실제 사용자 행동 기반 테스트 등 구체적인 예시와 기능 권장
- 룰(rule)이 잘 지켜지지 않을 때에는 필수 규칙을 "훅(hook)"으로 전환하여 코드레벨로 강제하는 방법을 강조
- 에이전트 규칙 파일이 비대해지면 성능 저하가 발생하므로, "블레이드(Blade) AI 레이어" 스킬로 불필요한 룰을 주기적으로 가지치기할 것을 권장
- 대화가 길어질수록 컨텍스트 로스(문맥 부패)로 인해 에이전트의 작업 품질이 떨어지므로, 주기적 세션 재시작 및 작업 이양(handoff) 문서 활용
- 프롬프트에 대한 에이전트의 과도한 대작업(큰 수정, 리팩터)은 명확히 간결함과 범위를 명시하여 방지할 수 있음을 구체적으로 안내
- 서브에이전트(sub-agent)와 대용량 LLM 활용 등으로 과도한 토큰 소모 및 비용 폭증을 막기 위한 구체적 제한 규칙 관리 방안 제시
- 테스트 범위(블라스트 레이디우스) 자동 추론 및 단계적 검증 계획을 통해 쓸데없는 광범위 테스트와 리소스 낭비를 최소화하는 스킬 개선법 안내
- 산만하게 업무가 분산(탠전트)될 때 이를 이슈로 따로 기록하고, 본래 작업에는 집중을 유도하는 파일링 및 규칙화 전략 제공
- Arcade(아케이드)와 같은 에이전트 런타임 플랫폼 활용 사례와 그 장점(자동 인증, 감사, 보안 등)도 실제 예시로 제시
- 각 솔루션은 "문제 설명 → 제안 → 에이전트와 대화 후 AI 레이어 커스터마이즈" 라는 동일한 구조로 반복 적용 가능

## 세부 요약 - 주제별 정리

### 코딩 에이전트가 '작업 완료'를 잘못 선언할 때, 리뷰어 스킬로 검증 절차를 강화함

- 대부분의 코딩 에이전트는 예상보다 일찍, 혹은 불완전한 상태로 '작업 완료'를 선언함
- 이런 문제 상황에서는 대화 내에서 에이전트에게 "이 코드가 실제로 동작하지 않을 수 있는 이유는? 내가 요청한 것과 실제 구현의 차이점은?" 등 악마의 변호인 질문을 반복할 것을 권장
- 에이전트는 요청이 있을 때 상당히 많은 검증 리스트를 제시할 수 있으며, 실무에서 바로 보완 가능한 구체적 포인트를 발견하기 쉽다는 장점
- 이를 형식화하기 위해, 별도의 리뷰어 스킬(즉, 별도 에이전트)을 만들어 신선한 시각으로 코드를 검토하도록 하는 방법 추천
- 대부분의 인기 에이전트 프레임워크는 이런 리뷰 프로세스를 내장하고 있지만, 프로젝트에 맞는 커스텀이 중요하다고 반복적으로 강조
- 실제 예시: 코딩 에이전트에게 해당 문제를 설명하고 리뷰어 에이전트 생성 및 적용을 요청하니, 즉시 관련 기능을 구축함
- 결론: 거의 모든 문제 해결의 90%는 "문제 설명 → 제안 → AI 레이어 조정"의 대화로 신속히 개선 가능

### 테스트 증거 부족 문제는 구체적 산출물을 명시적으로 제시하도록 요구하여 해결함

- 코딩 에이전트가 “테스트 완료”만 선언하고 실제 테스트 데이터를 제공하지 않으면 신뢰도와 업무 효율이 크게 저하됨
- 단순히 ‘모든 유닛테스트 성공’이라는 요약이 아니라, 실제 명령어 입력, 출력 스크린샷(예: agent browser CLI 통한 기능 작동 스크린샷)을 첨부하도록 제안
- 이러한 테스트 증거를 pull request body나 보고서에 포함시키면, 사람이 검토하고 신뢰하는 데 큰 도움이 됨
- 개선 방안: 규칙(rule)이나 별도 스킬에 '모든 작업 완료 보고에는 테스트 산출물이 반드시 포함돼야 함'을 명시
- 또는 ‘플래닝 스킬(planning skill)’ 내에 테스트 산출물을 사전에 정의하게 하여, 이후 실제 코딩 구조에도 자동 반영
- 실제 구현 예: 에이전트와 대화하여 새 스킬을 만들거나 기존 규칙 수정/강화

### 에이전트 테스트가 통과하지만 실제 앱이 작동하지 않을 때, 사용자 동작 기반 테스트를 추가함

- 흔히 겪는 문제 : 코딩 에이전트가 통과시킨 테스트 코드만 올리고, 실제 앱은 깨짐
- 원인 : 유닛테스트 등 코드 레벨 검증에만 치중하고, 실제 ‘사용자 입장에서’ 앱을 검증하지 않기 때문
- 해결 방법: 브라우저 자동화 툴(agent browser CLI 등) 활용해 UI 버튼 클릭, 인풋 입력 등 실제 사용자의 여정 시나리오로 테스트 강제
- 플래닝 스킬에 ‘사용자 검증 플래닝’을 추가하거나, 별도의 "try-after-change" 스킬을 생성해 UI 변경 후 실제 앱 동작 여부 검증
- 다른 관점의 예시 : 전반적인 플래닝 스킬을 업그레이드하거나, 별도의 검증 스킬(try 스킬)을 만들어 사용자 동작 기반 테스트 실행

### 코딩 에이전트가 규칙을 무시할 때, 필수사항은 반드시 '훅(Hook)'으로 강제함

- 규칙(rule)이 자연어 지시만으론 자주 무시될 수 있음 (예: ".env 파일 읽지 말라"는 룰)
- 훅(hook)은 코드로 직접 특정 상황에 강제 실행되는 보안-컨벤션 로직 (실행 도구 호출 전, 채팅 세션 시작 시 등)
- 훅 예시: .env 파일 접근 시도 차단, 특정 폴더 내 마이그레이션 금지, 특정 명령어만 사용 제한 등
- '항상/절대' 등 강제성 요구사항은 모두 훅으로 이관하는 것이 가장 강력하며, 자연어 룰은 권장/가이드 수준만 남기는 구조 권장
- 에이전트에게 전체 룰 파일을 검토케 하여, 훅으로 변환이 필요한 부분을 자동 감지하고 커스텀 훅 구현 지원

### 규칙 파일이 비대해지면 효율적 유지관리를 위한 'Blade AI 레이어' 스킬을 적극 활용해야 성능 저하를 막을 수 있음

- 손쉽게 추가한 룰(rule)이 시간이 지나면 굉장히 방대해져, 에이전트의 맥락 이해 효율을 떨어뜨림 (토큰 낭비, 참조 오류 빈발)
- 최신 LLM은 문맥이 작아질수록 더 신뢰성 있는 추론을 제공하므로, 비효율적/중복적 룰을 주기적으로 제거(blading)해야 함
- Blade AI 레이어 스킬 사용 예시: 전역 룰 파일 내 유지할 것/삭제할 것/훅으로 이관할 것 자동 제안 → 직접 기능 테스트 후 성능 비교 검증
- 에이전트-사용자 대화 기반으로 완성되는 가지치기 프로세스 안내

### 대화가 길어질수록 에이전트 품질이 급격히 떨어지므로, '핸드오프' 문서로 세션을 나누는 것이 효과적임

- 대화 세션이 진행될수록 컨텍스트 로스(context rot) 발생, 에이전트가 중요 정보 망각 및 반복 실수
- 롱런 세션 내에서 연쇄 오류가 새 세션에서도 반복될 수 있음 (예측 기계로서 LLM 특성)
- 해결책: 각 작업을 짧고 단일 목적의 세션으로 유지, 긴 세션엔 markdown 기반 'handoff.md' 문서를 작성케 하여, 다음 세션에서 간결하게 이어받을 수 있게 함
- 실제 예시: cloud code 활용 시 “write a handoff to handoff.md” 등 프롬프트로 요약-이양 문서 생성, 후속 작업에 활용

### 개발자 주도권 상실(에이전트가 결정권을 가져감) 문제는 플래닝 스킬의 결정보조/위임 범위를 커스터마이즈하여 해결함

- 에이전트 진화로 인해 자동결정 많아졌으나, 고레벨 설계·제품 방향 등은 여전히 인간의 결정이 중요
- 플래닝 스킬(Plan Skill)에서 “에이전트가 자체적 결정, 반드시 사용자 재확인 필요, 우선질문·의사결정 등” 세부 목록을 분류해 명확히 달리해야 함
- 자신이 대답하길 원하는 항목(예: UI 디자인, 특정 제품 행위)은 반드시 확인 목록에 추가
- 실제 예시: 플랜 생성 시, “이 사항은 내가 결정, 이 사항은 질문 필요”를 명확히 문서화하여 검토 기회 부여

### 작은 요청도 불필요하게 대규모 작업으로 확장할 때는, 간결성·범위를 명확히 정의하는 규칙 추가로 방지해야 함

- LLM 계열 에이전트는 기본적으로 매우 장황한 답, 쓸데없이 확장하는 경향 있음
- 작은 버그픽스 요청에도 코드 전체 리팩터, 새로운 추상화, 추가 파일 생성 등 과도한 작업 경향
- 규칙이나 스킬, 글로벌 룰에 “간결하게 구현”, “요구한 부분 외 확대 금지”, “작은 요청은 꼭 작은 변경으로” 등 명확히 예시와 함께 기재
- 자신이 생각하는 ‘간결하고 집중된 구현’이 구체적으로 무엇인지, 코드베이스별로 에이전트에 입력해 커스터마이즈

### 서브에이전트·에이전트 팀 난발로 토큰 비용이 급등할 때는, 명확한 사용 조건을 규칙으로 제한함

- CloudCode나 Codex 등은 디폴트로 수많은 서브에이전트(도우미 에이전트)를 자동 인스턴스화 → 토큰 과다 소모
- 특히 백엔드/프론트엔드/웹리서치 등별로 각각의 서브에이전트 자동 생성 시, 수십만~수백만 토큰 단위까지 비용이 폭증
- 대책: “서브에이전트는 내가 지정한 경우에만 생성”, “서브에이전트 생성 수량/용도 제한”, “주요 업무별 소형 LLM만 사용” 등 규칙화
- 전체 토큰 사용량 모니터링 및 직접 커스터마이즈 가능하니, 정기적으로 점검해야 함

### 에이전트가 과도하게 깊고 많은 테스트를 할 때는, 변경 영향도(블라스트 레이디우스) 자동 추론으로 최적화함

- LLM은 변경 범위에 대한 감을 잘 못 파악해, 사소한 변경에도 모든 테스트를 실행하려 들음 (시간과 비용 낭비)
- 플래닝 스킬에 “변경된 코드 영향도 자동 분석” 단계와, “변경 영향도에 따라 검증 수준 설정” 절차를 추가
- 이를 통해 소규모 변경은 라이트 검증, 대규모 변경은 심층 검증 등 합리적 리소스 관리 가능
- 3번(유효성 검증 수준 결정)과 연계해 어떤 테스트를 어디까지 할지 사전에 계획하여 실행

### 에이전트가 산만하게 관련 없는 문제까지 손대려 할 때는, 그 이슈만 따로 기록케 하여 주요 목표에만 집중함

- 대규모 코드베이스 작업 시, 에이전트가 새로 발견하는 문제마다 엉뚱한 작업으로 분기(탠전트)함
- 해결책: 규칙에 “탠전트 발생 시 별도 마크다운이나 github issue로만 기록, 본래 목표 작업에만 집중”을 명시
- 단, 에이전트에게 매번 탠전트 탐색 요청 시 오히려 업무 과부하(불필요한 이슈 폭증)가 발생하므로, 발견 시에만 기록만 하도록 제한

### Arcade 등 에이전트 런타임 활용 시 인증 관리, 작업 추적, 자동화 등 시간 절감의 실제 사례를 공유함

- Arcade(MCP 런타임)는 각 서비스별 1회 인증(sign-in)만으로 모든 에이전트 환경에서 자동 인증/토큰 관리 가능
- API 키/게이트웨이 설정 불필요, OAuth 등 사용자의 권한 회수 시 즉시 작업 차단 등 보안을 강화함
- 실제 예시: ‘두 번째 두뇌’ 에이전트가 한 주 전체를 계획하도록 오버나이트 장기 작업 실행 → 모든 툴 호출 내역, 성공/실패/차단 사유 등 완전 감사 지원
- Arcade는 시작이 무료이며, 영상 설명란에 링크를 안내
