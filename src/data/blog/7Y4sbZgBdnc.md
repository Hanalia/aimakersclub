## *더 똑똑해진 모델이 Agent Harness를 사라지게 만들었다. 그 이후 남은 것은 무엇인가* 핵심 요약

- 영상은 2023~2025년 사이 AI 에이전트 개발 현장에서 'agent harness(에이전트 하니스)' 개념의 변화와 현재의 역할을 심도 있게 설명함
- 초기에는 프롬프트 엔지니어에서 컨텍스트 엔지니어, 그리고 하니스 엔지니어로 직무가 진화했으며, 하니스는 모델의 "눈과 손" 역할을 하면서 외부 서비스와 연결해주는 중간 계층임
- 하니스 구조는 러ntime, 컨텍스트·오케스트레이션 계층으로 나뉘며, 런타임은 기본 인프라, 컨텍스트·오케스트레이션은 동작 맥락 제어와 다양한 트릭 적용을 담당
- 그라인드스웜(Grind Swarm) 등 고도화된 하니스는 유용했으나, 최신 스마트 모델들은 하니스 없이도 동일한 수준의 작업을 수행할 수 있게 되어 "하니스는 죽었다"는 주장이 나타남
- UC버클리, Apple/EPFL의 연구는 고성능 코딩 모델이 어떤 하니스와 조합해도 SweetBench light, MLEBench 등의 성능 평가에서 유의미한 차이가 없음을 입증
- "데이터 플라이휠" 효과: 하니스가 더 어려운 코딩 태스크를 가능하게 만들면, 데이터가 쌓이고, 결국 모델이 네이티브하게 그 역량을 습득해 하니스의 역할이 소멸함
- 그러나 하니스는 새로운 태스크의 프런티어를 열고, 모델이 흡수하지 못하는 인프라·신뢰성·보안·비용 효율성 영역에서는 여전히 필수적 역할을 수행함
- 제품 그록봇(GrokBot), 소프트웨어 팩토리 등은 여러 에이전트 조합, 롱런 타임/워크플로, 통합 이벤트 구독 등 차세대 하니스의 모습을 보여주며, 하니스의 진화가 계속됨을 강조
- 앞으로 하니스는 더 높은 추상화, 프리미티브 설계, 클라우드 기반으로 발전하며, 전체 에이전트 작업의 90%가 랩탑을 벗어나 실행될 것이라고 전망
- 최종 결론: 코딩 지능 보정이라는 과거 하니스 역할은 사라졌지만, 새로운 프런티어 개척과 인프라/신뢰/효율성 지원이라는 하니스의 진보적 역할은 계속됨

## 세부 요약 - 주제별 정리

### 프롬프트 엔지니어에서 하니스 엔지니어로 직무 트렌드가 변화함

- 2023년에는 ‘프롬프트 엔지니어’가 AI 현업에서 가장 각광받는 타이틀이었음
- 2025년쯤에는 ‘컨텍스트 엔지니어’ 개념으로 진화, 프로그램적으로 모델에 최적 맥락을 제공하는 직무 탄생
- 2024~2025년 경, ‘에이전트 하니스’, ‘하니스 엔지니어링’이라는 용어로 통합됨
- 하니스 개발팀(Curator, SpaceX)은 이러한 트렌드 변화의 중심에서 활동함

### 에이전트 하니스 구조는 런타임(기반)과 오케스트레이션(동작 제어) 계층으로 구분됨

- 하니스는 모델을 둘러싸고 세상과 연결하는 중간 프레임워크로 비유
- 사용자는 앱을 통해 하니스와 연결, 하니스는 다시 모델과 외부 컴퓨터·서비스 (예: MCP) 연결
- 런타임 계층: 에이전트 메인루프 실행과 상태 저장 등 기본 인프라 제공 (전통적 SW 엔지니어링과 유사)
- 컨텍스트/오케스트레이션 계층: 어떤 모델을 언제 호출할지, 어떤 맥락·프롬프트·도구·메모리 압축 등을 적용할지 “야생의 서부”처럼 복잡하게 제어
- 발표자는 주요 업무가 컨텍스트와 오케스트레이션 영역임을 명시

### 그라인드스웜(Grind Swarm) 등 고도화된 하니스는 짧은 시간 내 빠르게 등장·사라짐

- 2024년 말~2025년 초 Cursor팀은 Grind Swarm이라는 멀티모달, 롱런닝 하니스를 개발·발표
- Grind Swarm은 다양한 에이전트와 머신을 오케스트레이션, 자체 브라우저까지 내장한 시스템이었음
- 실제 데모 실행 과정에서 하니스의 리소스 소모·불안정 등으로 Cursor 서비스 자체가 멈춘 사례도 발생
- 에이전트 생태계 특성상, 최첨단 하니스도 몇 달 만에 “하니스는 죽었다”는 담론으로 전환됨

### 최신 연구 결과 하니스 유형은 더 이상 코딩 모델의 성능 향상에 결정적이지 않음

- UC버클리 연구팀은 여러 프론티어 모델(Pi, Codex, Claude Code 등)과 다양한 하니스 조합으로 실험
- SweetBench light 벤치마크 결과, 최신 고성능 모델에서는 하니스 종류와 무관하게 성능이 비슷함을 확인
- Apple과 EPFL 연구진도 MLEBench에서 별도 “MLE 하니스” 도입이 유의미한 성능 향상에 기여하지 않음을 입증
- “단순한 하니스만으로도 최신 모델은 복잡한 코드 작업을 해결할 수 있다”는 결론 도출

### 과거 하니스가 담당하던 코딩 지능 보완 기능은 더 이상 필요하지 않음

- 기존에는 코드베이스 탐색법, 지속적 작업(슬래시 골), 코드 수정 전용 미니 모델 등 하니스를 통해 “모델의 부족한 점”을 보완
- 이제는 모델이 이런 작업 자체를 네이티브하게 수행, 추가 하니스 트릭이나 룰이 의미를 잃음
- 구체적 사례: 코드 작업 흐름 안내, 작업 검증, 파일별 수정 지시 등 추가 프롬프트/가이드 제거

### “데이터 플라이휠” 효과로 하니스가 자신의 존재 이유를 소멸시킴

- 하니스가 어려운 코딩 태스크를 가능하게 만들면, 더 많은 사용자가 실제 작업을 시도해 코드 데이터가 급격히 축적
- 이런 데이터가 오픈AI 등 랩에 입력되어 모델이 궁극적으로 그 태스크 자체를 학습해버림
- ‘하니스→데이터 증가→모델 개선→하니스 필요성 감소’의 자기소멸적 고리 형성
- 이 때문에 하니스가 “죽었다”는 주장(Anthropic의 Tariq, YC의 Garry Tan 등 현업 리더 포함)이 등장함

### 하니스는 여전히 프런티어 태스크 확장과 신뢰성·효율성 확보에 필수임

- 똑똑한 모델 덕분에 단순 코드 작업에서는 하니스가 불필요해졌지만, 새로운 업무 영역 진출에는 반드시 필요
- 예시: 그록봇(GrokBot)은 단일 채팅이 아닌, 롱러닝 코디네이터 에이전트가 여러 작업자 에이전트를 오케스트레이션
- 코딩을 넘어, 여행 예약, 슬라이드 제작, 커뮤니케이션 관리 등 총체적 지식 작업이 신규 미션
- 프롬프트와 가이드, 거드레일, 메모리 설계 등 기존에 뺐던 하니스 기능이 재투입됨
- 이런 신규 프런티어에서 하니스는 본질적인 역할을 다시 차지

### 그록봇(GrokBot) 하니스는 다양한 팀 업무 시나리오를 가능하게 만듦

- 그록봇은 사용자의 ‘자율 동료’로, 단순 코딩 beyond하고 실제 팀내 지식·관리·소통까지 지원
- 새로운 하니스는 단발성 채팅이 아닌, 메신저, 일정, 슬라이드, 여행 등 연속/다양한 워크플로 담당
- 작업 업데이트 방식(과도한 정보 제공 방지), 사용자의 승인 없는 위험 행동(예: 메일 발송) 방지, 사용자별 기억 학습 등이 집중 과제
- 실험 결과, 이런 복합 업무는 오직 하니스의 도움을 통해서만 실현 가능함

### 소프트웨어 팩토리형 하니스 구조가 다수 에이전트의 협업을 오케스트레이션함

- ‘소프트웨어 팩토리’라는 비전: 다수 에이전트가 소프트웨어 개발 전체 라이프사이클을 자동화/협업
- 실제 구현 예: 버그 보고 → 자동 트리아지 → 클라우드 에이전트 버그 수정 → 전후 동영상 자동 기록 → 롤아웃 시나리오 자동 감시 등
- 이 과정을 일종의 ‘메타 하니스’로 설정, 각 업무 단계 별로 에이전트 오케스트레이션이 핵심
- 이로써 단순 모델 성능 향상만으로 대체할 수 없는 업무 확장이 가능해짐

### 최신 하니스는 인프라, 신뢰성, 보안, 비용 효율성 등 모델이 흡수할 수 없는 기능을 담당함

- 자율 동료 수준 에이전트는 minutes→hours→days 이상 장기 실행, 클라우드 기반 런타임 필요
- 단순 하니스에서는 전체 API키 제공 등 보안 위험 존재, 실제 기업 환경에서는 정밀 권한 관리·감사·거드레일 필수
- 하니스 종류에 따라 비용, 속도, 자원 소모가 다름; 캐시 활용, 토큰 효율, 모델 믹싱 등 최적화로 비용 절감 사례 다수
- 실제 그록봇 하니스는 수많은 효율화(캐시 히트율, 토큰 관리, 모델 믹스) 덕분에 동일 품질 기준에서 비용·속도 모두 대폭 개선

### 하니스의 미래: 더 높은 추상화·프리미티브 설계(구성요소화)와 클라우드 중심 실행으로 진입함

- 데이터 플라이휠 가속화로 제품 혁신 속도가 모델 진화 추월, 하니스는 더욱 복잡해질 것(피처 추가/삭제의 유연성 필요)
- 하니스의 세부 동작(Inner workings)은 점점 사용자에게 비공개화되어, 변화 관리 부담을 줄이고 배포 속도를 높임
- 핵심 빌딩 블록(프리미티브) 설계를 통해 복잡화 방지 및 유연성 확보 예시: 슬랙 이벤트, CI·타임 트리거에 대응하는 “구독(subscription)” 프리미티브 도입
- 미봉책적 거드레일(Shim)은 중앙관리, 더 이상 필요 없는 경우 시스템이 자동 PR 생성해 코드 간소화 진행
- LLM 단일콜 조합이었던 과거에서, 이제는 에이전트를 조합하는 구조로 추상화 수준 업그레이드
- 향후 6개월 내 전체 에이전트작업의 90% 이상이 노트북이 아닌 클라우드에서 실행될 것으로 전망

### 결론: 하니스는 죽지 않았으며, 새로운 차원의 역할과 진화가 지속될 것임

- “코딩 작업 보정”만을 위한 하니스 역할은 모델의 발전과 데이터 플라이휠 효과로 사라짐
- 그러나 새로운 애플리케이션 영역, 팀형/복합작업, 인프라·신뢰·보안·효율성 확보 등에서는 하니스가 필수 불가결
- “하니스는 죽었다”가 아니라, “새로운 하니스의 시대가 열리고 있다”는 점을 마지막으로 강조
