## *AI 에이전트를 믿지 마세요. 과학자처럼 테스트하세요* 핵심 요약

- 스테파니 자르막은 Omni Analytics의 AI 엔지니어로, 에이전트 ‘Bloopy’를 활용한 비즈니스 데이터 의미적 거버넌스 플랫폼 개발에 참여 중임
- Sourcegraph에서 Amp 코드 에이전트의 솔루션 엔지니어와 평가 플랫폼을 개발하며 Code Scale Bench라는 공공 벤치마크를 구축한 경험을 보유
- 에이전트 테스트 시 단순 효과성 지표(예: 비용 28% 절감)에 집중하기보다 실제 문제(예: 툴 사용 여부)로 원인을 추적하는 과학적 탐구 접근이 중요함을 강조
- 동일 모델이라도 벤치마크 하네스(실행 환경) 구성 차이로 효과가 최대 30% 이상 다르게 나타남. 실제 운영환경에 맞는 구성이 필수
- 공개 벤치마크는 빠른 모델 후보군 선정용 참조일 뿐, 각 조직의 실제 워크로드에 맞춘 별도 평가 설계가 반드시 요구됨
- 평가 설계 시 업무 범위 커버리지, 작업 유형 분류, 반복성(비결정성), 하네스-모델 상호작용 등 다변량 요소 탐색이 핵심
- 실험 데이터(트레이스, 로그 등) 완전 수집 및 실패·비사용 케이스까지 분석하는 ‘탐정적 추적’ 접근법이 필요함
- 평가지표는 조직별 업무 목적에 맞게 선정해야 하며, 공공 벤치마크 단일 점수(예: F1, precision/recall) 해석에 주의 필요
- 자동화된 품질 게이트, 알람-휴먼 검토 부하 관리 등 실제 신뢰와 안전성 확보 위한 현업 사례와 전략 소개
- 에이전트 트레이스의 신뢰성 한계(특히 보안 이슈) 및 독립적 기록·감사 체계의 필요성 강조
- 실제 운영 환경에서 발생한 데이터와 결과를 최종 신뢰 기준으로 삼아야 하며, 관찰성과 현실 적합성을 최대화하는 평가 설계가 중요함
- 자신이 운영 중인 GitHub 레포와 아카이브를 통해 평가 설계 및 신뢰성 확보 방법 공유

## 세부 요약 - 주제별 정리

### 스테파니 자르막의 역할 변화와 과학적 시각 기반 평가 경험이 영상의 큰 줄기를 이룸

- 스테파니 자르막은 Omni Analytics에서 ‘Bloopy’ 에이전트 활용 비즈니스 데이터 플랫폼을 개발하고 있음
- 이전에는 Sourcegraph에서 코드 에이전트(Amp)의 솔루션 엔지니어 및 평가 시스템 구축 업무를 맡았음
- Code Scale Bench라는 복잡한 코드베이스용 공공 벤치마크를 직접 개발함
- 초기 경력은 천문학자로, 근본적으로 ‘모든 것을 의심’하는 연구적·과학적 자세를 평가에 도입함
- 영상 제목인 ‘Lies, Damned Lies, and Evals’(거짓말, 악질적 거짓말, 그리고 평가)는 AI 에이전트 신뢰의 근본적 경계 지점을 강조함

### 단일 실험에서의 표면적 수치(예: 비용 절감)에 빠지지 말고, 의도한 변화의 실질적 효과에 집중할 필요가 있음

- Sourcegraph에서 코딩 에이전트의 코드 탐색 툴 미사용 문제를 발견하고 실험
- 프롬프트를 변경한 결과 28% 비용 절감이 있었으나, 목표(특정 툴 사용)는 달성되지 않음
- 비용 절감은 흥미로운 현상이지만, 실질적으로 측정·이해해야 할 대상(에이전트 행동 변화)에는 무관함
- 실험 변수(비용 등) 잠재적 원인 분석은 필요하지만, 궁극적으로 ‘툴 미사용’ 현상에 집중하며 원인 추적해야 함

### 벤치마크 하네스(실행 환경) 차이가 모델 효과에 큰 영향을 끼치므로, 실제 업무 환경과 최대한 유사하게 평가해야 함

- Turbo Bench 4와 같은 벤치마크에서, Opus 5와 Astra 모델의 성능을 여러 하네스(Open Hands 등)로 비교함
- 동일 모델이라도 하네스만 변경하면, 성능 차이가 30% 이상 나타남
- 즉, 벤치마크 간 결과 신뢰도만 보지 말고 실제 도입 환경과 유사한 구성을 찾아 테스트해야 함

### 공개 벤치마크는 참고용 ‘쇼트리스트 도구’일 뿐, 자체 워크로드 반영 평가가 진짜 필요한 결정 포인트임

- ‘평가’(evaluation)는 실제 제품·프로세스 변경을 위한 측정과 의사결정 과정임
- 공개 벤치마크는 전체 솔루션 또는 모델 시장의 풍경 파악, 후보군 선별에 도움이 됨
- 하지만 각 조직의 실제 환경과 워크로드가 반영되지 않으면 벤치마크 점수에 과도하게 의존하는 것은 위험
- 예를 들어, 법률 업계라면 코드 에이전트 벤치가 의미없을 수 있음
- 조직 내부에 특화된 자체 벤치마크(내부 평가) 설계가 중요하며, 점진적 개선(‘hill climbing’) 반복 가능

### 평가 항목 선정 시 업무 범위, 작업 유형, 반복실험, 상호작용 변수 등 다각도로 다뤄야 함

- 워크로드 커버리지를 넓게 잡아야 하며, 업무 유형(예: 버그 수정, 코드 이해, QA, 대시보드 구축 등)을 세분화·분류할 수 있음
- 버그 수정만으로는 실제 개발자 워크로드 반영에 한계 → 다양한 소프트웨어 라이프사이클 업무 반영 필요
- 모델의 비결정성 문제(실험마다 결과값 변동)에 따라 여러번 반복실행 권장
- 평가 변수(모델, 하네스, 입력 등) 간 상호작용 영향도 체크 필요
- 다양한 조합 시험을 통해 ‘조합적 효과’ 및 다운스트림 결과에 대한 인과관계를 밝혀야 함

### 실험 추적성(트레이스), 실패 및 미사용 사례, 전체 정보 파이프라인 관리 필요

- 모든 트레이스(로그, 결과 등) 보존이 필수적이며, 문제 발생 시 원인역추적이 쉬워야 함
- 예를 들어, 에이전트가 툴을 안 썼을 때 (1) 툴이 제공되었는지, (2) 콜은 되었는지 등 파이프라인별 논리적 점검 필요
- 최적화 시 의도대로 도구 사용이 늘더라도, 업무 목적 달성이 안 될 수 있음 → 원인 재귀적 분석 반복
- 비사용, 실패 사례, 다운스트림 비효과 등도 모두 인과적 추적의 대상

### 평가지표(F1, precision, recall 등)는 사업 목적에 맞게 설계해야 하며, 단일 수치에 과도히 의존하지 말아야 함

- 예: 검색 도구 평가 시 precision보다 recall(관련 정보 최대한 수집)에 초점을 둘 수도 있음
- 실제로 Claude 기반 검색은 295개 파일을 반환(필요파일은 6개)에 recall은 높지만 precision은 낮음
- 각 조직의 필요(관련 정보 놓치지 않기 vs. 정확한 결과 선호)에 따라 평가 기준이 달라짐
- 공개 벤치마크 결과의 수치를 단순 비교하지 말고, 평가 지표 선택 이유와 실제 필요에 맞춰 해석 필요

### 자동화 게이트, 알람 및 휴먼 검토 부하 관리는 신뢰 및 안전성 확보의 핵심임

- 본인의 소프트웨어 파이프라인에서 ‘자동화 승인 큐’와 규칙 기반 감시 추가 실험 진행 중
- 시스템이 이상을 감지해도 ‘강제 중지’ 등 실질적 방어구조가 없는 경우가 많으므로, 감지와 조치(게이트)는 명확히 분리해야 함
- 알람이 너무 많으면 휴먼 리뷰 부하가 증가(예: 1% false alarm만으로도 10,000건 체크 발생), 실제 조직의 전문가 자원과 부하를 반드시 사전에 계산해야 함
- 적절한 알람 조정, 영향력 기준, 휴먼 개입 시점 등의 워크플로우 최적화 필요

### 에이전트가 남기는 트레이스 자체의 신뢰성에 결함이 있을 수 있으며, 별도 별도의 감사 인프라가 필요함

- 일부 보안 실험에서는 에이전트 트레이스에 문제가 있어 변조·오류·보안이슈 주입에도 자체 체크로는 이상이 감지되지 않음
- 독립적 감사(예: 전체 트래픽 및 기록 대조)에서는 모두 감지 가능
- 보안 관점에서는 에이전트 자체 데이터를 무조건 신뢰하지 말고, 외부 감사 및 기록 보존 체계 필요

### 실제 운영 환경 및 데이터가 ‘진실의 기준’으로, 평가 설계도 현실 업무에 최대한 가깝게 설계해야 함

- Omni Analytics 내 실제 내부 프로덕션 데이터로, 실사용자의 에이전트 활용 유형을 기준으로 평가 설계
- Q&A(쉬운 질문, 복잡한 질문), 대시보드/앱 생성 등 실제 사용 행태별 작업 유형을 분류·정의함
- 실험적 평가에서 이상적 결과가 나와도 실제 운영 환경(Production)에서만 진정한 신뢰 획득 가능
- Shadow 배포(실험적 데이터 수집), 폭넓은 관찰성 확보를 통해 현실 환경 내 문제점을 빠르게 탐지해야 함
- 현실적 위험 허용 범위, 자동/수동 검토 경계 등도 평가 시 반드시 명확히 설정

### 안전하고 신뢰 가능한 에이전트 운영을 위한 본인의 실전 프레임워크, 자료 및 커뮤니티 공유

- 자신의 소프트웨어 파이프라인에서는 ‘저위험 자동 승인’ 기준, 에이전트 의사결정, 인간 개입/확인, 운영 범위 등을 명확하게 관리
- GitHub 레포지토리에서 평가 설계, 하네스 추적 및 신뢰성 강화 관련 여러 사례와 코드, 문서를 공개
- 300페이지 분량 아카이브 자료를 통해, 커뮤니티 누구나 에이전트 평가 및 신뢰성 구축에 참고할 수 있도록 지원
