## *모델 스왑 워크숍: GPT-5.5, Kimi, DeepSeek, Mistral 비교 워크숍 — 마이크로소프트 파멜라 폭스* 핵심 요약

- 이 워크숍의 목적은 AI 엔지니어들이 GPT-5.5, Kimi K2.6, DeepSeek V4 Flash, Mistral Large 3 네 가지 최신 대형 언어 모델을 실제 사용 시나리오에서 직접 비교해보고, 각 모델의 차이와 강점을 경험하는 데 있다.
- 참가자는 제공된 깃허브 레포를 통해 환경을 구축하고, 각종 예제 스크립트와 실습을 통해 모델 결과를 직접 실험할 수 있다.
- 첫 번째 실습에서는 LLM들이 단순 계산(문장 내 특정 알파벳 개수 세기)을 얼마나 정확하게 수행하는지 비교하였으며, 모델마다 수학적 능력에 분명한 차이가 나타났다.
- RAG(검색 증강 생성) 테스트에서는 각 모델이 주어진 컨텍스트 내에서만 정보를 응답하는지, 혹은 자신의 학습 파라미터(웨이트)에서 답을 추론하여 할루시네이션을 일으키는지 평가하였다.
- 멀티모달(이미지 입력) 처리 능력 비교에서, 이미지 해석 및 분석 정확성에 큰 편차가 발견됨. 특히 작은 글씨 인식, 오브젝트 분류 등에서 모델별 차이가 컸다.
- Function Calling(함수 호출) 및 Tool Calling(도구 호출)에서는 JSON Schema 기반 함수 정의를 이해하고, 입력에 따라 적합한 함수와 파라미터를 호출하는 능력을 측정했다.
- 에이전트 설계 및 도구 호출 루프에서는 LangChain, Pydantic AI, 에이전트 프레임워크 등 다양한 프레임워크로 구성된 에이전트의 효율성(병렬 처리, 호출 횟수 최적화 등)도 비교하였다.
- 모델/에이전트의 출력 및 응답 평가를 위해 스트링 비교, LLM을 심판(판정자)으로 사용, 그리고 Microsoft Research의 신제품 'Assert' 프레임워크 등 정량적·정성적 평가 방법이 소개되었다.
- Dspy와 Jeppa와 같은 프로그래밍적 프롬프트 최적화 도구를 활용하여, 모델별 최적화된 프롬프트를 자동 생성·선택하는 방법도 시연되었다.
- Anthropic, Llama 등 추가 모델 지원 및 다양한 API 방식(메시지 API, 로컬 서버 활용), 다국어 대응, 사용자 실습 지원 등 실전 적용 팁도 공유되었다.

## 세부 요약 - 주제별 정리

### 실습 환경 구축은 Python, UV, GitHub Codespaces로 신속하고 유연하게 진행 가능함

- 참가자들은 GitHub 레포를 클론한 후 환경 변수(.env) 파일을 세팅하고, Python과 UV(의존성 관리 툴)로 필요한 패키지 설치를 진행함.
- Python과 UV가 설치되어있지 않은 경우, GitHub Codespaces(VS Code 기반 브라우저 개발 환경)에서 즉시 실습이 가능하도록 안내함.
- 실습 환경은 Microsoft Foundry에 배포된 여러 LLM(GPT-5.5, Kimi, DeepSeek, Mistral)과 연동되며, 토큰 리미트가 존재하므로 제한 초과시 환경 변수 변경으로 대응 가능함.
- 모든 예제 파일은 모델 이름 변수로 원하는 LLM을 쉽게 전환할 수 있는 구조로 설계되어 있음.

### 단일 LLM 호출(알파벳 수세기 예제)에서 모델별 수학·추론 능력 차이가 명확히 드러남

- 입력 문장 내 알파벳 'E' 개수(정답: 13) 세기 문제에서, GPT-3.5와 Kimi는 정확히 답을 맞춤.
- DeepSeek V4 Flash(6개)와 Mistral(8개)은 오답을 반환하여, 기본 계산 인스트럭션 수행력에서 차이가 있음을 보여줌.
- 프롬프트 엔지니어링(문장을 단어별로 나누어 카운트, 중간 추론 지시 등) 시, Mistral 등도 정답률이 개선됨.
- 이는 모델별로 동일한 프롬프트에 대한 처리 방식이 다르며, 간단한 명령도 모델마다 약점이 있을 수 있음을 시사함.

### RAG 테스트에서는 컨텍스트 기반 응답 충실성과 할루시네이션 발생 빈도에서 모델별로 명확한 차이가 있음

- RAG(검색 증강 생성)란 LLM이 외부 문맥(Context)에 기반해 답하는 구조로, 정보 근거(소스)에만 의존해야 함.
- 'Carpenter bees' 데이터셋만 제공된 상황에서, "Carpenter bee와 Honey bee의 둥지 짓기 차이점" 질문을 주고 응답을 비교.
- GPT-5.5와 Kimmy, DeepSeek는 "Honey bee 정보는 소스에 없다"고 정확히 답변.
- Mistral은 소스에 없는 Honey bee의 정보를 자체적으로 생성(할루시네이션)하여 제공함.
- 프롬프트 내 "정보 근거가 소스에 없으면 'No source provided'를 명시하라" 등 지시를 강화해도, 일부 모델은 여전히 불필요한 정보를 생성함.
- 보다 정확한 RAG 운용을 위해서는 모델이 '모르는 것을 안다고 말하지 않는지', 소스 충실성이 중요한 판단 기준임.

### 이미지 입력(멀티모달) 해석에서는 사진/표 등 다양한 유형별로 LLM 간 이해력에 큰 차이가 나타남

- 멀티모달(이미지+텍스트) 입력 테스트는 ① 소 에오록스(aurochs) 사진, ② 코스타리카 악어/악어 사진, ③ 작게 적힌 식물 리스트 표 이미지로 구성.
- GPT-5.5와 Kimmy는 각각 '유니콘 아님'(정답), '악어' 판별(입 모양으로 구분), 표에서 가장 저렴한 식물(58센트짜리)을 정확히 추출함.
- Mistral은 '악어' 대신 '엘리게이터'로 오답, 가격도 더 비싼 식물을 반환하는 등 인식 오차가 발생.
- DeepSeek는 멀티모달 입력이 불가하여 참여하지 않음.
- 다국어(예: 스페인어)로 질문시 잘못된 매핑/오해가 일어나기도 하므로, 언어별·도메인별 LLM 성능이 다를 수 있음을 강조.

### 함수 호출(Function Calling) 및 Tool Calling에서는 인자 생성, 함수 선택 등 논리적 적합성 측면에서 차이가 드러남

- JSON Schema 기반으로 "일정 등록(create calendar event)" 함수 정의/파라미터 선언 후, 다양한 LLM에 실세계 사용자 메시지(일정 제목, 참석자, 일시 등)로 함수 호출을 요청.
- GPT-5.5, DeepSeek, Mistral 등 모두 적절한 함수는 잘 호출하나, 파라미터(예: 참석자, 장소)에 미세한 차이(추가, 누락, 오답 등)가 나타남.
- 명확하지 않은 인자(ambiguity) 존재시, 프롬프트/설명 추가 등으로 세부 규칙을 보완할 필요성이 강조됨.
- Tool Calling 결과 비교를 통해, 툴 정의 방식 및 입력 케이스에 따라 LLM이 얼마나 정확히 의도를 파악하는지 실전 평가가 가능함.

### Tool Calling 반복(Loop) 및 효율성에서는 목표 달성까지의 호출 횟수와 최적화 능력에서 모델별 차이가 존재함

- 예시: 상점 계산 워드프로블럼에서, 도구(계산기 함수)를 한 번만 호출(모든 연산 일괄 처리) vs 여러 번 개별 호출(단계별 처리)로 답을 도출.
- GPT-5.5는 한 번의 호출로 전체 계산 처리, DeepSeek는 네 번 나눠 호출함(비효율적).
- Kimmy는 정상 동작하다가, 특정 상황에서는 검증 차원에서 불필요하게 여러 번 호출하는 현상도 발생할 수 있음.
- 동일한 문제도 LLM의 반복적 추론 전략, 효율적 툴 사용 능력에 따라 요청 횟수, 응답 속도, 리소스 소모가 달라진다.

### Agent 프레임워크 기반 실전 사례(여행 계획)에서는 병렬 처리, 조건 충실성, 효율 등에서 GPT-5.5가 두드러진 강점을 보임

- LangChain, Pydantic AI, Agent Framework 등으로 여행 플래너 예제 구현: 항공권/호텔 검색, 예산 확인, 활동 추천 등 복합 시나리오.
- GPT-5.5는 병렬 툴 호출을 지원하여(예: 항공권 검색과 호텔 검색 동시 실행), 최소한의 턴과 호출 횟수로 목표를 달성.
- Kimmy, DeepSeek, Mistral은 병렬 호출 미지원/비효율적 호출/마지막 단계 누락 등 덜 최적화된 동작을 보임.
- 에이전트 평가시 각 단계의 적절성, 도구 호출 효율, 병렬성, 지침 준수 여부 등 다양한 지표를 고려해야 함.

### 대량 자동 평가(이밸류에이션)는 스트링 체크부터 LLM 판정자, 새롭게 나온 Assert까지 점진적인 자동화·정교화 방법이 도입됨

- 함수 호출 결과는 단순 스트링 비교(예상 값과 실제 반환 값)의 단순 자동 평가가 가능함.
- 실제 운영 환경에서는 다양한 케이스(날짜 계산, 다양한 언어, 비표준 요청 등)를 커버하는 다수 테스트케이스 운용이 중요함.
- 스트링 비교만으로 복잡한 정답률을 측정하기 어렵기 때문에, 'LLM을 판정자 모드'로 활용(예: GPT-5.5 Judge 모델). 판정 프롬프트, Pass/Fail, 사유까지 함께 수집.
- 평가 자동화 프레임워크로는 LangFuse, LangSmith, Azure AI Evaluation SDK, OpenAI.evals, DeepEval, Promptfoo, VALLY 등 다양한 도구 존재.
- LLM-Based Judge 운영시 실제 전문가(사람) 레이블과의 calibration(정합성 체크)가 중요함.
- Microsoft Research의 신제품 Assert는 YAML 기반 스펙을 정의하면 테스트케이스와 평가 기준을 자동 생성, 실제 행위별 오류(예산, 직항, 등)와 위반 지점, 시나리오별 결과 분석을 자동화함.

### Dspy 및 Jeppa 등 프로그래밍적 프롬프트 최적화 프레임워크는 모델별 프롬프트 튜닝을 자동화하여 중소형 모델 활용도를 극대화함

- Dspy 프레임워크에서는 "요구 사항(예: 단어 개수, 첫 글자, 구조 등)"을 명세(spec)로 선언하면, Dspy가 여러 프롬프트 버전을 실험하며 최적화된 프롬프트를 자동 생성.
- Jeppa(유전 알고리즘 기반)로 다양한 후보 프롬프트를 시도하며 hills climbing 방식으로 성능을 개선.
- 이 방법은 특히 Mistral 등 사전 학습 프롬프트로 성능이 떨어지는 모델도, Dspy가 도출한 최적 프롬프트로 기대 성능을 이끌어낼 수 있음을 사례로 제시.
- 프롬프트가 입력 코드가 아닌 출력물로 도출된다는 점에서 전통적 방식과 큰 차이가 있음.

### Anthropic, Llama 등 추가 LLM 통합 및 다양한 API·로컬 환경 지원까지 실전 활용성을 크게 보강함

- Anthropic Claude 계열은 자체 메시지 API를 사용하며, RAG에 특화된 citation 기능(출처 내장 출력)을 제공함.
- 로컬 Llama 서버 연동도 지원되며, .env 및 모델 이름만 변경하면 동일한 워크플로에서 로컬 LLM 실험이 가능함.
- 다국어 실습, 다양한 input type(RAG, 이미지, 대화, 함수호출 등), 실습용 키 제공 등 실전 적용 팁도 함께 안내됨.

### 평가 프레임워크/도구 선택, 커스텀 평가 기준 설계, 실제 운영 데이터 반영, 실무형 자동화 방안 등 전문가의 노하우가 공유됨

- 평가 프레임워크(예: LangFuse, LangSmith, Assert 등) 선택 시 실제 운영 데이터·시나리오(유저 입력 케이스) 반영이 유의미함.
- LLM Judge 평가 설계시 사람 전문가와 calibration, 정확한 Pass/Fail 기준 명시, 평가 자동화시 테스트케이스 확장·추가 용이성 확보 등이 중요함.
- "Coherence/Fluency(일관성/유창성) 검사는 대부분의 LLM에서 불필요" 등 평가 관점별 실전 노하우, 오류 탐지 및 drift 방지 운영 방법 조언.

### 모델/프롬프트/프레임워크/실행 환경의 다양성에 대한 경험적 비교와, 실무에서의 융통성 확보가 중요함을 거듭 강조함

- 다양한 모델의 실제 성능, 프레임워크 기반 에이전트 동작, 멀티모달 입력 등, 단순 벤치마크로 대체 불가한 세부적 성능 차이를 확인함.
- 각 모델·시나리오별 최적 프롬프트/RAG/도구 호출 전략이 달라질 수 있으므로, 직접 실험 및 반복적인 평가와 최적화가 중요함.
