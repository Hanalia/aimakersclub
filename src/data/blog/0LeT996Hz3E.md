## *코딩 에이전트를 시스템처럼 엔지니어링하라 — 소프트웨어 팩토리의 미래* 핵심 요약

- Warp CEO 잭 로이드(Zach Lloyd)가 소프트웨어 팩토리 개념과 코딩 에이전트 시스템 설계의 변화에 대해 설명
- 과거에는 개발자가 각자 로컬 환경에서 개별 코딩 에이전트(local multi-threading)를 운용하는 경우가 많았으나, 최근에는 조직적이고 표준화된 소프트웨어 팩토리로의 전환이 활발히 이뤄짐
- 코딩 에이전트의 로컬 운용 방식은 자동화 한계, 운영비/생산성 관리 미흡, 보안 및 거버넌스 문제로 한계가 존재
- 소프트웨어 팩토리를 ‘코드로 정의되고(closed-loop) 지속적으로 개선하는 시스템’으로 규정
- 팩토리의 핵심 요건으로 ① 선언적 코드 정의, ② 측정과 데이터 기반 개선, ③ 자동화된 평가/벤치마킹/셀프임프루브(자가 개선) 프레임워크 필요성 강조
- ‘팩토리 엔지니어링’이라는 새로운 소프트웨어 개발 도구·관점의 부상: 디버거, 프로파일러, 크롬 디버그 툴처럼 이제는 벤치마크, AB테스트, 온라인 평가 등 새로운 툴셋 마스터 필요
- 팩토리 전체는 코드로 정의되어야 하며, 이를 통해 브랜칭·롤백·자가 개선(에이전트가 스스로 공정 제안) 등이 가능해짐
- 코딩 에이전트 워크플로 기록, 산출물 중앙수집 및 데이터화가 시스템 개선의 근간이 됨
- 실제 Warp 팩토리 데모를 통해, 실시간 팀 코딩 에이전트 모니터링, 성능 평가, 온라인 평가(evals), 벤치마킹 자동화 프로세스를 구현
- 모든 엔지니어는 이제 ‘제품’뿐 아니라 ‘시스템 개선 역량’을 갖춘 팩토리 엔지니어링을 배워야 하며, 이는 기존 소프트웨어 엔지니어링과 연결되는 새로운 도전임을 강조

## 세부 요약 - 주제별 정리

### 소프트웨어 개발 방식은 코딩 에이전트 개인 운용에서 시스템적 ‘팩토리’로 빠르게 전환되고 있음

- Warp의 CEO 잭 로이드는 과거 수백만 사용자를 위한 구글 독스(Google Docs) 엔지니어링 리드를 맡았으며, 현재는 Warp 오픈소스 코드 에이전트 터미널과 ‘내부 소프트웨어 팩토리’ 플랫폼을 개발
- 기존에는 대부분 개발자·플랫폼팀이 개인 로컬 환경에서 여러 코딩 에이전트(local multi-threading)를 직접 운용
- 실제 청중 대상으로 ‘로컬 멀티스레딩’ 방식 운용자 현황 조사, 여전히 다수이나 팩토리 개념 도입 및 테스트도 빠르게 증가
- 개발 방식의 이런 변화가 이미 진행 중임을 현장 분위기와 사례로 설명

### 로컬 코딩 에이전트 운용 방식에는 자동화, 비용, 보안 측면의 한계가 분명히 존재함

- 로컬 인터랙티브 프롬프트 기반 운용 시, 사용자의 수동 입력(휴먼 쓰루풋)에 의해 자동화 수준이 제한됨
- 엔지니어/플랫폼팀별로 에이전트 환경·모델·스킬을 개별 설정하다 보니, 생산성과 비용 효율 측정이 어렵고 배포·최적화도 비효율적임
- 각자 로컬 설치 환경에서는 보안 취약점과 거버넌스 추적 불가라는 명확한 조직적 위험성이 내재

### 소프트웨어 팩토리는 느슨한 오토메이션 집합이 아니라, ‘코드로 정의된 클로즈드루프 개선 시스템’이어야 함

- 소프트웨어 팩토리가 단순 프로세스 조합(charge set of automation)이나 개인 에이전트 집합이 아님을 명확히 구분
- 본인의 정의: “코드로 선언된(Declarative), 폐쇄루프(Closed-loop) 구조의 지속적 개선 시스템”
- 핵심은 모든 요소(에이전트, 워크플로, 트리거, 스킬, 배포 위치 등)를 코드로 선언하고 관리하는 구조
- 워크플로 자동화, 클라우드 배포 등 최대한 테라폼(Terraform) 스타일의 선언적 파일 구조 도입 필요성 제시

### 측정과 데이터 수집이 시스템 개선의 핵심, 모든 코딩 에이전트 행위를 구체적으로 기록해야 함

- 단순한 ‘좋은 분위기(vibes)’로 시스템 성능·품질을 판단하면 안 된다고 강조
- 실질적 성능·비용 최적화, 쓰루풋 극대화, 산출물 품질 확보를 위해서는 전면적인 관측·측정 체계 필요
- 모든 작업, 산출물, 세션, 대화, 코드, 아티팩트, 영상·스크린샷까지 저장·집적
- 이 데이터가 후속 개선, 자동 평가, 자기 개선의 근간이 됨

### 팩토리 엔지니어링은 ‘제품 개발’과 ‘시스템 자체 개선’을 복합적으로 요구하며, 모든 엔지니어가 새 도구셋을 마스터해야 함

- 기존 소프트웨어 엔지니어링이 디버거, 프로파일러 등 툴셋 능력에 따라 구분됐던 것처럼, 팩토리 엔지니어링은 벤치마킹, AB테스트, 자동 평가 능력이 핵심
- ‘에이전트 시스템 최적화’가 새로운 엔지니어링 프리미티브로 부상: 이제 모든 엔지니어가 시스템 개선까지 관여해야 함
- 물론 제품 개발(Product Engineering)은 여전히 중요하지만, 시스템 레벨에서의 최적화 도구셋 학습 또한 필수

### 팩토리 엔지니어링 스택: 코드정의-데이터수집-컴퓨트-추론-오케스트레이션-API 통합의 6층 구조가 필요함

- **코드로 선언된 팩토리(Factories as Code):** 워크플로/정책/트리거/스킬 등 모든 요소를 코드로 관리, 브랜치·롤백·자가개선 기능 가능
- **데이터·컨텍스트 계층:** 모든 에이전트의 작업 결과, 대화, 산출물, 아티팩트 중앙 저장(개선 재료)
- **컴퓨트(Compute) 계층:** 샌드박스 기반 실행, 멀티플랫폼 지원으로 보안·재현성 확보
- **추론(Inference) 계층:** 모델 및 에이전트 자유 교체·테스트 지원(예: Claude Code, Codex, Py, Warp 등)
- **오케스트레이션 계층:** 공장 내 작업 흐름 관장, 다양한 파이프라인 구성
- **API·MCP 우선 구조:** Slack, Linear, Jira, GitHub 등 조직 업무 툴과 자연스럽게 통합

### 모든 워크플로/산출물은 실시간 모니터링·집계·개선 대상이 되어야 하며, 중앙 추적체계 구축이 필수임

- Warp 플랫폼 내부 데모: 모든 엔지니어의 코딩 에이전트 세션·작업·산출물·대화를 실시간 Google Docs 형태로 시각화/감시
- 특정 작업(예시: Maggie가 Slack 상에서 Opus 55 구현) 실제 이력, 대화, 산출물, 자동문서화 가능
- 이런 데이터 집적이 없다면 조직의 생산성·품질·비용 관리가 ‘앞이 안 보이는(flying blind)’ 상태임

### 온라인 평가(Eval) 및 자동화된 벤치마킹이 시스템 개선의 핵심 메커니즘이 됨

- 모든 코딩 에이전트 세션에 대한 결과를 자동 평가(evals) 시스템이 재판단, 특정 품질지표 기준으로 스코어 제공
- 예시: Warp의 평가 항목 중 하나로 ‘불필요한 중복 테스트’ 탐지, 실패 사례 집계·분석에 사용
- 도출된 평가 지표와 에러 분석을 기반으로, 워크플로 파라미터 조정·정책 개선을 추진

### ‘자가 개선(Self-improvement)’ 루프에서는 에이전트가 직접 성능 저하 패턴을 감지, 코드 레벨 PR로 개선책을 제시함

- 전체 러닝 루프 예시: ① 모든 세션 자동 기록 → ② 자동 평가(evals) 적용 → ③ 실패 패턴 추출 → ④ 개선 솔루션(팩토리 코드 PR) 자동 생성
- 이 과정에서 인간의 직접 피드백 개입 필요 X, 에이전트간 자기진단·자가개선 루프가 중심

### 벤치마크 및 재현 테스트셋을 통한 모델, 스킬, 공장 구성의 품질·비용 트레이드오프 분석이 필요함

- 실제 데이터에서 벤치마크셋 생성 → 새로운 모델/스킬/하네스/팩토리 구성을 Replay하여 품질·비용 비교
- 예시: Sweebench, Terminal Bench 산출물과 유사한 품질/비용 산포 그래프 제공(왼쪽 상단: 이상적)
- 특정 스킬 제거, 팩토리 파라미터 조정 시 성과 변화 측정 중요

### Warp 실사례: 이러한 공장 엔지니어링 체계 도입으로 생산성·비용 효율성 극대화, 성능 가이드라인·벤치마킹·자동화 루프 지속

- Warp는 실제 조직 내에서 자체 벤치마킹/온라인 평가/성능측정/자동 개선을 반복 적용하여 비용 감소 및 쓰루풋 증대를 성취
- 모든 엔지니어가 새로운 팩토리 엔지니어링 관점과 도구셋을 배워, 시스템 전체의 품질 및 효율성을 극대화해야 함을 강조
- 결론: 코딩 에이전트를 ‘시스템처럼’ 엔지니어링해야 하며, 기존 엔지니어링 경험이 새로운 시대에도 여전히 중요하다고 언급
