## *모든 기업이 협업 불가능한 에이전트를 만들고 있다 - Justin Schroeder, Standard Agents* 핵심 요약

- 영상은 최근 AI 업계에서 각 회사가 자체적인 '에이전트(Agent)'를 개발하지만, 이들이 서로 호환되지 않아 생기는 문제를 지적하며, 이를 해결할 표준화의 필요성과 그 구체적 방안을 설명함
- 기존 AI 적용 방식은 MCP 서버와 마크다운 문서를 통한 추상적 스킬 연결이 주류였으나, 실제 기업들은 보다 구체적이고 통제 가능한 에이전트 개발을 선호함
- 기업이 에이전트를 선호하는 주된 이유는 ▲기존 핵심 비즈니스 프로세스와의 밀접한 통합, ▲에이전트의 '신뢰 가능성(범위 제한, 통제성)', ▲실질적 효율 및 효과(작업 성과 보장)에 있음
- 예시로 HVAC(냉난방) 업체, 대학교, 클라우드 제공자 등 다양한 산업에서 복잡한 비즈니스 절차(예: 워런티 처리, 크루 스케줄링, 재정지원 등)가 AI로 자동화될 때는 맞춤형 제어와 반복 가능성이 중요함이 강조됨
- 현존 에이전트 생태계는 언어, 도구, 실행 방식이 난립해 실제 대규모/교차 조직 활용·재사용이 어려움
- 표준 스펙의 필요성을 인식, 'Standard Agent Specification'(standardagentspec.org, 오픈소스)을 공식 발표하며 기본 설계철학, 구조, 원칙을 상세히 설명함
- 중요한 표준 원칙은 벤더 불가지론(어디서나 구동 및 호스팅), 도메인 특이성, 특정 모델과의 밀결합, 조합성, 이식성 등임
- 표준 내 모든 에이전트 구성(모델, 프롬프트, 도구, 서브에이전트, 훅, 효과, 스레드 등)은 코드(타입스크립트)로 정의·배포·패키징 가능함
- 실제 배터리 워런티 에이전트를 코딩에이전트에 의해 5분 21초 만에 생성·배포하는 데모를 통해, 실전 적용의 용이함과 투명성, 모니터링 기능 등을 시연
- 'Standard Agent Builder'라는 공개 런타임까지 발표하여, 누구나 로컬/클라우드/자체환경에서 손쉽게 표준 에이전트 개발·실행이 가능함을 강조함

## 세부 요약 - 주제별 정리

### AI 도입 트렌드는 개별 에이전트 개발이 주류로 부상하며 추상적 접근 방식과 괴리를 드러냄

- 과거 AI 도입의 정석은 MCP 서버에 기업 데이터와 업무를 API·마크다운(예: skill files, agents.md)로 문서화하고, 이를 LLM에 연동하는 방식
- 그러나 실제 시장에서는 이런 '도큐먼트+모델 연결' 방식이 아닌, 각기 자체적인 업무 에이전트를 직접 개발하는 사례가 확산 중
- 표준적 접근을 지키지 않는 건 실수가 아니라, 시장이 "더 나은 통합, 통제, 효과"를 무의식적으로 원하기 때문이라고 해석

### 기업이 자체 에이전트 개발을 선택하는 배경에는 통합, 신뢰성, 효과성 3대 요인이 있음

- 1) **통합(Integration)**:  
    - 기업의 핵심 프로세스는 각 조직별로 복잡하고 민감하며, 단순한 범용 모델(예: Grokbot)에 맡기기엔 위험 부담이 큼
    - 예: HVAC(냉난방) 회사의 워런티 처리, 크루 스케줄링, 허가증 발급, 대학의 금융지원, 클라우드사의 abuse 관리 등 실제 업무에 특화된 통제 필요
    - 관계 자산, 독점 데이터, 네트워크 효과 등 비즈니스의 '진짜 자산'은 이 프로세스 내에서 생성
    - 반복 가능성, 신뢰할 수 있는 집행, 기업만의 톤(voice) 보존 등 범용화된 LLM 기반 자동화로는 해결 불가

- 2) **신뢰성(Trustworthiness)**:  
    - "무엇이든 할 수 있으면, 정말 무엇이든 저지를 수 있다"  
    - LLM 에이전트가 과잉 권한을 갖고 의도치 않은 행동(예: 로그인 실패시 새 사용자 생성, 불필요한 이메일 송수신, 엉뚱한 데이터 접근 등) 위험 존재
    - 기업들은 '스코프가 좁고 명확한' 에이전트, 가능한 도구만 사용 가능한 구조를 추구
    - 워런티 처리 에이전트는 '장비 조회, 사진 첨부, 청구서 제출' 등 특정 툴만 사용하도록 제한

- 3) **효과성(Efficacy)**:  
    - 단순히 '모델이 똑똑한가?'가 아니라, '실제 업무 목표를 제대로 성취하는가?'가 중요
    - 벤치마킹/효율성 평가(evaluation)가 에이전트 단위에서 실질적 성과 개선으로 직결
    - 업무 단위별 미니 에이전트(ex: 워런티 청구)라면, 맞춤형 평가와 효과성 향상이 쉬움

### 대형 LLM+범용 스킬 기반 시스템과 '맞춤형 소형 에이전트' 전략의 성능 및 비용 차이가 뚜렷함

- 지금까지는 Opus 55 등 고성능 LLM과 다수의 도구·스킬 통합형으로 에이전트 시스템 생태계가 구축됨
- 그러나 DeepSeek V4.1 Flash 등 저가 LLM 기반의 '작은 업무용 에이전트'가 특정 작업에선 비용 효율성과 성능 모두 우수
- 논문(JEEPA) 인용: "모델 파인튜닝보다 개별 에이전트의 프롬프트/도구 조합 파인튜닝이 훨씬 효과적"
- 무리하게 범용화를 추구하기보다, '작고 잘 정의된' 도메인별 에이전트의 집합 및 하이라키 구축이 더 바람직

### 현재 시장의 에이전트 구현은 난립 상태라 협업·공유·재사용·조합에 본질적 한계 존재

- 언어, 툴, 프레임워크, 에이전틱 루프 등 각종 방식과 생태계가 제각기여서 기업 간, 부서 간 교환·협력이 어려움
- 에이전트 개발은 사실상 '하니스(harness)' 구축에 가까움(실행 환경, 내구성, 에러 복구, 병렬 처리 등 고려사항 다수)
- MCP로도 해결 불가: 종합 추론능력, 여러 단계의 인터페이스 요구 등 복잡성이 늘어나 결국 (비표준) 에이전트 시스템을 재구축하게 됨
- 커스텀 하니스 간 이식·조합 불가, 대량 개발의 비효율, 중복 문제 등 실무적 병목

### 에이전트 표준화 필요성과 기존(비본질적) 표준들과의 차별성 부각

- Skills, MCP 등 일부 요소는 이미 부분적 표준화(툴 분배, 프롬프트 파일, intercommunication 프로토콜 등)가 있으나, '하니스 자체'(에이전트 런타임)의 표준은 부재
- 스펙 표준화의 효과:  
   - '빠른 개발(구현 반복 최소화)'
   - '구현 일관성(모든 에이전트가 동일한 방식으로 작동)'
   - '이식성(어디서든 쉽게 배포, 실행, 공유)'
   - '조합성(효율적 복합 시스템 세팅)'

### Standard Agent Specification의 설계 철학과 5대 핵심 원칙 명확히 제시됨

- **에이전트는 비결정론적 결과를 결정론적으로 다루는 소프트웨어**(즉, 하니스의 인스턴스)
- 다섯 가지 설계 원칙:
    1. Vendor Agnostic(벤더 불가지론: 특정 클라우드/엔진/하드웨어에 종속되지 않아야 함)
    2. Domain Specific(도메인 특이성: 명확한 업무 목적에 집중)
    3. Model Coupling(특정 모델과 결합: 개별 작업에 최적화된 모델 연결)
    4. Composable(조합 가능성: 작은 단위 결합 가능)
    5. Portable(이식성: 코드 패키지화 및 타 환경 배포/실행 가능)

### 표준에서 요구하는 모든 에이전트 구성요소 및 실행 환경은 코드(타입스크립트)로 엄격히 통합됨

- 모든 정의(모델, 프롬프트, 도구, 서브에이전트, 룰, 훅, 효과 등)는 Typescript로 이루어져야 함
- 이 선택의 이유:
    - 타입 강제, 실행 효율, 어디서나 구동 가능, No 빌드/컴파일 실시간 실행(인터프리트)
    - MCP 방식은 툴 제공 서버 요구·유지관리 번거로움 → 표준은 코드 번들링으로 일체화 지원
    - 향후 '에이전트가 에이전트를 만드는' 자동화 지원 위해 필요

### 코드 예시와 함께 표준 내 주요 구성 구조(모델, 프롬프트, 도구, 에이전트, 핸들러 등) 상세 설명

- 모델: 실질적으로 사용하는 LLM(예: OpenAI 특정 모델, DeepSeek 등)과 버전/옵션을 타입으로 명확히 설정
    - 주 모델 실패시 '상위 모델' 대체 지정 가능
    - 도메인 특화성에 따라 저렴한 모델을 선택적으로 핀ning하는 전략도 가능
- 프롬프트: 대화 내 역할(assistant/user) 지정, 서브프롬프트 내장, 런타임 변수 삽입 가능(톤, 지침 등 일관화 용이)
- 도구(Tool): 타입은 '코드 실행', '서브프롬프트', '서브에이전트'
    - 예: 이미지 생성 툴=서브프롬프트, 내용 평가 툴=서브에이전트 등 계층적 조립 가능
- 핸들러: 완전히 결정론적 코드로 사람 혹은 AI에 반응, 'non-AI 에이전트'도 규격 내 작성 가능
- 에이전트간 대화구조(side A/B)·컴포지션(예: QA용 AI↔AI 등), 서브에이전트, 부모 훅 구조 모두 표준화
    - 훅(Hook): 내부 결정론적 이벤트(예: 호출 전/후, 메세지 필터, 업데이트 등) 정의
    - 효과(Effect): 예약 코드(trigger/스케줄), 예: 툴이 미래에 리마인더 자동 호출

### 스레드(Threads) 설계로 에이전트별 격리 샌드박스 및 모니터링, 투명성, 고도화 지원

- 스레드는 자체 메시지, 도구, 서브에이전트, 키밸류저장, 유사 파일시스템 등 독립 환경으로 존재
- AI/코드 내장 실행, 외부접근 제어, 코드·파일 작성·실행가능 지원(인터넷 접근 허용여부, import 허가도 규정)
- 의사결정용 모델(Typesafe AI, Jev 등) 연동, 특정 상황(예: 감정·위기 판단)에만 사람 개입 루트 확보
- 모든 에이전트는 자체 API(HTTP·웹소켓) 엔드포인트 노출 표준 지원으로, 챗봇, MCP 연동 등 용이
- 에이전트 패키징(zip, npm 등), 런타임은 다양한 방식 지원(Rust, Go, JS 등)은 TypeScript 컴플라이언스만 지키면 됨

### 표준 기반의 실제 에이전트 생성·배포·관리 데모로 실질적 효과와 개발 흐름 실증

- 배터리 워런티 청구 에이전트 생성 예시:
    - Claude Code(코딩에이전트 활용)로 프로세스 PDF → 업무별 도구·모델·프롬프트 코드 자동 생성
    - 5분 21초 내 완성, 파일시스템에 프롬프트·도구(offer tradein, check battery 등) 파일로 생성
    - 실제 정해진 도구만 사용 가능, 불필요한 행동 원천 차단
    - Admin UI 상에서 실행 내역, LLM 사용량, 토큰, 비용, 모델, 캐시율 등 투명하게 시각화 제공
    - HTTP/websocket API 자동 노출 → 실제 챗봇, MCP 서버 등 외부 서비스와 연동 간소화

### 표준 런타임인 'Standard Agent Builder'를 오픈소스로 공개해 자유로운 확장성을 보장함

- 누구나 즉시 머신에 클론·설치 후 표준 에이전트 생성·실행·패키징 가능
- 로컬/클라우드 옵션, 기존 생산 환경에서 이미 가동 중
- 개발자 에이전트(코딩 에이전트)에게 표준만 알려주면 자동으로 하니스·에이전트 코드를 생성
- 런타임은 특정 언어·환경 불문(TypeScript 규격만 준수) → 생태계 확장, 다양한 아키텍처 지원

### 이제 에이전트 생태계의 Future는 '웹 표준의 초기'처럼, 모두가 참여하는 오픈 협업·표준화에 달려있음을 강조

- 웹 초창기처럼 표준 없이 각자 고유 방식으로 난립하던 국면에서, 협업적 표준규약 설정의 중요성 역설
- 커뮤니티·생태계(standardagentspec.org, 공개 런타임/스펙·참여 유도 등) 중심으로 발전 추진
- 이후 표준 위에서 다양한 도메인 특화 에이전트, 협력적 배포·확장 문화 형성을 목표로 함
