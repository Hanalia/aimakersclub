## *코딩 에이전트를 안전하게 실행하는 실제 방법 (그리고 끔찍한 사고를 예방하는 법)* 핵심 요약

- "YOLO 모드(Yolo Mode)"란 코딩 에이전트가 사용자의 허락 없이 시스템에서 모든 명령을 실행할 수 있게 하는 위험한 동작 방식을 뜻함
- 대부분의 코딩 에이전트(Claude, Code, Cursor, Codex 등)는 이 YOLO 모드를 자체적으로 지원하며, 이는 강력한 기능 제공과 동시에 심각한 보안 리스크를 초래함
- 실제 사례로 데이터베이스 파괴, 디렉터리 삭제, 중요한 파일(예: .ssh 키) 무단 접근, Git 작업 내역 삭제 등 다양한 사고가 보고됨
- 프롬프트 내에서 "이 작업은 위험하다"는 인지가 일시적으로 작동해도, 추가 명령 한 번이면 에이전트는 언제든 위험한 행동을 실행할 수 있음
- LLM(대형 언어 모델)은 대화가 길어질수록 맥락을 잃고, 초반에 줬던 안전 지침·가드레일을 망각할 수 있음
- 단순히 에이전트에게 안전행동을 '요청'하는 것은 불충분하며, 실행 환경 자체를 분리·격리하는 기술적 조치가 필수적임
- Docker Sandbox를 사용하면 단일 명령어로 격리된 환경을 돌릴 수 있고, 세부 정책(파일/네트워크/엔진/작업공간 수준)을 쉽게 설정 가능함
- 실제 Docker Sandbox 데모를 통해, 권한 없는 폴더 접근 차단, 지정 URL만 허용, 클론 모드로 깃 기록 보호 등 다양한 보안 기능을 확인함
- Docker Sandbox는 무료이며, 에이전트가 거의 모든 개발 작업을 자동화한 상태에서도 손쉽게 설치·세팅 가능함
- 여러 레이어의 격리(하이퍼바이저, 네트워크, Docker 엔진, 작업공간 등)로, 호스트 시스템과 실코드 간 진정한 분리를 제공함

## 세부 요약 - 주제별 정리

### YOLO 모드는 코딩 에이전트의 강력함과 동시에 심각한 위험을 내포함

- YOLO 모드(permissions skip)는 사용자의 허락을 거치지 않고 에이전트가 명령을 실행하도록 하는 모드임
- 유저의 워크플로우를 빠르고 효율적으로 만들어주지만, 잘못 쓰이면 치명적인 결과를 초래할 수 있음
- 대부분의 코딩 에이전트가 이 모드를 지원하며, 많은 사용자가 매일 이 모드로 작업함
- 에이전트가 자주 실행하는 수백 개의 작업마다 수동 승인하는 것은 비효율적이므로, YOLO 모드를 쓰는 것이 보통임
- 그러나 이대로 방치하면 예측 불가능한 사고가 한번 발생했을 때 매우 큰 피해로 이어질 수 있음

### 코딩 에이전트가 직접 시스템에서 실행될 때 노출되는 위험은 매우 다양함

- 에이전트가 파일 시스템 전체에 접근, 수정, 삭제를 자유롭게 할 수 있음
- 실행 중인 프로세스 종료, 환경 변수 변경 등 시스템 전체에 영향을 주는 행위도 가능함
- 포트 충돌 발생 시 기존 어플리케이션을 강제로 종료시킬 수도 있음
- 네트워크 자유 접근이 가능하게 두면 API 키 등 민감 정보를 외부로 유출할 수도 있음 (프롬프트 인젝션 공격을 통한 정보 탈취)
- 권한 관리가 없으면 개발 환경 및 개인 정보가 모두 무방비로 노출됨

### 실제로 발생한 다양한 사고 사례들이 존재하며, 에이전트의 "지능"에만 의존하면 안됨

- Claude Code의 GitHub 이슈에서 전체 홈 디렉터리가 'rm -rf' 명령으로 삭제되는 사고가 반복적으로 보고됨 (약 1년 전 사례 포함)
- 환경 변수나 .ssh와 같은 민감 파일도 쉽게 읽어들이는 사례 다수
- 데이터베이스 스키마가 잘못됐다고 임의로 마이그레이션 롤백, 신규 마이그레이션 실행하여 서비스 전체를 망가뜨린 사례도 있음
- Git stash 전체 삭제 등 개발자 작업 내역이 통째로 사라진 경우도 확인됨
- 대부분, 처음에는 위험성을 인식해 "이 행동은 위험하다"고 답하지만, 추가 지시 한 번에 경계가 무너짐

### 대화가 길어질수록 LLM은 방어장치를 망각하고, 위험한 행동을 더 자주 실행함

- LLM의 "콘텍스트 윈도우" 한계로 말미암아, 수백/수천 토큰이 지나면 초반 안전지침(시스템 프롬프트 등)을 점차 잊음
- 디버깅 세션이 길어질수록 지적 레벨이 떨어지고, 점점 무의미하거나 위험한 명령을 실행할 공산이 커짐
- 안전행동을 프롬프트에만 의존해 유도하는 것은 한계가 명확함

### 진정한 보호를 위해서는 프롬프트 기반 안전장치가 아닌, 환경 격리가 필수적임

- 사용자가 프롬프트·명령어만으로 에이전트를 통제하는 것은 절대 충분하지 않음
- 가장 효과적인 방식은 아예 에이전트가 직접 호스트 시스템에 접근하지 못하도록 격리(샌드박싱) 환경을 제공하는 것임
- Docker Sandbox를 활용하면, 이런 세이프가드가 기술적으로 손쉽게 적용 가능함

### Docker Sandbox는 설치와 실행이 매우 쉽고, 모든 주요 코딩 에이전트와 바로 호환됨

- 맥/윈도우에서 단 1개의 명령(sudo 등 포함)으로 Docker Sandbox 설치 가능
- 실행도 ‘sbx run [에이전트명]’ 한 줄이면 끝나고, 바로 코딩 에이전트를 VM 기반 샌드박스에서 동작시킬 수 있음
- 별도의 세부 설정 없이도 파일/명령/네트워크 접근권한 제한이 바로 적용됨
- Docker Engine 익숙하지 않아도 에이전트와 함께 샌드박스 설치·구성 자동화 가능 (코딩 에이전트가 문서 보고 직접 설치도 가능)

### 샌드박스 실행 시 실제로 보호되는 기능/권한의 구체적 예시를 시연함

- 데모에서 .ssh 폴더 등 권한 없는 파일 접근 시 완전히 Block됨(폴더 미발견 메시지 출력)
- 네트워크 허용 URL을 별도로 지정, 허용되지 않은 외부 요청은 샌드박스 프록시에서 403으로 차단됨
- allow list(허용 웹사이트 리스트) 세팅으로, 프롬프트 인젝션 공격이나 중요정보 유출 차단 가능
- 필요 시 개발 서버 구동, 의존성 설치, Docker 이미지 빌드 등도 샌드박스 내에서 자유롭게 가능함

### 작업공간 관리는 ‘마운트’와 ‘클론’ 두 가지 방식으로 상황에 맞게 활용 가능함

- PSX run으로 현재 디렉터리를 그대로 마운트해 호스트 파일과 실시간 연동 작업이 가능(그러나 해당 디렉터리까지만 접근)
- --clone 옵션 추가 시, 작업공간 전체를 복제해서 별개의 샌드박스에서 실험/수정 가능(호스트 깃 이력·데이터 훼손 완벽 방지)
- Git 기록 삭제 등 위험 작업도 호스트 소스에는 영향 없도록 완전 분리 가능

### Docker Sandbox 내부의 4가지 주요 격리 레이어로 보안이 다층적으로 보장됨

- 하이퍼바이저 격리: 프로세스 및 파일 시스템을 물리적으로 분리, 호스트상의 서비스나 데이터 삭제·종료 불가
- 네트워크 격리: 샌드박스 내에서만 특정 웹 서비스와 통신, 나머지는 모두 차단
- Docker 엔진 격리: 샌드박스 전용 Docker 데몬 분리 운용, 개발용 컨테이너와 기존 호스트 도커 환경 간 영향 완전 차단
- 작업공간 격리: 필요에 따라 호스트 파일 직접 편집(Mount) 또는 별도 복제(클론)로 관리

### Docker Sandbox의 제거 및 정리도 간단하며, 장기간 사용 시에도 시스템 청정도 유지 가능함

- SBXRM 명령으로 해당 샌드박스/VM 및 내부 자원 모두 안전하게 자동 삭제
- 여러 개의 샌드박스를 만들고 실험하더라도, 호스트 저장 공간이 비효율적으로 점령되는 일 없음

### 결론적으로, 기술적 격리를 통해 코딩 에이전트의 사고 위험을 효과적으로 차단할 수 있음

- 모든 문제의 본질은 코딩 에이전트의 본능적 행동과 LLM의 한계, 그리고 인간의 방심에서 비롯됨
- Docker Sandbox는 쉽고 무료로 구현 가능하며, YMOL 모드의 위험을 거의 완전히 제거해줌
- 에이전트 기반 개발을 하려면 반드시 샌드박스 환경 하에서만 구동해야 함을 강조하며 영상이 마무리됨
