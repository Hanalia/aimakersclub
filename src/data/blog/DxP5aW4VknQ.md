**채널명:** AI Engineer

## *서브 에이전트는 분산 시스템이다. 분산 시스템처럼 다뤄야 한다* 핵심 요약

- 영상 시작에서 강연자 Girish Konda(Microsoft 수석 소프트웨어 엔지니어)는 '서브 에이전트'를 실제 엔지니어링 업무에 활용한 경험을 바탕으로, 서브 에이전트 시스템의 문제를 분산 시스템 관점에서 분석할 필요성을 강조함
- 대표적인 아키텍처 구조는 오케스트레이터가 작업을 여러 서브 에이전트에 동시에 분배, 각각이 동일한 공유 상태를 읽고 외부 도구나 시스템에 접근·수정하며, 결과를 취합하는 형태임
- 이 구조에서 발생하는 실패 원인들은 인공지능 에이전트 특유의 것이 아니라, 분산 시스템에서 반복되어온 고전적인 문제(부분 실패, Dirty Read, Unbounded Fan-out, 부적절한 재시도 등)임
- Girish는 시스템의 견고성과 신뢰성을 위해 'Safe Handoff Consistency Model'이라는 새로운 일관성 모델을 제안, 이를 S(원본 기록), A(한 번만 반영), F(분산 제어 예산), E(명확한 상태 반환)로 구체화함
- 구체 사례(서브 에이전트의 오동작, 무응답, 추론이 사실화되는 오류, 작업 부하 폭증 문제 등)를 공개한 오픈소스 MCP Peacemaker 프로젝트 및 자작 논문에 근거해 설명함
- 각 개념은 실제 분산 시스템 논문(FLP, Chandra&Toueg, Lamport 등)과 연관 지어 고전 이론의 현대적 적용 양상을 제시함
- Safe Handoff 모델의 도입은 활동 기록·추적성, 작업의 리트라이/중복 방지, 분기·재시도 관리, 에이전트 간 데이터 신뢰 기준, 부하 제어, 실패 기록을 체계적으로 개선할 수 있도록 설계됨
- 다만, 이 모델이 모든 상황에 적용되는 것은 아니며, 사람이 직접 후처리하는 에이전트 또는 멀티 오케스트레이터 환경에는 부적합함을 명확히 고지함
- 최종적으로, 에이전트 간의 작업 위임을 네트워크 호출로 인식, 실패 및 일관성 규약을 반드시 코드로 강제할 것을 조언함
- 관련 참고자료로 자신이 직접 작성한 오픈소스, 논문, 국제표준, 분산 시스템 고전 논문들이 언급됨

## 세부 요약 - 주제별 정리

### 에이전트 간 작업 위임은 분산 시스템의 고전적 문제를 그대로 드러냄

- 오케스트레이터가 업무를 분할해 여러 서브 에이전트에 전달하고, 이들은 동시 실행됨
- 모든 서브 에이전트가 동일한 공유 상태(대화, 메모리, 파일, 저장소, 이슈, 벡터스토어 등)를 읽음
- 에이전트는 단순 연산뿐 아니라 실제 시스템(데이터베이스, API, CI/CD, 배포 파이프라인 등)에 실제 영향을 주는 "툴 콜" 수행
- 결과는 오케스트레이터가 병합해 단일 응답으로 반환
- 이 구조는 전형적인 분산 시스템의 특징 (분산 상태, 동시성, 결과 병합, 공유 자원 접근 등)을 그대로 가짐
- 실제로 나타나는 문제 역시 분산 시스템에서 겪어온 여러 고전적 장애 양상과 일치함 (네트워크 실패, 지연, 동시성 이슈 등)

### 부분 실패와 반환 오류는 분산 시스템의 기본 문제로, AI 환경에서도 반복됨

- 분산 시스템에서의 부분 실패(Partial Failure): 호출 도중 실패 및 예외 반환
- 서브 에이전트 환경에서는 성공처럼 보이는 오류 응답(텍스트만 정상적으로 리턴)도 존재
- 클린 장애(Crash down): 프로세스가 중단되어 멈추는 경우, 명확하게 감지 및 처리 가능
- 무응답(No Reply): 호출이 유실되거나 지연…실패 탐지기가 완벽하지 않음을 지적(Chandra & Toueg 1996)
- Byzantine Failure: 잘못된 정보나 모순된 결과 반환(일부만 수행된 서브에이전트 등)
- 예시: 동일 작업 결과(정상 데이터 기반, 이전 답변 근거, 아무 연산 없이 응답)들이 모두 동등하게 분류됨 → 실질적 수행 여부 구분 불가

### FLP/분산 이론 사례로, 서브 에이전트의 실패 감지가 불확실함을 강조

- FLP 논문(1985): 비동기 시스템에서 하나의 장애만 있어도 완전한 합의가 불가능함
- Chandra & Toueg(1996): ‘실패 탐지기’도 오탐 가능(확실하지 못함)을 강조
- MCP Peacemaker 오픈소스 사례: 최초 실행시 30초 타임아웃 오류는 느림(슬로우 스타트)일 뿐, 진짜 실패 아님 → 개별 초기화 타임아웃으로 해결
- 서버가 호출 중 크래시된 경우, 타임아웃으로 인해 종료 코드가 무시됨 → 타임아웃과 실제 오류 정보를 구분, time out은 suspicion(의심) 상태로 기록
- 실패는 상태값으로 명시적으로 관리(완료, 실패, 취소, 거부 등)

### Dirty Read(더티 리드) 및 잘못된 합의는 공유 상태와 무비판적 병합에서 발생함

- 서브 에이전트가 실제 측정 없이 오류율 80% 감소를 추론해 공유 컨텍스트에 즉시 기록
- 다른 에이전트가 이 추론 기반 데이터를 사실로 읽고 또다시 증폭/인용, 마지막으로 오케스트레이터가 여러 결과를 병합
- 결과적으로 한 번의 추측이 약 3번의 ‘사실’처럼 기록, 합의가 잘못 형성됨
- SQL 격리 수준 이론(1995)에서 Dirty Read는 트랜잭션 커밋/롤백 전 데이터를 읽는 오류로 정의
- 분산 시스템에서는 쿼럼(Quorum) 방식(동시 다수 노드의 일치)이 Dirty Read 방지에 효과적이나, 에이전트의 공유 컨텍스트에서는 쿼럼이 유의미하지 않음(동일 소스의 반복 인용일 뿐)

### 기존 데이터베이스 일관성 모델(선형화, 인과적, 세션 등)이 서브 에이전트 환경에 부합하지 않음을 논증

- 선형적 일관성(Linearizable), 순차적 일관성(Sequential), 인과적 일관성(Causal), 세션 일관성(Session Guarantees), 최종 일관성(Eventual Consistency) 등이 소개됨
- 서브 에이전트의 공유 컨텍스트는 어떠한 일관성 모델도 보장하지 않음(명시적 약속이 없음)
- 차상위 일관성(Causal/Session Guarantees)은 단일 오케스트레이터 한정에서만 가능
- 병렬적/다중 에이전트·오케스트레이터 환경에선 별도 모델 필요

### Safe Handoff Consistency Model은 분산 시스템 문제 해결을 위한 실용적 모델임

- Safe Handoff는 S(소스 버전 명시), A(1회성 반영), F(분산(팬아웃) 제어), E(명확한 결과 상태 선언)로 구성
    - S: 모든 데이터와 판단에 ‘출처, 시점, 버전’ 기록 → “사실”과 “추론”을 분리
    - A: 모든 쓰기 작업은 단 1회, 동일 작업에는 반드시 ‘사용자 승인, 작업 ID’로 구분(리트라이/중복 방지)
    - F: 병렬 실행(팬아웃) 수, 각 하위 세션 대기시간, 거부(실패) 여부를 오케스트레이터가 명시적으로 관리
    - E: 모든 작업 결과는 ‘완료, 실패, 취소, 거부, 미확정, 타임아웃’ 등으로 명시적으로 반환

### S(소스 명확화)에서는 데이터 프로비넌스(기록화)와 정보 신선도를 주기적으로 점검함

- Lamport(1978) 논문 인용: 사건의 선후 관계를 ‘사실’ 단위의 기록으로 명확히 함
- 모든 데이터에는 출처(누가, 언제, 무엇을 근거), 데이터가 최신인지(신선도)를 판별하는 타임스탬프(데이터 발생/읽음/사용 시각) 부착
- 예시: 신선도 한계를 5분으로 둘 경우, 9:05에 데이터 생성→9:06에 리딩→9:07에 활용→새 요청(9:15)엔 신선도 한계 초과로 재판독 요구
- 관찰(Observation)과 추론(Inference)을 구분점으로, 실측값만 신뢰

### A(한 번만 효과)는 재시도(리트라이) 문제를 분산 트랜잭션 이론 기반으로 관리함

- 1회성 반영(At Most Once): 한 작업은 한 번만 실질 결과에 반영, 중복·불확실성 방지
- 예시: 툴콜 호출 reply 분실시, 리트라이로 인해 실제 작업(예: PR 생성)이 중복 실행될 수 있음
- 분산시스템 논문(RPC 1984) 언급: 리턴값에 따라 “정확히 한 번”, “최소 한 번”, “최대 한 번” 등 디딤돌 삼아 설계
- MCP에서는 idempotency(중복 방지)는 기본값이 “false”, 필요시 직접 구현 권장
- 재시도 과정에서 액션에는 고유 식별자를 부여, 승인(approval)→1회성, 이후 결과를 상태값으로 판별 후 확정
- 분산 락/리스 이론(Distributed Lock/Lease, Martin Kleppmann) 기반으로, ‘펜싱 토큰’(Fencing Token, 한번만 유효) 방식 도입
- 서브에이전트가 재개/종료하며 상태가 뒤섞이는 문제 해결(세션 복원시 컨텍스트만 복구, 실제 효과는 ID와 approval로 제어)

### F(분산 제어 예산)는 비제한적 부하 확산 및 리소스 고갈 버그를 사전 예방함

- 실사례: MCP bridge에서 병렬 세션이 동시에 패키지 매니저(NPX/NPM) 호출시 패키지 캐시 충돌, Lock 오류로 집단 실패 발생
- 어떠한 개별 요청도 독립적으로 문제없지만, 전체 동시성에 의해 전체 서비스가 붕괴
- 분산 시스템 flow control 개념 적용: Cold Start는 기본 2개 동시만 허용, 이후 15초 대기 → 이 시간 초과시 비보장 실행(가용성 우선)
- 세션 개수 상한 도입(10초 내 시작 못하면 거절로 명확 기록)
- capacity reserve를 실제 시작 전에 사전 점유하지 않으면 여러 큐가 동시에 cap을 초과시킴(“check then act” race)
- 오케스트레이터가 각 세션별 대기, 실행, 거절 모두 명시적으로 관리

### E(명확한 결과 반환)는 모든 하위 작업의 상태를 코드로 확정해 신뢰도와 추적성을 높임

- 서브에이전트의 응답은 “텍스트”가 아닌 “상태”로 명시(완료, 실패, 거절, 타임아웃, 미확정 등)
- 오케스트레이터가 결과를 schema·신선도·수치 검증 코드로 명확히 심사
- 결과 체크 실패시 경고문구만 전달하는 것이 아니라, 단계 자체를 거절로 처리
- 예시: 서브에이전트가 에러율이 10/1000→6/600으로 떨어졌다고 함, 실제 에러율은 1%로 차이 없음 → 수학적 검증 후 거절 처리
- 허용되는 결과: 명확 근거가 있는 답, 의도된 인간 승인/델리게이션
- 허용 불가: 추정에 기반한 자신감 있는 답변(Confident Guess)
- 승인, 감사, 결제 등 후속 트래킹 때문에 결과값 명확화 필수

### Safe Handoff 일관성 모델의 한계와 설계 Trade-off를 명확히 밝힘

- 모델은 사실을 '진실'로 만드는 기능이 아님, 오직 '출처 추적'만 보장
- 정확히 한 번의 결과 전달(Exactly Once)을 전제하지 않음, 리턴값 분실은 ‘unknown’으로 남음
- 롤백(Undo)을 자동 지원하지 않음(부분작업 보상 로직은 별도 설계 필요, 1987년 논문 인용)
- 작업자(서브에이전트) 간 전역 순서 불가, 오로지 단일 이벤트 체인(Causal Only)
- CAP Theorem 상 'Cold start' 등 쓰기 작업에서는 가용성 포기, 일관성 우선(실패를 추정하지 않고 거절)
- PACELC(Consistency-Latency Trade-off): 일관성 체크 빈도 증가시 대기 시간/오버헤드 상승

### Safe Handoff 모델은 일부 환경(사람 검토용, 멀티 오케스트레이터)에서는 오히려 불필요하거나 부적합함

- 결과를 사람이 직접 검토하는 에이전트: Safe Handoff의 상태 관리, 승인 절차는 오버헤드에 불과
- 단일 오케스트레이터 환경 전제, 멀티 오케스트레이터·피어 투 피어 구조에는 적용 힘듦

### 실무 적용 권고 및 마무리 요약
