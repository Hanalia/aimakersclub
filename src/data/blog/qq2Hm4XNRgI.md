## *AI 에이전트가 무엇을 기억해야 하는지 결정하는 방법* 핵심 요약

- **Oracle의 Wojciech Pluta는 지난 10년간 영국 은행들과의 프로젝트 경험과 오라클 AI 데이터베이스의 기술 마케팅 리더로서의 배경을 바탕으로 발표함**
- **에이전트 메모리 설계는 ‘읽기(리트리벌)-쓰기(메모리)’ 경로를 분리해, 무엇을 최종적으로 장기 저장할지 결정하는 '메모리 프로모션'이 핵심이라고 강조**
- **모델과 하니스(모델을 감싸는 실행 제어 코드) 구조에서 데이터를 기업의 경쟁사와 차별화하는 본질적인 요소로 바라봄**
- **‘메모리 프로모션 파이프라인’은 의미 분류, 기존 기록 비교, 증거 요구 검증, 하니스의 승인·거부 또는 휴먼 리뷰 단계로 구성**
- **금융 사례 데모에서는 사용자 요청 내용과 AI의 반응, 메모리 저장 및 재호출, guardrail(프로모션 제한) 설정, 조직 내 팀 멤버와의 기억 공유 등 실제 플로우가 구체적으로 시연됨**
- **에이전트가 단기(세션), 장기(에피소드·프로시저·지식·선호), 공유 메모리로 다층적으로 기억을 분류해야 함을 강조**
- **오라클의 에이전트 메모리 패키지는 데이터베이스 기반의 robust 구조와 스키마, 인덱스, 라이프사이클, 권한 관리 등 실무적 요건을 적극 반영**
- **최신 릴리즈는 엔드유저 격리 및 다양한 데이터 타입(문서, 벡터, 이미지 등) 지원, context card 제공 등으로 관리와 활용이 대폭 단순화됨**
- **결론적으로, ‘모델은 누구나 쓸 수 있지만 메모리는 각 기업의 경쟁력이므로’, 올바른 메모리 관리와 프로모션 전략이 AI 활용의 핵심이라는 메시지로 마무리**
- **마지막으로 GitHub 저장소와 유튜브 채널에 다양한 실습 자료와 튜토리얼이 마련되어 있음을 언급함**

## 세부 요약 - 주제별 정리

### 10년간 금융 및 클라우드 AI 프로젝트 경험이 발표의 실질적 토대를 제공함

- Wojciech Pluta는 Oracle에서 10년간 근무하며 다양한 프로젝트(고객 경험, 모기지 사례, 얼리 컨택리스 결제, 오픈 뱅킹 등)를 수행
- 영국 은행과의 협업 등 실제 금융 산업 내 AI 및 시스템 구축 경험을 쌓음
- Oracle AI 데이터베이스 기술 마케팅 팀을 이끌고 있으며, 클라우드 네이티브/AI 인프라 경험도 보유
- 이러한 현장 경험을 바탕으로 발표가 시작됨

### 인터페이스 발전과 AI 시대의 데이터 레이어 중요성이 강조됨

- 과거에는 명령 기반, 클릭&입력 방식에서 현재처럼 '의도 기반(intent-based)' 시스템으로 발전
- 이 변화는 '온디맨드', '저스트 인 타임' 소프트웨어의 가능성을 열었음
- AI 스택에서 인프라와 모델 레이어는 점차 범용화(commoditized)되고 경쟁우위는 데이터에 있다고 역설
- 오라클도 모델+하니스 구조를 채택: 모델은 상대적으로 정적이나, 하니스(코드)가 실행·결정 권한을 가짐

### 랙(rack) 시스템의 리트리벌과 메모리 시스템의 프로모션 차별점 설명

- 랙 시스템은 ‘회화적 상태’만을 보존(리트리벌 - 읽기)
- 메모리(쓰기)는 에이전트가 '영속적으로 남길 가치가 있는 정보'를 선별함
- 단순 검색(retrieval)로는 보존할 정보를 결정할 수 없음
- ‘무엇을 남길지(promote)'를 결정하는 설계가 매우 중요함

### 메모리 프로모션 파이프라인을 통한 프로세스 소개

- 단계1: 후보(대화 내용 등)의 의미 분류
- 단계2: 기존 저장된 레코드와의 비교 및 증거 요건 검증
- 단계3: 하니스가 승인을 할지, 거부할지, 또는 휴먼 리뷰로 보낼지 결정
- 각 단계별로 명확한 책임/룰이 존재

### 실시간 데모로 금융 서비스 시나리오와 메모리 결정 플로우를 구체적 예로 설명

- Kyle과 Vincent라는 가상의 고객 어플리케이션 예시
- Kyle의 모기지 신청에서 누락된 서류가 있는 상황을 AI가 분석, 해당 내용을 구조화해 응답
- 사용자의 ‘정중함’을 감지(예: ‘please’ 사용)해, 더 양호한 응답이나 추가 혜택(여분의 쉼표) 제공
- 허니스가 결정 모델(예: 'Jeff')과 연동되어 판단 및 데이터베이스 저장
- 새로운 세션을 개시해도(컨텍스트 완전 초기화) 이전에 저장한 semantic preference가 보존되어 즉시 재활용 가능함
- Vincent의 경우, 다른 상황 및 서류 정보가 분리 저장·조회됨을 확인
- “모든 신청 승인”과 같은 위험한 blanket rule에 대해서는 guardrail로 승인을 차단
- 조직/팀에 공유할 기억은 휴먼 승인 후 enterprise-wide memory store로 확장 가능

### 메모리 프로모션 시 가드레일 및 공유 범위 설정이 핵심임을 강조

- 위험하거나 허용 불가한 내용을 메모리에 영구 저장하는 사고를 guardrail로 방지
- 조직 내 중요한 기억(knowledge, 사례 등)을 단일 개인이 아니라 팀/기업 단위에서 공유할 수 있도록 인간 승인 워크플로 도입
- 이는 무분별한 기억 저장을 막으면서도, 핵심 지식은 장기적으로 전사 공유가 가능하도록 설계

### 에이전트 메모리는 단일 구조가 아닌 다층적 구조로 바라보아야 함

- 단기 메모리: 세션 단위 대화 내용으로, 세션 종료 시 소멸
- 장기 메모리: 에피소드, 프로시저, 시맨틱, 툴박스, 지식 등 유형별로 분류·저장
- 공유 메모리: 장기 기억 중 조직 내 공유가 적절한 것은 엔터프라이즈 스토어로 격상
- 기억 보존 기준과 supersede(기존 기록 대체) 정책의 명확성 필요함을 시사

### robust한 메모리 저장을 위해 데이터베이스와 스키마, 인덱스 등 실무 요건이 필수임을 강조

- 가장 안정적이고 확장 가능한 메모리 저장은 데이터베이스 기반
- ACID 보장, 멀티라이터, 파일 트리 문제 해결, search 확장성 제공
- 레코드 타입 구분 스키마, 리트리벌 목적에 맞는 인덱스, 라이프사이클 및 권한 관리 필요
- 오라클은 이러한 구조를 지원하는 agent memory 패키지를 2024년 초부터 제공

### 에이전트 메모리 패키지의 context card로 개발·관리 복잡성을 대폭 낮춤

- 로직상 한 줄 코드로 context 추출·조립 가능
- context card: topic, summaries, relevant info, 최근 메시지 등으로 구성
- 하니스가 매 턴마다 어떤 기억이 중요한지 선택·조립하여 에이전트에 전달
- 개발자가 토큰 예산, 요약, 추출, 결합, 리트리벌 등에서 직접 부담하는 작업을 크게 절감

### 최신 릴리즈에서 보안, 확장성, 다양한 데이터 타입 지원이 대폭 강화됨

- end-user isolation(엔드유저 별 철저한 경계) 기능 강화
- 이미지, 벡터, 일반 문서 등 다양한 데이터 타입을 하나의 멀티 데이터 엔진으로 다룸
- 별도의 벡터스토어나 다중 데이터베이스 운영 필요성이 대폭 감소
- 포스트 프로세싱, 이벤트 리스팅 등 부가 기능 추가
- context blow(과도한 맥락 발생) 방지를 위해 최신 구조로 최적화

### 모델은 누구나 공유하지만, 메모리는 각 기업에 특화된 경쟁력임을 재차 강조하며 발표를 마무리함

- 모델은 범용적이나 데이터 및 기억은 각 기업의 고유 자산이라고 주장
- 올바른 메모리 관리·프롬션 정책이 경쟁력 창출의 핵심임을 재확인
- 실습 자료, 하이브리드 리트리벌 등 실제 적용 가능한 노트북과 Tutor 자료가 GitHub 및 오라클 유튜브에 마련되어 있음
- 다양한 활용 예시와 상세한 설명 시리즈가 채널에 있으니 참고를 권함
