## *AI 에이전트에게 코드 병합은 맡기지만 프로덕션 배포는 직접 검토한다* 핵심 요약

- 영상의 주제는 AI 에이전트가 밤새 코드 병합을 자동으로 처리할 수는 있어도, 프로덕션 배포 단계까지는 인간의 직접 검토가 반드시 필요하다는 점에 초점을 맞춤
- AI 소프트웨어 팩토리는 스테이징 환경까지 자동화하지만, 실제 배포 전 최종 검토는 인간이 직접 진행함
- AI 에이전트에 의해 수행되는 테스트와 리뷰는 코드가 '겉으로는' 올바른 것처럼 보인다는 것만 확인할 수 있음
- 실사용자 앞에 기능이 실제로 노출될 때만이 코드 변경의 진짜 영향을 알 수 있기 때문에 신중해야 함
- 수년 전부터 기능 플래그(feature flag)를 통해 변경 사항을 제한된 사용자에게만 배포, 문제가 있으면 즉시 롤백하는 방법이 효과적이라는 것이 이미 알려져 있었음
- 하지만 기존에는 엔지니어가 직접 기능 플래그를 추가해야 했고, 규모가 커질수록 PR(풀 리퀘스트) 관리에 어려움이 있었음
- Launch Darkly라는 서비스는 프로덕션에서 변경 사항을 세밀하게 제어할 수 있는 기능을 제공함
- Launch Darkly의 '릴리즈 오토파일럿(Release Autopilot)'을 통해 AI 에이전트가 기능 플래그 작업까지 자동으로 수행
- 위험도 분류, 성공 지표 설정, 카나리 배포, 실시간 모니터링, 플래그 정리 등 릴리즈 단계 전체를 자동으로 관리함
- 각 변경 사항은 여전히 PR에서 검토자 승인이 이루어지며, 실제 적용 전에는 사람이 한 차례 직접 결정을 내릴 수 있음

## 세부 요약 - 주제별 정리

### AI 에이전트는 코드 병합 자동화에는 적합하지만 최종 프로덕션 배포에는 신뢰가 제한적임

- 영상 제작자는 자신의 AI 에이전트(AI agents)가 밤새 코드 병합을 수행하도록 신뢰하고 있음
- 그러나 AI 에이전트에게 코드의 프로덕션(실서비스 환경) 직접 배포까지 맡기지는 않음
- 이유는 AI가 처리하는 테스트 결과와 리뷰만으로는 코드 품질을 전적으로 보장할 수 없기 때문임
- 실제 코드 변경이 실사용자 환경에 적용된 후 발생할 수 있는 예기치 않은 문제가 우려됨

### AI 소프트웨어 팩토리는 스테이징 환경까지만 자동화하고 프로덕션 직전에서 인간 검토를 추가함

- AI 소프트웨어 공장은 스테이징 환경까지 변경 사항을 자동으로 반영함
- 이는 개발·테스트 과정에서는 자동화를 적극적으로 활용하지만, 실제 서비스 배포 시에는 추가적인 신뢰 장치가 필요함을 의미함
- 제작자는 "내가 직접 검토한다"는 원칙을 강조함

### 테스트와 리뷰 자동화는 코드의 외형적 정상만을 확인해줄 뿐 실효성까지 보장하지 못함

- AI 에이전트가 실행하는 각종 테스트와 리뷰는 코드가 '맞아 보인다'는 수준을 확인함
- 실제 변경의 효과(실제 영향)는 현업에서 실 사용자 앞에 릴리즈된 후에야 명확히 파악 가능함
- 즉, 테스트만으로는 실제 배포에 따른 모든 상황을 고려할 수 없음

### 기능 플래그는 변경 사항 배포의 위험을 통제하는 오래된 해법이었으나 확산에는 어려움이 있었음

- 기능 플래그(Feature Flag)를 뒤에 두고 변경사항을 일부분 사용자에게만 점진적으로 배포하는 해법이 예전부터 존재함
- 문제가 생기면 바로 해당 기능을 끌 수 있다는 장점이 있음
- 그러나 이 기능 플래그 추가는 매번 엔지니어가 수작업으로 작성해야 해 번거로웠고,
- 많은 팀들이 이 과정을 완전하게 실현하지 못함
- 대규모 PR이 생성되는 환경에서는 기능 플래그 관리가 거의 불가능해짐

### Launch Darkly는 프로덕션 변경의 행위를 세밀하게 통제할 수 있도록 지원함

- Launch Darkly는 변경 사항이 실제 프로덕션 환경에 릴리즈되는 방식을 제어할 수 있는 서비스를 제공
- 실서비스 환경에서의 기능 제어 및 실시간 모니터링 등이 주요 기능임

### Launch Darkly의 '릴리즈 오토파일럿'은 기능 플래그 작업까지 AI 에이전트가 자동화하도록 함

- 최근 출시된 '릴리즈 오토파일럿(Release Autopilot)' 기능에 주목
- 이 기능을 사용하면 AI 에이전트가 자동으로 기능 플래그 관련 작업을 수행함
- 일일이 엔지니어가 플래그를 다는 번거로움이 사라짐
- 대규모 변경 및 자동 PR 생성 시에도 플래그 관리가 일관되고 수월해짐

### 자동화 프로세스는 위험도 평가, 성공 지표 설정 등 체계적으로 이루어짐

- 위험 분류(Risk Classification): 변경의 위험도를 평가하여 플래그 적용 여부 결정
- 성공 지표(Success Metrics) 설정: 해당 기능이 프로덕션에서 어떻게 동작해야 하는지 기준을 설정
- 자동 릴리즈 플랜: 카나리 배포(Canary Release)로 일부 사용자에게만 점진적으로 변경을 적용
- 변화가 설정된 가드레일(Guard Rails)을 벗어나지 않는 한 점진적으로 대상을 확대함
- 실시간 성능 측정 및 모니터링 수행

### 실시간 관찰 및 자동 플래그 정리로 코드베이스 유지보수가 수월해짐

- 기능 수준의 가시성(Feature Level Observability) 제공: 각각의 변경사항을 라이브 프로덕션 신호와 실시간 비교
- 플래그 정리(Flag Cleanup): 프로젝트 내에 남아있는 오래된 플래그 항목을 평가 및 자동 삭제하여 코드베이스를 정리
- 자동화로 인한 코드 관리 효율성 증가

### 최종 승인 과정은 여전히 인간 개발자의 통제 하에 이루어짐

- 모든 플래그 작업과 변경 제안은 Pull Request(PR) 단계에서 명확하게 제시됨
- 실제 변경사항 반영 및 프로덕션 릴리즈는 인간 개발자의 최종 승인 없이는 진행되지 않음
- "완전 자동 운영이 아니므로, AI 에이전트를 추가적으로 신뢰할 필요가 없다"는 점을 강조
- 실사용자에게 실제 적용 전, 모든 변경사항은 사람이 한번 더 확인 가능

### AI 자동화와 엔지니어의 최종 승인 결합이 안전하고 확장성 있는 소프트웨어 배포를 가능하게 함

- 자동화된 에이전트와 인간의 직접적인 검토, 승인 절차의 조화가 핵심임
- 팀이 적은 부담으로 많은 배포 작업을 효율적으로 수행할 수 있도록 도와줌
- 영상 마지막에 Launch Darkly와의 협업에 감사하며, 서비스 링크가 설명란에 있음을 언급
