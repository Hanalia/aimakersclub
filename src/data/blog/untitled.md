## *프롬프트 인젝션은 AI 에이전트 보안의 시작일 뿐이다 (당신에게 필요한 것들)* 핵심 요약

- 영상은 ‘두 번째 두뇌’(Second Brain)라는 자동화 시스템을 통해 다양한 업무를 관리하면서 AI 에이전트에 시스템과 데이터 접근권을 부여하는 보안 위험을 강조함
- 프롬프트 인젝션(명령 주입) 공격이 현실적 위협임을 언급하며, 외부 데이터가 AI에게 예기치 않은 지시를 내릴 수 있음을 설명
- 이를 막기 위해 필자는 모델 입력 전 다양한 보안 검사와 접근 제어(필요한 리소스만 제한적으로 접근 가능)를 구축했다고 밝힘
- 개인 프로젝트에서는 에이전트를 직접 개발했기에 보안 통제가 용이하지만, 기업 환경에서는 수많은 에이전트가 클라우드 및 직원 디바이스에서 동작해 관리가 어렵다고 지적
- IT 부서는 ‘에이전트의 목록, 소유자, 실제 접근 범위’를 파악해야 하며, 기존 보안 관리 체계에 한계가 있음
- 마이크로소프트는 Agent 365 및 Project Perception 등으로 이 문제를 해결하려 시도하고 있음
- Project Perception은 각 AI 에이전트에 별도의 신원을 부여하고, 권한을 과업별로 세분/제한하여 위험 변화에 따라 유연하게 통제함
- 동적 에이전트 권한‧리스크 기반 접근 통제, Guardian 에이전트 지원, 권한 변경 미리보기 및 점진적 적용 등 구체적 도구와 절차를 소개
- 이러한 시스템이 직원 권한과 분리되어 보안 영향을 최소화하며, 기존 통제의 취약점도 시각화함
- 영상자는 현재 한 명의 에이전트에 이를 적용했으나, 마이크로소프트와 함께 수백 개 에이전트에 대해 확장 가능함을 강조

## 세부 요약 - 주제별 정리

### AI 에이전트에게 시스템 및 데이터 접근 권한 부여가 근본적인 보안 과제가 됨

- 영상자는 최근 다양한 업무 자동화를 위해 ‘두 번째 두뇌’ 시스템을 활용하고 있다고 밝힘
- 이 AI 에이전트 시스템에 조직 내 여러 데이터와 시스템에 대한 접근 권한을 할당함
- 광범위한 접근 권한을 부여할 때, 예상치 못한 위험 및 보안 침해 가능성이 크게 증가함
- 특히 외부 데이터와 상호작용하는 에이전트의 경우 잠재적 공격 경로가 늘어난다는 점을 지적

### 프롬프트 인젝션(명령 주입) 공격은 AI 에이전트 관리에서 항상 고려해야 할 요소임

- 프롬프트 인젝션(Prompt Injection)이 AI 보안의 중요한 위협임을 강조
- 외부 데이터가 AI 에이전트의 입력값으로 들어올 때, 악의적 명령이 전달될 수 있다고 설명
- 에이전트가 의도치 않게, 사용자가 지시하지 않은 행동(예: 정보 유출, 권한 남용)을 하도록 유도될 수 있음
- 영상자는 이런 이유로 모든 외부 입력을 LLM에 전달하기 전 엄격하게 필터링 및 검사함

### 맞춤형 보안 검사와 최소 권한 원칙 적용으로 프롬프트 인젝션 리스크를 선제적으로 관리함

- 영상자는 자신의 ‘두 번째 두뇌’ 시스템에 다양한 보안 점검 과정을 추가함
- 모든 입력을 대형 언어 모델(LLM)에 전달하기 전 사전 검사 절차를 구축
- 에이전트가 실제로 필요한 시스템과 데이터에만 제한적으로 접근하도록 최소 권한 원칙을 적용
- 이로써 예상하지 못한 행동이나 명령 실행을 사전에 차단

### 개인 개발 환경에서는 직접 통제가 가능하지만, 기업 규모에서는 복잡성이 급격히 증가함

- 개인적 프로젝트에서는 자신이 직접 에이전트를 개발, 관리하기 때문에 보안 설정과 접근 통제가 용이함
- 그러나 기업에서는 수십, 수백 개의 에이전트가 클라우드와 임직원의 로컬 디바이스에서 운용됨
- 모든 에이전트의 목록, 소유자, 접근 권한, 동작 현황 등 파악이 어려워짐
- 기업 IT 부서는 보안상 각 에이전트가 어디에 있고, 누가 소유하며, 어떤 데이터에 접근 가능한지 지속적으로 감시해야 함

### 마이크로소프트는 ‘Agent 365’와 ‘Project Perception’으로 AI 에이전트 보안 이슈를 구조적으로 해결하려 함

- 마이크로소프트는 ‘Agent 365’ 및 ‘Project Perception’ 등의 서비스를 통해 에이전트 관리 문제를 해결하고자 함
- 이 접근 방식은 기존의 사용자 기반 보안 제어에서 에이전트(소프트웨어) 단위의 신원 및 권한 관리 체계로 전환함
- ‘Project Perception’은 에이전트별로 독립적인 신분 증명(Identity)을 부여하여 추적이 용이하도록 설계됨

### 각 에이전트가 별도의 신원과 과업별/시간제한 권한을 가지게 하여 접근 통제의 유연성과 안전성이 증대됨

- AI 에이전트는 각각 별도의 신원을 부여받아, 누가 어떤 작업을 수행하는지 추적 가능함
- 각 과업(Task) 단위로 접근 권한이 정의되어, 과업 수행 중에만 필요한 자원에 접근하도록 제한됨
- 동적으로 접근 권한의 범위와 기간을 설정할 수 있어, 불필요한 장기 권한 부여를 방지
- 이는 회사 직원의 고유 권한 구조와 분리되어, 조직 내 권한 충돌 또는 오용 가능성을 줄임

### Project Perception이 제공하는 에이전트 가시성과 취약점 진단 기능이 조직 전체 보안 상태를 시각화함

- Project Perception 내 ‘에이전트 인사이트(Agent Insights)’ 기능을 통해 현재의 보안 제어로 인해 발생하는 취약점을 쉽게 파악할 수 있음
- 기존에 간과했던 에이전트별 접근 통제의 허점과 보안 정책 미비점을 한눈에 볼 수 있도록 지원함
- 이를 통해 조직 내 수많은 에이전트의 리스크 수준과 취약 에이전트 목록을 실시간으로 모니터링 가능함

### Guardian 에이전트가 팀 단위로 집단적 위험 관리와 지원을 수행함

- Project Perception은 ‘Guardian Agents’라는 별도 보조 에이전트를 활용
- Guardian 에이전트는 단일 에이전트가 아닌, 조직 전반에 분포한 여러 에이전트를 조율하며, 보안 이슈와 위험을 효과적으로 통합 관리함
- 개별 사고 케이스마다 일일이 조사하는 대신, 조직 전체 혹은 팀 단위로 빠르게 위험에 대응 가능함

### 동적 권한과 위험 기반 접근 제어가 실시간으로 에이전트 행동을 평가하고 위험을 줄임

- Project Perception의 동적 권한 시스템은 에이전트가 실제로 필요한 시간과 목적에만 접근할 수 있도록 실시간 권한 부여
- 위험 기반 접근제어(Risk-Based Access Control)는 에이전트의 행동을 지속적으로 평가, 리스크가 높아질 경우 권한 제어 강화
- 이 시스템은 전통적 로그인/인증 단계에만 의존하지 않고, 작업 수행 중에도 지속적으로 보안 평가가 적용됨

### IT팀은 보안 정책 미리보기, 점진적 배포 등을 통해 안전한 도입과 운영을 지원받음

- IT 부서는 마이크로소프트 솔루션 내에서 추천 보호 정책(Protections)을 미리 검토할 수 있음
- 정책 적용 시 예상되는 영향도(impact)를 사전에 시뮬레이션하며, 실제 적용 여부를 점진적으로 업데이트 가능함
- 공식 시행 전 단계적 도입 및 승인 절차를 통해 보안 사고 위험을 최소화함

### 마이크로소프트와의 협업으로 한 에이전트 기반 보안에서 수백 개 에이전트 규모로 관리 능력을 확장할 수 있게 됨

- 영상자(제작자)는 현재 한 명의 에이전트 관리에 대해 마이크로소프트와 협업하여 백여 개, 혹은 그 이상의 에이전트로 확장 가능한 체계를 구축
- 영상 마무리에서 마이크로소프트의 기술적 지원과 협력에 대한 감사를 표함
- 기업은 개인 프로젝트에 비해 수백 개의 AI 에이전트에 역동적이고 체계적인 보안 및 권한 관리가 필수임을 우회적으로 강조함
