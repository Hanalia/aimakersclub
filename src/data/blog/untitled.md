## *코딩 에이전트에게 치명적인 사각지대가 있음을 반드시 해결해야 한다* 핵심 요약

- 영상 제목은 “코딩 에이전트에게 치명적인 사각지대가 있음을 반드시 해결해야 한다”로 번역될 수 있음
- 제작자는 실제 프로덕션 환경에서 AI 코딩 에이전트가 여러 번 실패한 경험을 공유함
- 대부분의 실패 원인은 에이전트의 “사각지대”, 즉 실행 중 발생하는 실제 문제를 보지 못하는 데 있음
- 최근 본인의 이메일 초안 생성용 에이전트에서 심각한 문제를 발견
- 정상적인 평가(evals)를 모두 통과한 에이전트가 실제 프로덕션에서는 미답변 이메일을 무시함
- 문제는 충돌이나 오류가 아닌, 실행 중 발생한 기대하지 않은 동작이었으며 코드만으로는 원인을 알 수 없었음
- 본인은 실제 실행 로그를 직접 관찰해 문제를 7분 만에 수정함
- Dinatrace MCP 서버가 이 문제 해결에 유용하다고 소개
- Dinatrace는 실제 프로덕션 데이터를 IDE의 에이전트에 연결해 실행 상태를 실시간 피드백으로 제공함
- 실제 예시로, 느린 응답(89초)을 보이는 앱에서 에이전트가 주요 DB 부하 메서드 TOP 5를 실제 데이터 기반으로 정확히 추적함
- 최종 조치로는 인덱스 추가와 같이 실질적 조치가 가능해짐
- 영상은 반드시 코딩 에이전트에 “실행 중 피드백”을 제공할 장치를 넣어야 한다고 강조함

## 세부 요약 - 주제별 정리

### AI 코딩 에이전트의 실패 경험은 주로 “실행 중 동작을 관찰하지 못함”에서 비롯됨

- 제작자는 프로덕션 환경에서 코딩 에이전트가 여러 번 예기치 않게 동작하거나 실패하는 사례를 목격함
- 실패는 때로는 상당히 당황스러운 방식으로 나타나기도 했음
- 거의 모든 경우, 에이전트의 사각지대 – 즉 “실행 중 코드를 현실적으로 평가하지 못함” – 이 원인으로 작용함

### 이메일 초안 작성 에이전트에서 드러난 치명적 문제 사례

- 최근 본인의 “이메일 초안을 작성하는 에이전트”의 새 버전을 출시함
- 해당 에이전트는 자신의 “AI 세컨드 브레인”의 일부로 도입함
- 개발과정에서 작성한 자체 평가(evals)를 모두 무난히 통과함
- 그러나 프로덕션에서의 첫 실제 동작 시, 아직 답변하지 않은 이메일 2개를 감지했음에도 불구하고 조치를 취하지 않음
- 에이전트는 툴(도구)를 한 번도 호출하지 않고, 처리할 것이 없다고 결과를 보고함

### 오류나 충돌 없이도 실제 문제는 충분히 발생할 수 있음을 강조함

- 이 상황은 일반적인 충돌(crash)이나 코드 에러(error)가 전혀 발생하지 않았음
- 코드베이스만 읽어서는 명확한 원인이나 단서를 찾기 어려웠음
- 실제 코드 실행 상황을 외부에서 관찰하지 않았다면, 해당 문제는 쉽게 발견할 수 없었음

### 제작자가 직접 실행 상황을 관찰해 빠른 수정에 성공함

- 문제를 발견한 계기는 에이전트의 실제 실행 과정을 제작자가 “직접 관찰”했기 때문임
- 이 과정을 통해 문제 원인을 즉각 식별했고, 해결까지 7분 정도밖에 소요되지 않았음
- 해당 경험은 코딩 에이전트에게 실행 상태에 대한 피드백이 얼마나 중요한지 보여줌

### 에이전트가 소스 코드를 읽을 수 있어도 ‘실행 중 데이터’가 없으면 본질적 문제는 감지 불가

- AI 코딩 에이전트는 전체 코드베이스를 읽을 수 있는 능력을 가지고 있음
- 하지만, 실제로 실행하는 동안 코드가 어떤 행동(상태, 결과 등)을 보이는지 알지 못함
- 실행 중 관찰 데이터, 즉 “테이블이 정말로 어떻게 사용되는가” 등의 정보 없이는 진짜 병목이나 문제를 짚어낼 수 없음

### Dinatrace MCP 서버는 실행 데이터와 코드베이스를 연결해 사각지대를 메움

- Dinatrace에서는 이러한 실행-관찰 문제를 해결하는 방식을 제시함
- Dinatrace MCP 서버는 프로덕션 환경의 실제 실행 데이터를 IDE와 에이전트로 직접 불러옴
- 이를 통해 개발자는 코드만이 아니라 “실제 작동하는 프로그램의 상태”를 실시간으로 확인할 수 있게 됨

### 실제 예시: 앱의 느린 응답 시간 문제를 Dinatrace가 정확히 파악·해결함

- 예시에서는 한 앱에서 응답 시간이 약 89초에 달하는 현상을 관찰
- 에이전트에 “DB를 가장 많이 부하시키는 메서드 TOP 5”를 질의해봄
- 에이전트는 실시간 수집된 텔레메트리 데이터로 가장 중요한 병목 메서드들을 순위별로 제시함

### 에이전트가 코드와 실행 데이터를 모두 파악해 근본적 수정 제안을 도출함

- 같은 에이전트가 그 병목 메서드의 소스 코드도 직접 읽을 수 있음
- 앱의 실제 성능 저하 원인을 “특정 검색 쿼리가 매번 테이블의 모든 행을 읽음”으로 정확히 짚음
- 일반적으로 코드를 보는 입장에선 문제가 없어 보이는 단순 쿼리였으나, 실제 실행 지표가 원인을 명확히 보여줌
- Dinatrace의 제안은 “인덱스 추가”로, 앱 코드 자체의 수정 없이도 성능 개선 가능함

### 실행 진단 데이터 없이는 실제 병목 원인을 파악할 수 없음을 강조함

- “코드만” 보면 단순한 검색 쿼리로 인식하고 병목을 캐치하지 못함
- 실제 실행시 나오는 숫자(telemetry, 예: CPU 소모, 응답 시간 등)가 있어야 진짜 병목 지점 식별 가능
- 수행 중수집 데이터가 없으면 코딩 에이전트는 여전히 주요 문제를 짚지 못함

### 어떤 도구를 쓰더라도 반드시 코딩 에이전트에 “실행 중 피드백”을 제공해야 함

- 도구(Dynatrace 등)의 종류와 무관하게, 코딩 에이전트가 “코드의 실제 실행 상태”를 확인할 방법을 확보하는 것이 중요함
- 이를 통해 실제로 사용자에게 발생하는 문제를 조기에 파악하고, 근본적인 솔루션과 접목이 가능함
- 영상 제작자는 본 영상이 Dinatrace의 후원임을 명확히 밝혔으며, 추가 자료는 설명란에 있다고 안내함
