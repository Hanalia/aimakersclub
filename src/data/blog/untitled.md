## *코딩 에이전트가 가진 치명적인 맹점과 이를 해결하는 방법* 핵심 요약

- 영상 제목: *코딩 에이전트가 가진 치명적인 맹점과 이를 해결하는 방법*
- 제작자는 실무에서 코딩 에이전트가 수십 차례 실패한 경험을 언급하며, 대부분 ‘맹점(blind spot)’이 원인임을 강조
- 최근 제작한 이메일 초안 작성 코딩 에이전트가 배포 즉시 아무 작업도 하지 않는 오류가 발생함
- 해당 에이전트는 정상적으로 평가를 통과했으나, 실제 배포 환경에서 미응답 이메일을 무시하고 “처리 필요 없음”으로 잘못 판단함
- 코드상 버그나 크래시 없이 눈에 잘 보이지 않는 문제라, 실제 실행 과정을 관찰해서만 원인을 파악하고 7분 만에 수정함
- 이런 사례는 코딩 에이전트가 코드베이스는 잘 읽지만, 실제 ‘실행 중인 동작’을 관찰할 수 없다는 한계를 명확히 보여줌
- Dinatrace의 MCP 서버를 사용하면 실서비스 데이터(프로덕션 데이터)를 IDE 안에서 코딩 에이전트가 관찰할 수 있도록 해줌
- 예시로, 응답 시간이 비정상적으로 긴(약 89초) 앱을 대상으로, 실제 모니터링 데이터를 바탕으로 문제 원인을 추적
- 에이전트는 디비 쿼리 효율이 낮은 실제 코드를 집어서 인덱싱(코드 수정 없이 DB 최적화) 개선안을 제시함
- 최종적으로, 코딩 에이전트에게 반드시 ‘실행 중인 코드의 거동’을 보여줄 방법을 제공할 필요가 있음을 강조

## 세부 요약 - 주제별 정리

### 실무에서 반복적으로 발생하는 코딩 에이전트의 실패 경험이 문제의식을 확산시킴

- 제작자는 자신의 코딩 에이전트가 실무 환경에서 수십 번이나 실패했던 경험을 솔직하게 고백함
- 이 실패들 중 상당수는 눈에 띄는 코드 오류나 치명적인 크래시가 아니라, 미묘하고 감지 어려운 맹점 때문에 발생했음
- 종종 이로 인해 매우 난감하고 부끄러운 상황을 겪었다고 언급

### 이메일 초안 코딩 에이전트의 실서비스 맹점이 실제 문제를 드러냄

- 한 달 전, 제작자는 이메일 초안을 자동으로 작성해주는 코딩 에이전트의 새 버전을 배포함
- 이 에이전트는 "AI 세컨드 브레인"의 일부로 설계
- 테스트(이벨) 상에서는 모든 항목을 통과함
- 하지만 실서비스 첫 실행에서 답변되지 않은 이메일 두 통을 확인하고도 일절 툴 호출 없이 "처리 필요 없음"이라고 잘못 판단
- 오류 메시지나 크래시가 아니라, 겉으로는 아무 문제 없어 보이는 비정상적 동작이었음
- 코드상으로도 맹점이 명확하게 드러나지 않아 원인 파악이 어려웠음

### 실제 운영 환경에서만 드러나는 맹점을 직접 관찰해 7분 만에 수정함

- 문제의 존재를 오직 실서비스 실행 과정을 ‘직접 보는 것’으로만 감지
- 실제로 실행 로그를 관찰하면서 상황을 파악, 원인을 신속히 확인
- 일단 문제를 포착한 후 코드를 7분 만에 고쳐 해결함

### 코딩 에이전트는 코드베이스는 볼 수 있지만, ‘런타임’ 정보에는 눈이 멂

- 에이전트가 소스코드 전체를 읽고 분석하는 능력은 충분함
- 하지만 코드가 실행됐을 때 ‘실제로 무엇을 하는지’, 즉 실제 프로덕션 거동까지는 관찰하지 못하는 구조적 한계가 있음
- 이 맹점 때문에 잘못된 판단, 미묘한 오류, 비효율 등이 숨어 발생할 수 있음

### Dinatrace MCP 서버는 실프로덕션 데이터를 IDE에 연동해 이 맹점을 해소함

- Dinatrace MCP 서버를 활용할 경우, 실서비스에서 얻은 운영 데이터(telemetry)가 IDE(개발 환경)로 바로 피드백됨
- 코딩 에이전트가 개발 환경에서 운영 중인 앱의 실시간 런타임 정보를 바로 확인 가능
- 이를 통해 기존에 볼 수 없던 실행 맥락, 성능 데이터 등도 코드와 융합해서 분석할 수 있게 됨

### 문제 앱 케이스 예시를 통해 실데이터 기반 분석 과정 시연

- 영상에서는 앱의 평균 응답 시간이 ‘89초’로 매우 비정상적으로 느린 사례가 제시됨
- 에이전트에게 데이터베이스에 가장 큰 부하를 주는 상위 5개 메서드를 질의
- 실서비스 프로덕션 텔레메트리 데이터를 활용, 실제 부하가 큰 메서드를 순위별로 응답
- 코딩 에이전트는 이들 메서드 분석을 통해 코드베이스 내 정확한 행(line)을 지적함

### 실서비스 데이터 없이는 감지되지 않을 쿼리 효율 저하를 정확히 진단함

- 예시에서, 검색 쿼리가 테이블의 모든 행을 반복 조회(풀스캔)함을 탐지
- 소스코드를 표면적으로 읽기만 하면 정상적인 쿼리로 보이지만, 실데이터에 근거한 CPU/성능 분석 결과 과도한 리소스 소모 확인
- 에이전트는 DB 인덱스 추가(애플리케이션 코드 변경 없이 DB만 개선)라는 구체적이고 적합한 해결 방안을 제안

### 실프로덕션 데이터가 없으면 코드의 맹점은 쉽게 발견되지 않음을 강조함

- 코드만 읽어서 찾을 수 없는 비효율 혹은 오류는 실제 런타임 데이터와 결합해야만 파악 가능
- 운영 환경에서의 실제 거동을 코드분석과 연계할 때만, 유의미한 개선과 실질적 오류 수정 가능
- 개발자와 코딩 에이전트 모두에게 실서비스 행동 데이터를 제공하는 것이 중요

### 자신이 사용하는 도구와 무관하게, 실행 중 코드의 작동상황을 AI가 ‘볼 수 있게’ 해야 함을 최종 강조

- Dinatrace 소프트웨어는 하나의 솔루션 예시에 불과하며, 어떤 툴이든 이런 정보 제공 기능이 필요
- 코딩 에이전트가 런타임에서 무슨 일이 일어나는지 ‘직접 볼 수’ 있도록 지원해야 제대로 된 자동화와 판단이 가능함
- 영상 말미에는 Dinatrace에 대한 감사와 함께 관련 자료 링크가 소개됨
