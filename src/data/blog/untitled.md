## *나는 AI 에이전트가 코드를 병합하는 것은 믿지만, 바로 프로덕션에 배포하는 것은 믿지 않는다* 핵심 요약

- AI 에이전트는 밤새 코드 병합(merge)을 맡길 만큼 신뢰하지만, 프로덕션 환경에 즉시 배포(deploy)는 신뢰하지 않는다.
- AI 소프트웨어 개발 공정은 스테이징 환경(staging environment)까지 진행되며, 그 이후부터는 직접 검토한다.
- 에이전트가 수행하는 테스트와 코드 리뷰는 코드가 ‘형식적으로’ 올바른지 여부만 나타낼 뿐, 실제 변화가 사용자에게 미치는 진짜 영향은 확인할 수 없다.
- 수년간의 해결책은 ‘피처 플래그(feature flag)’를 적용해 변경 사항을 소수 사용자에게만 공개, 위험 발생 시 즉시 비활성화한다는 것이었다.
- 그러나 이 방법은 엔지니어가 수동으로 플래그를 추가해야 했고, 많은 팀에서는 제대로 활용하지 못했다.
- AI 에이전트가 대규모로 PR(pull request)을 생성하는 환경에서는 기존 방식으로 플래그를 관리하기 어렵다.
- Launch Darkly(런치 다클리)는 실제 프로덕션에서 변경 사항의 동작을 제어할 수 있게 도와주는 도구다.
- 최근 추가된 ‘Release Autopilot’ 기능은 에이전트가 피처 플래그 작업까지 자동화할 수 있도록 지원한다.
- 위험 분류, 성공 지표 설정, 카나리 릴리스, 실시간 관측, 플래그 정리 등 단계별 관리가 자동으로 이뤄진다.
- 최종 적용 전 사람의 승인이 필요해, 에이전트를 과도하게 신뢰할 필요 없이 변경 사항이 실제 사용자에게 문제없이 적용되는지 검증할 수 있다.

## 세부 요약 - 주제별 정리

### AI 에이전트는 코드 병합까지 신뢰할 수 있지만 프로덕션 배포까지는 제한된다

- AI 에이전트(agents)는 코드 작성과 병합 작업을 자동으로 밤새 실행할 수 있다.
- 하지만 영상 제작자는 이러한 에이전트가 코드 변경을 직접 프로덕션 환경(미리 보지 않은 실제 사용자 환경)으로 즉시 배포하는 것은 신뢰하지 않는다.
- 이유는 코드 테스트 및 리뷰 결과가 본질적으로 “코드가 겉보기에는 올바르다”는 정도의 신호만 주기 때문임을 설명한다.
- 실제 코드 변경의 실질적 영향(버그나 비즈니스 문제)은 실사용자 앞에 적용되기 전에는 알 수가 없다.

### 피처 플래그는 소규모 대상에만 변경을 노출하고 즉시 차단할 수 있어 효과적인 안전 장치였다

- 과거부터 알려진 방법은 변경 사항을 ‘피처 플래그’로 감싸고, 제한된 소수 사용자에게만 노출해 문제가 있으면 빠르게 바꿀 수 있도록 하는 것이다.
- 피처 플래그 방식은 문제 발생 시 플래그를 끄는 것만으로 전체 사용자에 대한 영향을 즉시 차단할 수 있다.
- 이 전략은 위험성을 효율적으로 통제할 수 있게 해주므로 수년간 대안으로 인식되었음이 언급된다.

### 피처 플래그를 수동으로 추가하는 번거로움 때문에 팀들이 완전히 활용하지 못했다

- 그러나 피처 플래그는 엔지니어가 수작업으로 변경점마다 일일이 코드에 추가해야 한다.
- 이 과정의 추가 업무로 인해 실제로는 많은 팀이 피처 플래그 전략을 지속적으로 도입하지 못했다.
- 특히 AI 에이전트가 ‘대규모로 자동 PR’을 개설하고 있는 상황에서는 이러한 수동 관리가 더더욱 비현실적이다.

### Launch Darkly는 프로덕션 단계에서 변경 행동을 실시간으로 제어할 수 있게 해주는 툴임을 강조했다

- Launch Darkly는 코드가 실제 프로덕션에 반영된 이후에도 변경 사항의 동작을 정밀하게 실시간 제어할 수 있는 솔루션이다.
- 이 도구를 활용하면 문제 발생 시 즉각적으로 피처 플래그를 컨트롤하여 위험한 변경의 영향을 최소화할 수 있다.

### ‘Release Autopilot’은 피처 플래그 자동화를 통해 에이전트 작업을 손쉽게 관리하게 한다

- Launch Darkly에서 최근 새롭게 발표한 ‘Release Autopilot’ 기능은 AI 에이전트가 PR 생성 시 피처 플래그 생성 및 관리 업무까지 함께 수행한다.
- 즉, 에이전트가 단순히 코드를 병합할 뿐만 아니라, 변경 사항을 피처 플래그로 자동 감싸고 이에 대한 후속 관리 절차를 자동화한다.

### 위험 분류와 피처 플래그 여부, 성공 지표 설정이 단계적으로 자동 관리된다

- Release Autopilot 기능은 변경의 위험도를 분석하여, 플래그가 필요한 수정인지 자동으로 구분한다(위험 분류).
- 또한 해당 변경이 성공적으로 적용됐는지를 평가하는 생산 환경용 성공 지표를 직접 설정하게 한다.
- 이러한 과정을 통해 코드의 배포와 관련된 기준이 명확하게 정해진다.

### 변경 사항은 점진적(카나리) 배포를 통해 위험을 통제하며 자동으로 확대된다

- 자동 릴리스 플랜이 수립되어, 먼저 일부 소수 사용자에게만 변경사항(카나리 릴리스)이 시범 적용된다.
- 변경의 효과가 미리 설정한 임계치(guard rails) 내에서 안전하게 동작할 때만 대상 사용자가 점진적으로 확대된다.
- 이런 방식으로 대규모 장애나 위험을 미연에 방지할 수 있다.

### 실시간 피처 레벨 관측과 코드베이스 내 피처 플래그 정리가 자동으로 이루어진다

- 변경사항은 실제 프로덕션 환경에서 실시간 관측(오브저버빌리티, observability)을 통해 모니터링된다.
- 플래그 정리(flag cleanup) 기능은 오래된 플래그를 평가하여 코드베이스에서 자동 정리한다.
- 이로 인해 코드의 품질과 유지보수성이 높아진다.

### 승인 프로세스를 통해 최종 변경 전 사람의 통제를 보장한다

- 모든 플래그 작업과 변경사항은 PR(풀 리퀘스트)에 제안 상태로 남아있으며, 실제 프로덕션 반영 전 반드시 사람에 의한 승인이 필요하다.
- 팀원 또는 관리자의 승인이 있어야만 변경이 최종적으로 적용된다.
- 따라서 에이전트를 더 신뢰하지 않아도 모든 중요한 변경에 대해 사람이 개입할 수 있다.

### 실제 사용자 기준의 검증 이후에만 전체 릴리스가 이루어진다

- 릴리스 적용 전에는 실제 사용자 그룹 대상으로만 검증 및 성능 확인이 완료되어야 전체 출시가 이루어진다.
- 모든 변경 내역이 실사용자 기준에서 충분히 체크된 후에만 모든 사용자에게 확장된다.

### 제작자는 Launch Darkly와의 협업에 감사 인사를 전하며 관련 링크를 제공했다

- 영상 마지막에는 Launch Darkly와의 협업에 대한 고마움을 표했다.
- 해당 서비스의 링크를 영상 설명란에 첨부함을 언급했다.
