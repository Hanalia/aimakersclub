## *나는 AI 에이전트가 코드를 병합하도록 신뢰하지만 프로덕션 반영까지는 맡기지 않는다* 핵심 요약

- 영상에서는 AI 에이전트가 코드 병합을 자동화할 수 있지만, 최종 프로덕션 반영(실사용자 배포)까지 완전히 신뢰하지 않는 이유를 설명함
- AI 소프트웨어 팩토리의 자동화는 스테이징(사전 테스트) 환경까지만 이뤄지며, 실제 서비스 반영 전에는 사람이 직접 검토함
- 테스트와 리뷰 자동화는 코드의 외형상 정확성만 확인할 뿐, 실제 유저 환경에서 발생할 수 있는 모든 변수는 반영하지 못함
- 실제 영향도는 실사용자에게 배포 후에야 파악 가능하기 때문에 모든 변경을 곧바로 프로덕션에 적용하는 것은 위험하다고 진단
- 과거부터 해결책으로 '피처 플래그(Feature Flag)'를 활용, 일부 사용자에게만 기능 공개 후 성능 모니터링, 이상 발생 시 즉시 Rollback 가능하게 운영함
- 그러나 과거에는 엔지니어가 직접 플래그 코드를 추가했기 때문에 대규모 자동화 환경에서는 적용이 어려웠고, 규모가 커질수록 관리도 힘들었음
- Launch Darkly라는 제품이 이러한 문제를 자동화로 풀었으며, 최근에는 '릴리즈 오토파일럿(Release Autopilot)' 기능을 통해 AI가 플래그 운영까지 처리하게 됨
- 이 자동화는 변경 위험도 평가, 성공 지표(메트릭) 설정, 카나리아 릴리즈(일부 사용자 대상), 실시간 성능 체크, 플래그 클린업 등 전 과정을 포함
- 최종 배포 전에는 여전히 사람이 승인권을 갖기 때문에, 에이전트에 대한 신뢰보다 실제 사용자의 반응으로 최종 배포를 결정하는 구조임
- 영상 마지막에서 Launch Darkly와의 협업 사실 및 제품 설명 링크 공유

## 세부 요약 - 주제별 정리

### AI 소프트웨어 에이전트는 코드 병합 자동화까지만 신뢰할 수 있다고 판단함

- 발표자는 본인의 AI 소프트웨어 팩토리가 밤새 코드 병합(merge)을 자동화한다고 밝힘
- 그러나 '프로덕션(실서비스)' 배포 단계에 있어서는 에이전트를 신뢰하지 않는다고 강조
- 병합과 실제 사용자 대상 배포(Ship)는 완전히 다름을 명확히 함
- 이러한 경계를 마련한 이유와 한계에 대한 설명이 이어짐

### 자동화된 테스트와 리뷰만으로는 진짜 문제를 파악하지 못함을 지적함

- AI 에이전트가 수행하는 테스트와 코드 리뷰는 '코드가 정상적으로 보이는지'만 확인
- 코드의 진정한 영향력과 부작용은 실제 사용자가 사용하는 환경에서만 확인 가능
- "코드의 참된 결과는 실사용자 앞에 놓였을 때 알 수 있다"고 언급

### '피처 플래그'를 활용한 점진적 배포가 근본적 해결책이라는 점을 강조함

- 수년 전부터 업계에서 이미 '정답'으로 쓰이던 방법은 변경사항을 피처 플래그(Feature Flag)로 감쌌다가 소수 사용자에게만 노출 후 관찰하는 방식
- 이상이 감지되면 즉각적으로 플래그를 꺼 장애를 최소화함
- 과거 오랜 기간 이 방식을 수동으로 활용한 팀들이 있었음을 소개

### 수동 플래그 관리의 한계로 인해 대규모 자동화 환경에서 적용이 어려웠음을 설명함

- 플래그 삽입이 항상 엔지니어가 직접 코드를 넣어야 했던 작업이었음
- 실질적으로 모든 팀이 이 프로세스를 끝까지 잘 관리하지 못했다고 지적
- 에이전트가 머지 요청(pull request)을 대규모, 빠르게 생성하는 환경에서는 플래그 관리가 더욱 어려움

### Launch Darkly가 대규모 자동 플래그 운영 문제를 해결한다고 소개됨

- Launch Darkly는 새 코드 변경이 실제 프로덕션에서 어떻게 동작할지 팀에서 정밀하게 통제할 수 있도록 지원하는 플랫폼임
- 제품을 통해 변경사항의 실제 배포 행위를 안전하게 제어할 수 있음을 강조

### '릴리즈 오토파일럿' 기능으로 에이전트가 플래그 관리까지 자동화하게 진화함

- 최근 출시된 "Release Autopilot" 기능은 에이전트가 플래그 스크립트 작업 일체를 맡음
- Launch Darkly 플랫폼이 플래그 운영의 모든 단계를 자동으로 진행함

### 위험도 분류 및 피처 플래그 적용 결정이 자동으로 이뤄짐

- 위험 분류(Risk classification) 기능이 변경사항의 위험 수준을 평가
- 위험성이 높으면 해당 변경을 반드시 피처 플래그로 감싸도록 처리
- 위험도 평가를 기반으로 운영 정책 차별화가 가능해짐

### 성공 메트릭 설정 및 실서비스 프로덕션에서의 성과 측정이 포함됨

- 릴리즈의 성공 여부를 판단할 수 있는 KPI, 메트릭이 자동 생성됨
- 실시간으로 프로덕션 환경에서 기능의 성능과 영향도를 수치로 측정, 이상 신호를 감지함

### 카나리아 릴리즈를 통한 안전한 점진적 배포 절차가 자동 적용됨

- 자동 릴리즈 플랜은 일부 소수의 실제 사용자에게만 새 기능 오픈(카나리아 릴리즈)에서 시작함
- 이상이 없을 때에만 점진적으로 적용 범위를 넓히며, 위험 시 즉각 글로벌 배포를 중단함
- 모든 변경마다 보호(Guard Rail) 정책이 자동 적용됨

### 실시간 모니터링, 플래그 클린업, 승인 시스템으로 더욱 안전하게 설계됨

- 'Feature level observability'로 실제 프로덕션 신호를 기반으로 기능별 상태를 실시간 감시함
- 플래그 클린업(flag cleanup) 기능이 코드베이스에서 더 이상 쓰이지 않는 플래그를 주기적으로 정리해 코드 품질 유지함
- 모든 플래그 변경은 Pull Request에서 제안되고, 실제 비활성화/적용은 사람이 승인해야 적용됨
- 이 구조 덕분에, AI 에이전트를 완전히 신뢰하지 않더라도 안전하게 새로운 기능을 배포할 수 있게 됨

### 영상 마무리에서 Launch Darkly와의 협업 및 추가 정보 링크를 안내함

- Launch Darkly의 해당 기능을 영상 제작자와의 협업을 통해 소개함
- 영상 설명란에 관련 링크도 제공한다고 명시
