## *프롬프트 인젝션은 AI 에이전트 보안의 시작에 불과함 (AI 에이전트 보안에 필요한 것들)* 핵심 요약

- ‘두 번째 두뇌’로 부르는 개인 AI 에이전트를 이용해 업무를 관리하면, 여러 시스템과 데이터 접근 권한이 필수적임
- 이 과정에서 ‘프롬프트 인젝션’(Prompt Injection) 공격, 즉 AI가 외부 데이터를 통해 원치 않는 지시를 받는 위험 존재
- 이를 막기 위해, 본인은 실제 LLM(대형언어모델)로 전달되기 전에 모든 입력을 사전에 자동 점검하는 보안 절차를 직접 구축
- 에이전트의 접근 권한은 최소화하여 꼭 필요한 것만 허용
- 개인 개발자는 자신이 만든 에이전트여서 통제가 가능하나, 기업 환경에서는 수많은 에이전트가 각기 다른 위치(클라우드·직원 PC 등)에서 동작
- 기업에서는 IT 부서가 "어떤 에이전트가, 누가 소유했고, 무엇에 접근 가능한가"를 파악해야 하는 복잡한 관리 문제 발생
- 마이크로소프트의 Agent 365/프로젝트 Perception는 이 문제 해소를 위해 등장
- 이 시스템은 각 에이전트에게 독립된 정체성과 역할 기반 접근제어, 동적·임시 권한, 위험도 기반 보안감사와 노출 시각화 제공
- Guardian 에이전트로 조직 전체의 위험관리 및 보안 권고, 점진적 적용과 영향 미리보기 지원
- 이러한 솔루션으로 소수개가 아닌 수백 개의 에이전트도 안전하게 통합·관리 가능

## 세부 요약 - 주제별 정리

### AI 에이전트를 활용할 때는 필연적으로 주요 시스템과 데이터 접근이 요구됨

- 개인은 생산성 향상을 위해 ‘두 번째 두뇌’라 부르는 AI 에이전트로 다수의 업무를 관리함
- 이 에이전트가 효율적으로 일하려면, 다양한 시스템(클라우드, 로컬)과 데이터에 대한 접근 권한이 필수적임
- 이에 따라 민감한 정보나 사내 리소스 등 주요 자산을 AI 에이전트가 다루게 됨

### 프롬프트 인젝션 공격은 에이전트 보안의 매우 현실적인 위협임

- 프롬프트 인젝션은 AI가 외부에서 받은 데이터나 텍스트 내 숨겨진 지시문에 의해 원하지 않는 행동을 하도록 유도하는 공격 기법임
- 예시: 외부 데이터가 '특정 작업을 수행하라'는 명령을 포함하고 있어, 사용자가 지시하지 않은 행동이 일어날 수 있음
- 이러한 위협 때문에, 에이전트가 입력 데이터를 수신할 때마다 항상 위험성을 점검해야 함

### 입력 데이터는 LLM에 도달하기 전에 보안 검사가 반드시 필요함

- 제작자는 AI 에이전트가 받는 모든 입력을 실제 LLM으로 전달하기 전에 일련의 보안 점검 절차를 도입함
- 의심스럽거나 불허된 명령·패턴을 사전 필터링하여 악성 프롬프트가 LLM을 제어하지 못하게 함
- 이를 통해 원하지 않는 자동화된 행동이나 정보노출을 방지함

### 에이전트의 접근 권한은 최소한으로 제한해야 안전함

- 본인은 에이전트가 반드시 필요한 시스템/리소스에만 접근하도록 엄격히 권한을 제한하여 잠재적 피해를 최소화함
- 에이전트에게 과도한 권한을 부여하면, 악의적 공격에 노출될 경우 큰 피해 가능성이 큼
- 최소권한 원칙(Least Privilege Principle)을 실제 운영에 적용함

### 개인 개발환경에서는 에이전트 관리가 상대적으로 용이함

- 본인이 직접 구축한 에이전트의 경우, 어떤 코드가 돌아가는지/어떤 권한이 필요할지 명확하게 파악 가능함
- 수동 관리가 가능하므로, 보안 점검과 접근 권한 운영이 용이함

### 기업 환경에서는 수많은 에이전트와 복잡한 관리 문제가 발생함

- 대기업·기관에서는 수십~수백, 심지어 그 이상의 다양한 에이전트가 존재
- 이 에이전트들은 클라우드, 온프레미스, 직원 로컬 PC 등 다양한 환경에서 실행됨
- IT 부서는 각 에이전트의 존재 여부, 소유자, 수행 임무, 접근 권한 현황 파악 및 관리가 필수가 됨
- 소수 인원이 수동 점검으로 대응 불가, 체계적인 관리 솔루션이 필요해짐

### 마이크로소프트는 Agent 365와 프로젝트 Perception을 통해 체계적 에이전트 관리와 보안을 구현함

- 마이크로소프트는 이러한 과제를 해결하기 위해 Agent 365와 프로젝트 Perception을 개발함
- 각 에이전트에 독립된 ‘ID’와 정체성을 부여
- 에이전트별로 ‘임무 범위(스코프)’를 지정해 불필요한 데이터·기능 접근을 자동 제한함
- 변화하는 위험 수준에 맞춰 가변적으로 작동하는 ‘위험 컨테인먼트’(위험 봉쇄) 기능 내장

### 프로젝트 Perception은 보안 사각지대를 시각화하여 관리자의 대응력을 높임

- 프로젝트 Perception에서는 관리자에게 조직 내 에이전트들이 현행 보안정책에 비해 어느 부분에서 취약점·허점(갭)이 존재하는지 실시간 시각화
- 기존 접근제어 정책에 누락된 포인트, 취약점 노출, 잠재 위험 구간 등을 쉽게 파악할 수 있도록 지원함

### Guardian 에이전트를 통해 조직 전체의 에이전트 위험을 한눈에 관리 가능함

- 프로젝트 Perception의 특별 기능인 ‘Guardian’ 에이전트는 개별 인시던트가 아닌, 조직 전체의 에이전트 생태계를 효율적으로 위험관리함
- 개별 사례별 수작업 조사 대신, 전사적·종합적 위험 분석 및 자동 보안 권고가 가능해짐

### 임시·동적 권한 관리와 위험도 기반 접근 제어가 보안 수준을 한층 강화함

- 각 에이전트에 대해 ‘타임바운드’(기간 제한), ‘오퍼레이션 기반’(업무별), ‘리소스별 맞춤’ 접근권한 설정 가능
- 기존에는 입사/퇴사, 승인 시점 등 제한적으로 접근 권한을 변경했으나, 실시간 임무 단위로 세밀하게 제어 가능
- 위험도 평가와 정책 적용이 로그인 시점뿐 아니라, 에이전트의 실제 행동 단위로 지속적으로 이뤄짐

### 보안 정책 적용 전 영향 예측과 점진적 출시가 가능하도록 설계됨

- 새로운 권한/보안 보호조치를 적용하기 전, 미리 기업 영향도를 시뮬레이션하여 불필요한 혼란을 막음
- 보안 정책을 전면/점진적으로 단계별 적용하고, 실제 운영에 도입하기 전 미리 현장에 미치는 효과를 예측·조정 가능
- 보안점검 권고는 IT부서가 최종 승인함으로써, 자체 통제력도 확보

### 수백 개 이상의 에이전트도 통합적·일관되게 안전하게 관리 가능함

- 영상 제작자는 본인의 경험을 들어 수작업으로는 1개 에이전트 관리까지만 현실적으로 가능함을 강조
- 마이크로소프트 솔루션 도입을 통해 조직 내 수백 개 이상의 에이전트도 같은 수준의 보안과 효율로 관리할 수 있음을 시연
- 링크와 기술 참고 자료를 안내하며, 마이크로소프트와의 협력 사례를 언급함
