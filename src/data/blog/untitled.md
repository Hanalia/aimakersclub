## *나는 내 AI 에이전트가 코드를 병합하도록 신뢰하지만, 바로 프로덕션 배포는 맡기지 않는다* 핵심 요약

- 영상 제작자는 자신의 AI 소프트웨어 공장이 코드 병합까지는 맡기지만, 프로덕션 배포는 직접 검토한다고 밝힘
- AI 에이전트가 실행하는 테스트와 리뷰는 코드의 외형적 적합성만 확인할 뿐, 실제 배포 시 효과는 알 수 없음을 강조
- 실제 사용자 앞에 코드를 배포하기 전, 영향을 파악하기 위한 단계적 릴리즈 방법의 필요성을 설명
- 과거에는 기능 플래그(Feature Flag)를 추가해, 변경사항을 일부 사용자에게만 제한적으로 공개하고 실시간으로 모니터링 및 긴급 차단하는 방식이 널리 활용됨
- 하지만 엔지니어가 수동으로 플래그를 추가해야 하므로 많은 팀이 제대로 도입하지 못했고, 특히 에이전트가 대규모로 PR을 생성할 때엔 관리가 어려움
- Launch Darkly라는 서비스는 코드를 프로덕션에 배포한 뒤에도 변화의 행위 제어를 가능하게 해줌
- Launch Darkly의 ‘릴리즈 오토파일럿(Release Autopilot)’은 AI 에이전트가 기능 플래그 적용 작업을 자동화하여 부담을 해소함
- 위험 분류, 성공 지표 설정, 카나리아 릴리즈, 실시간 관측, 플래그 정리 등 단계별로 자동으로 관리
- 모든 변경사항은 사람의 승인을 받기 전까진 실제로 적용되지 않아 ‘완전 자동화’가 아닌, 최종 책임은 사람에게 있음
- 영상 마지막에서는 Launch Darkly의 협업과 제품 링크 안내로 마무리

## 세부 요약 - 주제별 정리

### AI 소프트웨어 에이전트에게 전적으로 프로덕션 배포를 맡기기 힘든 이유가 명확하게 제시됨

- 제작자는 자신의 AI 소프트웨어 공장에서 코드 병합 작업은 AI 에이전트에게 밤새 맡길 정도로 신뢰한다고 밝힘
- 그러나 AI가 직접 프로덕션까지 코드를 배포하는 것에는 신중을 기함
- AI의 테스트 및 리뷰는 코드의 외형적 적합성을 평가할 뿐, 실제 배포 시 전체 영향은 파악이 불가능함
- 진정한 변화의 효과는 코드가 실제 사용자 앞에 배포되어야만 확인할 수 있음을 강조

### 코드 변경의 실제 영향은 실사용자 환경에서만 명확히 검증할 수 있음을 지적함

- “테스트와 리뷰가 코드가 맞아 보인다는 주장만 한다”는 식으로 코드 리뷰의 한계를 강조
- 코드 변경의 실제 효과는 실시간으로 사용자들이 접한 후에만 파악 가능
- 이러한 불확실성을 고려해, 직접 검토 후에만 프로덕션 배포를 허용하는 전략을 유지

### 기능 플래그(Feature Flag)는 변화의 위험을 최소화하는 검증 방법으로 오랫동안 활용되어 왔음

- 지난 수년간, 코드 변경사항을 ‘기능 플래그(Feature Flag)’ 뒤에 숨기는 방식이 일반적이었음을 설명
- 선택적으로 기능을 소수 사용자에게만 단계적으로 배포(점진적 릴리즈)하며 문제 발생 시 빠른 롤백(플래그 비활성화)이 가능하도록 설계
- “플래그를 추가하려면 엔지니어가 직접 작업해야 한다”는 점 때문에, 많은 팀이 끝까지 이 프로세스를 적용하지 못했음

### AI 에이전트가 자동으로 PR을 대량 생성하는 환경에서는 기능 플래그 관리가 쉽지 않다는 점을 언급함

- AI 에이전트가 대량으로 Pull Request를 만들면, 각 변경사항마다 기능 플래그를 수작업으로 추가하기 어렵다고 설명
- 기능 플래그 추가, 적용, 정리 작업이 자동화되지 않으면 관리 비용이 급격히 증가할 수 있음을 시사

### Launch Darkly의 서비스는 프로덕션 배포 후 변경 제어를 구조적으로 지원함

- Launch Darkly는 코드를 프로덕션 환경에 배포한 뒤에도 각 변화를 세밀하게 조절할 수 있는 도구로 소개됨
- 실제 릴리즈 후에도 활성화 여부, 적용 범위 등을 세밀하게 관리 가능

### 릴리즈 오토파일럿(Release Autopilot)은 기능 플래그 작업의 자동화를 통해 부담을 해소함

- Launch Darkly의 새 기능인 ‘release autopilot’은 AI가 연관된 플래그 작업을 자동으로 처리
- 이 기능 덕분에 대규모 자동화 환경에서도 플래그 관리가 부담 없이 이루어짐
- “Launch Darkly가 단계별로 모든 작업을 처리해 준다”는 말로 작업 자동화 수준을 강조

### 위험 분류와 성공 지표 설정으로 변경 사항의 안전성이 자동으로 평가됨

- 위험 분류(Risk Classification) 기능으로 변경 사항의 위험도를 분석하고, 플래그로 묶어야 할지 결정함
- 성공 지표(Success Metrics)를 설정하여, 실제 프로덕션 내에서 해당 변경사항의 성과를 측정할 수 있게 준비

### 단계적 배포와 관측, 안전장치 등 세밀한 릴리즈 프로세스가 자동화됨

- 자동 릴리즈 계획(Automatic Release Plan)에는 카나리아 릴리즈(Canary Release)가 포함됨
- 카나리아 릴리즈: 변경사항을 일단 소수 사용자에게만 적용 후, 성과와 안전성이 입증되면 차츰 배포 대상을 확대
- ‘가드레일’(guard rails) 설정을 통해 문제가 발생했을 때, 더 넓은 배포 확장을 차단

### 실시간 관측과 플래그 정리 등 릴리즈 이후 관리까지 체계적으로 지원됨

- ‘기능 단위 관측(Feature Level Observability)’를 통해, 실시간 프로덕션 신호를 모니터링하여 변화의 안전성을 검증
- ‘플래그 정리(Flag Cleanup)’ 기능으로, 코드베이스에서 불필요하게 남아 있는 플래그를 정리함

### 모든 자동화 과정 이후에도 변경 사항 적용 전 최종 승인권한은 사람에게 있음

- 자동 플래그 생성 및 적용이 PR(풀 리퀘스트) 단계에서 ‘제안’ 형태로 이루어짐
- 실제 릴리즈 적용은 사람의 최종 승인 이후에만 활성화됨
- 즉, 완전 자동화가 아니며 사람의 개입과 검토를 필수적으로 거침

### 영상 마무리에서는 Launch Darkly와의 협업 및 제품 링크 안내로 끝맺음

- 영상 마지막 부분에서 Launch Darkly와의 협업을 언급
- 더 자세한 정보는 영상 설명란의 링크를 통해 확인할 수 있도록 안내
