## *코딩 에이전트가 간과하는 치명적 맹점, 반드시 바로잡아야 합니다* 핵심 요약

- 영상에서는 AI 기반 코딩 에이전트가 실제 프로덕션 환경에서 코드 실행 결과를 파악하지 못하는 치명적인 맹점이 반복적으로 발생한다는 점을 강조함
-  제작자는 이메일 초안 생성 에이전트의 문제 사례(이메일 무시, 이상 없음 보고)를 구체적으로 언급하며, 이는 코드베이스에는 드러나지 않는 문제임을 지적
-  코드 수준의 오류나 크래시 없이 잘못된 결과가 발생해, 문제 진단과 발견이 매우 어렵다는 현실을 강조함
-  개발자가 실제 런타임 동작을 주시함으로써만 빠르고 정확히 문제를 발견할 수 있었던 경험을 소개 (7분 내 수정)
-  AI 코딩 에이전트는 전체 코드베이스를 볼 수는 있어도, "실제로 실행되었을 때" 무엇이 일어나는지 직접적으로 인지하지 못함
-  Dinatrace MCP 서버를 활용하면, 프로덕션 데이터를 IDE로 바로 가져와 에이전트의 맹점을 해결할 수 있음을 시연 사례로 소개
-  영상에서는 앱의 응답 시간이 89초로 느렸던 실제 예시를 통해, 에이전트가 실시간 데이터로 DB를 혹사시키는 메서드까지 집어낼 수 있음을 설명
-  실시간 텔레메트리 데이터와 소스 코드 분석을 결합하면, 문제 라인과 최적의 해결책(인덱스 추가 등)을 명확히 도출할 수 있음을 강조함
-  "무엇을 쓰든, AI 에이전트에 런타임 동작 정보를 반드시 제공하라"는 당부로 마무리
-  영상 마지막에 Dinatrace와의 협업 및 링크 제공을 언급

## 세부 요약 - 주제별 정리

### 에이전트가 반복적으로 프로덕션에서 예상치 못한 문제를 일으키는 현실을 고백함

- 제작자는 자신이 만든 AI 코딩 에이전트가 실제 환경에서 수십 번이나 예기치 못한 방식으로 작동을 멈추거나 잘못된 결과를 낸 경험을 언급함
- 때때로 그 문제의 양상은 다소 당황스러울 만큼 기초적인 수준이었음을 솔직히 밝힘
- 이러한 문제의 근원은 대부분 "맹점(blind spot)", 즉 프로덕션 실행 과정에 대한 에이전트의 무지 때문임을 지적함

### 이메일 초안 생성 에이전트의 문제 사례로 맹점을 실제로 설명함

- 지난 달, 제작자는 자신의 AI 세컨드 브레인에 포함된 이메일 초안 생성 에이전트의 새로운 버전을 배포함
- 내부 평가(evals)까지 통과한 이 에이전트가, 실제 첫 프로덕션 동작에서 두 개의 미처리 이메일을 인식하고도 아무런 툴도 호출하지 않고 "조치할 필요 없음"이라 보고함
- 크래시나 명확한 에러 메시지도 없었고, 코드상에도 문제를 쉽게 드러내는 부분이 없었음
- 실제 동작 장면을 우연히 직접 보지 않았다면, 원인 파악에 상당한 시간이 소요될 수 있었고, 반면 실제론 7분 안에 문제를 파악해 해결함

### AI 코딩 에이전트의 최대 맹점이 “코드 실행 결과 관찰 불가”임을 강조함

- 코딩 에이전트는 코드베이스 전체를 읽고 분석하는 데 능함
- 하지만, 코드를 실제로 실행했을 때 어떠한 결과와 동작이 일어나는지는 직접적으로 파악하지 못함
- 이 차이로 인해, 코드 오류가 아닌 “운영상 문제”를 놓치게 되고, 사용자는 부적절한 결과가 발생해도 그 원인을 쉽게 알 수 없음

### Dinatrace MCP 서버를 통해 프로덕션 데이터를 IDE로 직접 연동할 수 있음을 소개함

- Dinatrace MCP 서버는 실제 서비스 운영 데이터(프로덕션 데이터)를 개발 환경(IDE)로 바로 전달해 줌
- 이를 통해 에이전트가 정적인 코드 분석이 아니라, 실제 동작 결과 데이터까지 기반으로 문제를 진단할 수 있게 됨

### 실시간 운영 데이터를 바탕으로 코드 병목을 파악하는 실제 예시를 보여줌

- Dinatrace 시연 예시에서는 애플리케이션 응답 시간이 무려 89초에 달하는 상황이 보여짐
- 에이전트에 “DB를 가장 많이 때리는 상위 5개 메서드”를 질의하자, 실시간 텔레메트리 데이터를 근거로 그 목록이 순위별로 산출됨
- 동일한 에이전트가 소스 코드도 읽을 수 있기 때문에, 실시간 데이터에서 찾은 병목 메서드의 정확한 코드 라인까지 추적 가능함

### 코드만 봐서는 알기 어려운 비효율 로직을 실시간 데이터가 드러냄

- 가장 큰 병목은 “테이블 전체 row를 모든 호출 때마다 읽어오는” 서치 쿼리였음
- 코드만 보면 그냥 평범한 쿼리로 보이지만, 실제 연산/트래픽 데이터를 바탕으로 하면 이 부분에서 많은 CPU 자원이 소모됨을 구체적으로 확인 가능함

### 실시간 데이터와 코드 분석을 결합하면 해결책이 명확해짐

- 운영 데이터가 제공하는 수치를 토대로, 에이전트는 어떤 부분을 어떻게 개선해야 할지(인덱스 추가 등)를 정확하게 추천할 수 있음
- 특히 데이터베이스 인덱스를 추가하는 것만으로도, 실제 어플리케이션 차원의 소스코드 수정 없이 큰 성능 개선이 이루어질 수 있음을 예시로 소개

### 어떤 툴을 사용하든 반드시 런타임 동작 데이터를 에이전트에 연결해야 함을 강조함

- Dinatrace MCP처럼 복잡한 툴이 아니더라도, 운영 데이터(실제 동작 수치, 로그, 트레이스 등)의 연결은 필수임을 주장함
- “코딩 에이전트가 코드베이스만으로 판단하지 않도록” 만들기 위해, 반드시 실행 정보가 필요함을 재차 당부

### Dinatrace 협찬 및 추가 정보 링크 제공 안내로 마무리함

- 본 영상 제작에 Dinatrace가 후원했음을 밝히고, 관련 링크 제공을 언급하며 영상을 마무리함
