## *코딩 에이전트에게 엄청난 맹점이 존재하며 직접 개선이 필요함* 핵심 요약

- 영상 제목: **코딩 에이전트에게 엄청난 맹점이 존재하며 직접 개선이 필요함**
- 제작자는 실제 서비스 환경에서 코딩 에이전트가 여러 번 예기치 않게 실패한 경험을 공유함
- 최근 이메일 초안을 작성하는 에이전트를 출시했으나, 실 서비스 첫 실행에서 대기 중인 이메일에 아무 조치도 하지 않는 문제 발생
- 문제는 코드 검토나 자동평가(evals)를 통과했음에도, 실제 동작 상황의 맹점에서 비롯됨
- 이 맹점은 에이전트가 코드베이스는 인식하지만 실제 런타임의 동작(실행 데이터)을 파악하지 못하기 때문임
- 제작자는 이 문제를 실제 실행 과정을 직접 관찰하여 7분 만에 수정함
- Dinatrace의 MCP 서버 사례를 통해, 프로덕션 데이터를 IDE로 가져와 에이전트에 실시간 실행 정보를 제공하는 방식을 소개
- 참조 예시에서, 응답 시간이 과도하게 긴 앱에 대해 데이터베이스 부하가 큰 메서드를 실시간 텔레메트리로 분석하여 정확한 코드라인까지 추적함
- 해결책으로 인덱스 추가 같은 DB 튜닝 조치를 통해 코드 수정 없이 성능 문제를 해결함
- 결론적으로, 모든 개발자와 에이전트 사용자는 코딩 에이전트가 ‘실행 중 코드를 볼 수 있는 방법’을 반드시 제공해야 함을 강조함

## 세부 요약 - 주제별 정리

### 실 서비스 환경에서 코딩 에이전트가 여러 번 실패를 겪음

- 제작자는 수십 번에 달하는 에이전트의 실행 실패를 직접 경험했다고 밝힘
- 일부 실패 사례는 꽤 민망하거나 대외적으로도 문제를 야기할 수 있었던 상황임
- 대부분의 실패는 코딩 에이전트가 가진 특정 맹점에서 비롯되었다고 설명함

### 이메일 초안 작성 에이전트의 실서비스 결함 사례 소개

- 한 달 전, 제작자는 자신의 AI 세컨드 브레인의 일부로 이메일 작성을 자동화하는 에이전트를 출시함
- 에이전트는 자체 평가(evals)를 문제 없이 통과함
- 그러나 첫 프로덕션 실행에서, 에이전트는 두 개의 미답장 이메일을 발견하고도 아무런 도구(tool) 호출을 하지 않음
- 에이전트는 ‘조치할 것이 없다’고 응답했으며, 이 과정에서 크래시나 에러 메시지도 발생하지 않음

### 코드 및 에러 로그에 흔적이 없어 문제 원인을 파악하기 어려웠음

- 코드베이스 상에서 해당 문제의 원인을 쉽게 파악할 수 있는 흔적이 존재하지 않았음
- 런타임 에러가 아니다 보니 crash 로그, 에러 메시지 등도 남지 않음
- 제작자는 실제 프로덕션 런을 직접 주시했기 때문에 이 문제를 발견할 수 있었음
- 문제 원인 분석 및 수정에 약 7분 정도 소요됨

### 에이전트의 맹점은 ‘런타임 행동 관찰 불능’에서 초래됨

- 코딩 에이전트는 전체 코드베이스를 읽고 분석할 수 있음
- 그러나 코드가 실제로 어떻게 실행되고, 어떤 행동을 하는지(실행 상황)는 인식하지 못함
- 이런 맹점 때문에 production 환경의 예측 불가한 버그 등이 발생할 수 있음

### 실행 데이터와 코딩 에이전트의 통합 방법을 Dinatrace 예시로 제시함

- Dinatrace MCP(Monitoring and Control Platform) 서버를 활용한 실사례를 언급함
- MCP 서버는 프로덕션 데이터를 IDE(통합 개발 환경)로 직접 연동시켜, 코딩 에이전트에게 런타임 상황을 인식시킴
- 이를 통해 실행 중인 애플리케이션의 실제 동작 데이터를 에이전트가 실시간으로 반영할 수 있게 됨

### 실시간 모니터링을 통한 성능 이슈 분석 및 해결 예시 설명

- Dinatrace의 예로, 한 앱의 응답 시간이 89초에 달하는 비정상적인 상황이 발생함
- 에이전트에게 데이터베이스 접근 부하가 가장 큰 다섯 개의 메서드를 요청함
- 에이전트는 실시간 텔레메트리 데이터를 기반으로 문제 메서드들을 순위별로 반환
- 동일한 에이전트가 소스코드를 분석해, 가장 문제가 되는 쿼리의 정확한 코드라인을 추출함
- 실시간 측정 없이 코드를 볼 때는 평범한 검색 쿼리로 보이나, 프로덕션 데이터가 실제 병목 지점을 명확히 보여줌

### 인덱스 추가 등 DB 튜닝 조치로 코드 수정 없이 성능 문제를 해결함

- 에이전트가 추천한 조치는 어플리케이션 코드 변경 없이 데이터베이스 인덱스를 추가하는 방식임
- 이 같은 최적화는 실제 측정 데이터 없이는 파악하기 어려운 현상임
- 예시 쿼리는 모든 호출에서 테이블의 모든 row를 읽었음

### 런타임 데이터가 없다면 코딩 에이전트의 한계가 명확함을 강조함

- 소스코드만으로는 숨겨진 성능 문제나 실동작 상의 맹점을 명확히 알 수 없음
- 프로덕션(실서비스) 단계에서만 나타나는 버그, 병목, 사용자 경험 저하 등을 에이전트 단독으로 파악 불가
- 대표 사례로 아무런 에러나 크래시 없이 큰 결함이 발생했던 자신의 경험을 재차 언급

### 모든 개발자와 에이전트 사용자에게 런타임 데이터 연동의 중요성을 당부함

- Dinatrace와 같은 시스템의 사례처럼, 실제 런타임 데이터를 에이전트에 전달하는 구조가 필수임을 강하게 주장
- 어떤 솔루션을 사용하든, 자신의 코딩 에이전트가 실행 중의 코드를 관찰할 수 있는 시스템을 반드시 구축할 것을 촉구함

### Dinatrace의 후원 언급 및 참고 링크 안내

- 본 영상이 Dinatrace의 후원으로 제작되었음을 명확히 밝힘
- Dinatrace 관련 자세한 소개 링크를 영상 설명란에 안내할 예정임
