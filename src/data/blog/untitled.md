## *프롬프트 인젝션은 AI 에이전트 보안의 시작에 불과하다 (여기에 무엇이 필요한지)* 핵심 요약

- 영상을 제작한 인물은 자신의 "세컨드 브레인"(두 번째 뇌, 자동화 AI 에이전트)을 다양한 업무 관리에 사용한다고 언급함
- 이를 위해 에이전트에 여러 시스템 및 데이터 접근 권한을 부여하는데, 이로 인해 프롬프트 인젝션(Prompt Injection)과 같은 보안 위험이 발생할 수 있다고 지적
- 외부 데이터가 AI 에이전트에 의도치 않은 명령을 내릴 수 있는 상황을 예로 들어, 이에 대해 사전에 방어 조치를 구축했다고 밝힘
- 본인은 에이전트에 도달하는 모든 데이터를 LLM(대형 언어 모델) 전달 전, 다중 보안 점검 시스템을 적용함
- 에이전트가 실제로 접근해야 할 최소한의 리소스만 권한을 주도록 제한
- 개인 프로젝트에서는 직접 개발자이기에 비교적 쉽게 구현했으나, 기업 환경에서는 수백 개 에이전트가 클라우드 및 직원 기기에서 동작하면서 보안관리 난이도가 크게 증가한다고 설명
- 마이크로소프트가 이 문제를 해결하기 위해 Agent 365 및 프로젝트 Perception을 제시함
- 해당 솔루션들은 에이전트 별 신원(Identity), 작업별 최소 권한, 동적 접근관리, 리스크 변화 감지, 가이드라인 준수 검토, 권한 승인 자동화 등 다양한 기능을 지원함
- 이러한 기능 도입을 통해 기업들은 수많은 AI 에이전트 관리 및 보안 통제를 보다 체계적이고 효율적으로 구현할 수 있음

## 세부 요약 - 주제별 정리

### AI 에이전트 활용이 보안 위협과 직결된다는 인식이 강조됨

- 영상 제작자는 “세컨드 브레인”이라고 부르는 AI 에이전트를 이용해 다양한 업무를 자동화 및 관리함
- 이 에이전트가 제대로 작동하려면 다양한 사내 시스템 및 민감 데이터 접근이 필수적임
- 시스템적 편리성과 함께, 이 에이전트가 가져올 보안 위협에 대해 지속적으로 고민할 필요성을 제기함

### 프롬프트 인젝션 문제는 실질적이고 광범위한 위험을 내포함

- 프롬프트 인젝션(Prompt Injection)은 외부에서 주입되는 데이터(명령어)가 AI에 예상치 않은 동작을 유도할 때 발생
- 예를 들어, 외부에서 들어온 데이터가 AI 에이전트에 ‘사용자 요청과 다른 명령’을 내릴 수도 있음
- 제작자는 이러한 상황을 대비하기 위해 각 단계마다 ‘보안 점검 시스템’을 구현했다고 설명

### 데이터 전송 전 다층 보안 점검을 구축하여 위험을 완화함

- AI 에이전트가 LLM에 입력값을 전달하기 전, 제작자는 모든 데이터에 다중 보안 점검을 실시함
- 이는 악의적 프롬프트 또는 비의도적 명령 주입을 막기 위한 방어 수단임
- 점검 시스템 구현을 통해 AI 시스템의 불확실성 및 외부 위험을 크게 줄였다고 언급

### 접근 권한을 최소화하여 피해 가능 범위를 제한함

- AI 에이전트에는 업무상 반드시 필요한 시스템 및 데이터 접근권한만 부여하도록 제한
- 이를 통해 에이전트가 잘못 행동하더라도, 피해가 확장되는 것을 방지
- “필요 최소한의 권한만 할당” 원칙을 실질적으로 적용했다고 설명

### 개인 개발자가 직접 설계한 시스템은 통제가 용이했음을 언급함

- 본인은 AI 에이전트를 직접 개발했기에 보안점검과 권한 제한 시스템 구축이 상대적으로 쉬웠음
- 그러나, 영상은 대기업 또는 조직에서는 이 방식이 확장성 및 관리 용이성 측면에서 매우 어렵다고 지적

### 대규모 기업 환경에서는 에이전트 식별과 권한 관리가 큰 난제로 부각됨

- 기업에는 수십~수백 개의 다양한 AI 에이전트가 존재하며, 이들은 클라우드와 직원 PC 등 다양한 장소에서 구동
- IT 부서는 에이전트 개별 성격, 소유자, 권한, 접근 범위 등을 모두 파악해야 하는데, 이는 매우 복잡하고 까다로운 과제

### 마이크로소프트는 Agent 365 및 Perception 프로젝트를 통해 통합 관리 솔루션을 제시함

- 마이크로소프트는 기업 내 AI 에이전트 보안을 위해 Agent 365와 프로젝트 Perception을 도입
- Agent 365는 에이전트마다 고유한 “신원(Identity)”을 부여
- 개별 에이전트는 사전에 정의된 작업 범위 내에서만 자원 접근이 가능하도록 제한함

### 프로젝트 Perception은 리스크 기반 에이전트 통제와 내부 가시성을 강화함

- Perception은 기업이 현재 적용 중인 에이전트 보안 통제에 ‘어디에 허점이 남아있는지’ 시각적으로 파악 가능케 해줌
- Guardian 에이전트의 도입을 통해, 여러 에이전트에 대한 리스크를 한 번에 분석 및 대응할 수 있음
- 이전에는 “에이전트 하나당, 한 번에 한 사건씩”만 조사했다면, Perception을 통해 집단적·총체적 접근이 가능해짐

### 동적 권한관리와 실시간 위험 분석이 도입됨을 설명함

- 에이전트의 접근 권한은 고정적이 아니라, 타임라인에 따라, 혹은 특정 작업 수행 시 ‘기간 한정·작업 한정 권한(동적 권한)’으로 관리
- 위험 기반 접근 검토는 단순 로그인 시점이 아닌, 에이전트 행동 전체 주기에서 리스크와 정책을 반영
- 이는 시시각각 변하는 위협과 상황에 기민하게 대응하기 위함

### 변경 사항은 팀이 직접 검토 및 점진적으로 적용할 수 있도록 설계됨

- 직원들은 Perception에서 제안된 보안 설정 및 개선 사항을 미리 확인·검토 가능
- 팀 승인 후 점진적으로 해당 방어 조치를 적용(gradual rollout)할 수 있음
- 이는 변화를 통제하며, 예상치 못한 문제 발생을 미연에 방지할 수 있도록 설계됨

### 마이크로소프트 솔루션 적용을 통해 대규모 에이전트 관리와 보안이 현실적으로 가능해졌음을 강조함

- 영상 제작자는 자신의 ‘1개 에이전트’에 이 시스템을 사용해왔으나, Agent 365와 Perception의 도입으로 수백 개 에이전트 관리도 가능해졌다고 평가
- “마이크로소프트와 협업하여 이 문제를 해결했다”고 감사 인사를 전하며, 추가 정보 링크를 영상 설명에 제공할 것임을 덧붙임
