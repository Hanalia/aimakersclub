## *여러분의 코딩 에이전트가 가진 치명적인 맹점(반드시 해결해야 할 문제)* 핵심 요약

- 영상 제목의 주장은 코딩 에이전트(AI 코드 도우미)가 실제로 운영 환경에서 발생하는 문제를 인식하지 못하는 '맹점'이 있다는 점을 지적함
- 제작자는 직접 운영 중 수십 번 에이전트가 실패한 경험을 토대로, 문제 대부분이 이 맹점에서 비롯된다고 설명
- 한 달 전 이메일 초안을 작성하는 AI 에이전트를 프로덕션(운영)에 배포했으나, 첫 실행에서 실제로 2개의 미응답 이메일이 있었음에도 아무런 동작도 하지 않고 ‘처리할 필요 없음’이라고 보고함
- 문제의 원인은 코드의 논리 오류나 버그가 아닌, 에이전트가 ‘코드가 실제로 실행되는 모습(운영 데이터)’을 볼 수 없다는 점에 있었음
- 이 문제는 에러도 로그도 발생하지 않아, 직접 실제 동작을 관찰(런타임 모니터링)하지 않으면 발견하기 어려웠음
- Dinatrace MCP 서버 등 운영 데이터(실행 중인 애플리케이션의 실시간 정보)를 에이전트에 연동하면, 실제 문제가 무엇인지 파악할 수 있음
- Dinatrace 활용 예시에서는 응답 시간이 89초에 달하는 앱에서 DB 과부하의 원인을 실시간 데이터로 분석해, 코드상의 문제를 정확히 집어내고 그 해결책까지 제시함
- AI 코딩 에이전트가 진정한 생산성 도구가 되려면, 코드만 보지 말고"실행 중인 코드가 실제로 어떻게 동작하는지"까지 파악해야 한다는 점을 강조
- 영상 말미에는 Dinatrace의 실제 사용 사례와 함께, 스폰서임을 밝힘


## 세부 요약 - 주제별 정리

### 운영 환경에서 반복적으로 발생하는 에이전트의 실패 사례를 경험함

- 제작자는 실제 프로덕션 환경에서 자신의 AI 코딩 에이전트가 여러 번(수십 회) 예상치 못한 방식으로 실패한 경험이 있음
- 때로는 매우 '당황스러운 방식'으로 문제가 드러나기도 했다고 솔직하게 밝힘
- 이러한 문제의 주요 원인은 에이전트가 코드 전체는 볼 수 있지만, 코드가 실제로 어떻게 동작하는지는 보지 못하기 때문임

### 이메일 초안 작성 AI 에이전트의 실 운영 첫날 문제 사례 공개

- 최근(지난달) 새로운 모델의 이메일 초안 작성용 에이전트를 배포함
- 이 에이전트는 본인의 ‘AI 세컨드 브레인’ 시스템의 일부
- 배포 전 자체 평가(evaluation)에서는 모든 테스트를 통과함
- 실제 운영 첫날, 에이전트가 미처리 상태인 두 통의 이메일을 발견하고도, 관련 툴 호출(tool call) 없이 '주의할 필요 없음(nothing needed attention)'이라며 정상종료함
- 이 과정에서 에이전트 측 오류 메시지나 시스템 에러, 명확한 코드 결함은 발견되지 않음

### 문제 원인은 코드상 오류가 아니라 에이전트의 관찰 맹점에 있음

- 코드상 어떤 버그나 장애, 크래시 등이 아니라, 실제 실행(런타임)에서 무엇이 일어났는지를 AI가 관찰하지 못한 것이 발단임
- 즉, 에이전트가 ‘코드베이스 전체’를 열람할 수 있음에도 ‘실시간 실행 결과’를 인지할 수 없었던 것
- 정상 작동처럼 보이지만 실제 해야 할 일을 놓치는 ‘위험한 맹점’ 발생
- 이 문제를 제작자가 직접 실행 결과를 육안으로 모니터링하면서 겨우 7분 만에 수정 가능했음

### 에이전트에게 실행 중인 코드의 실제 동작을 보게 할 필요가 있음

- AI 코딩 에이전트의 본질적 한계는 '정적 코드 이해'와 '실행(런타임) 중 현황'의 간극에 존재함
- 코딩 에이전트가 효율적으로 문제를 해결하려면 ‘실제 운영 데이터’(프로덕션 테레메트리, 실시간 로그 및 모니터링 정보)와 연동되어야 함을 강조
- 단순히 소스코드만 열람하는 것으로는 실전 문제를 놓칠 수 있음

### Dinatrace MCP 서버가 런타임 관찰 gap을 효과적으로 메꿀 수 있음

- Dinatrace의 MCP 서버가 이 문제를 해결하는 대표적 사례로 소개됨
- 이 MCP 서버(Managed Code Profiler)는 프로덕션 데이터를 실시간으로 개발자의 IDE에 제공함
- 즉, 에이전트와 개발자가 코드뿐 아니라 실행 과정을 실시간으로 추적할 수 있게 됨

### Dinatrace 활용 실제 시나리오: 운영 성능 저하 문제의 분석 예시

- 영상에서는 실제 Dinatrace 데모 시나리오로, 평균 응답 시간이 약 89초나 걸리는 앱을 분석
- 개발자가 에이전트에 “DB 부하가 가장 큰 다섯 메서드를 알려 달라”고 요청
- 에이전트가 실제 프로덕션 테레메트리(실시간 데이터) 기반으로 부하 순위를 산출 및 반환
- 동일한 에이전트가 코드까지 읽을 수 있어, 문제의 근원을 코드의 특정 라인까지 추적 가능
- 문제의 핵심: 모든 호출에서 테이블의 모든 row를 읽는 비효율적 검색 쿼리 존재
- 에이전트가 '인덱스 추가'라는 해결책을 코드 변경 없이 제안함
- 코드만 보면 단순한 SELECT 구문이지만, 실시간 데이터가 병목 위치를 명확히 보여줌

### 정적 코드 분석만으로는 숨겨진 성능 이슈를 파악할 수 없음

- 소스코드 상으로는 단순한 검색 쿼리처럼 보여도, 실제 프로덕션 부하와 병목은 데이터로만 확인 가능
- 코딩 에이전트가 실제 데이터(테레메트리, 모니터링 정보)를 접할 때에만 구체적이고 실질적인 파악 및 해결책 제시 가능

### 실행 데이터 연동은 어떤 코딩 에이전트에도 반드시 필요한 필수 조건

- 어떤 도구를 쓰든(에이전트, 서비스 무관) '실행 시 발생하는 현상'에 접근할 수 있어야 함
- 에이전트에게 '실시간 동작'을 확인 가능한 창구를 제공해야, 프로덕션 문제를 효과적으로 빠르게 감지 및 해결할 수 있음
- 영상 뒷부분에서 Dinatrace의 링크와, 이번 프로젝트의 스폰서임을 명확하게 안내함
