## *나는 내 AI 에이전트들이 코드를 합치는 것은 신뢰하지만, 프로덕션 반영은 직접 검토한다* 핵심 요약

- 영상 제작자는 자신의 AI 소프트웨어 에이전트에게 밤새 코드를 합치는 작업(merge)은 맡기지만, 최종 프로덕션 배포(ship)는 맡기지 않는다고 밝힘
- 실제로 AI가 진행한 테스트와 검토는 코드가 '약간 정상적으로 보인다'는 정도만 보장할 뿐, 실제 사용자 환경에서 어떻게 작동할지는 알 수 없음
- 프로덕션 배포로 인한 영향은 실제 사용자 앞에 공개되기 전에는 완전히 확인할 수 없어 신중한 통제가 필요함
- 과거에는 이런 위험을 줄이기 위해 엔지니어가 직접 '피처 플래그(feature flag)'를 코드에 추가하여, 변경사항을 일부 사용자에게만 노출하고 문제가 있을 시 즉시 비활성화하는 방법을 사용했음
- 하지만 많은 팀들이 플래그를 직접 손으로 관리해야 했기에, 규모가 커질수록 이 방식은 실질적으로 적용되지 못했음
- AI 에이전트가 대규모로 Pull Request(코드 병합 요청)를 생성하는 환경에서는 플래그 관리가 더욱 어려워짐
- Launch Darkly 서비스는 프로덕션에 반영된 변경사항을 효과적으로 제어할 수 있도록 해주며, 최근에는 'Release Autopilot' 기능을 출시해 AI 에이전트가 플래그 작업까지 자동화함
- 이 시스템에서 위험 분류, 성능 지표 설정, 카나리 배포, 실시간 관찰, 플래그 정리 등이 단계별로 자동으로 이뤄짐
- 모든 변경은 Pull Request 단계에서 제안되고, 팀원의 승인이 있을 때만 적용되어 지나치게 AI를 신뢰하지 않아도 됨
- 영상 마지막에 Launch Darkly와의 협업 사실과 서비스 링크를 안내함

## 세부 요약 - 주제별 정리

### AI 에이전트에게 코드 병합은 맡기지만, 프로덕션 배포는 직접 통제해야 하는 이유

- 제작자는 밤새 자신의 AI 소프트웨어 에이전트들이 코드를 합치는 작업(merge)을 신뢰한다고 언급
- 하지만 이 에이전트에게 코드를 바로 프로덕션 환경으로 배포하는 것은 신뢰하지 않는다고 강조
- 이유는 자동화된 테스트와 코드를 검토하는 과정이 실제로 코드가 "정상적으로 보인다"는 것만을 검증할 뿐이라는 한계가 있기 때문임
- 코드 변경의 진짜 효과와 영향은 실제 사용자 앞에 서비스가 공개되기 전까지는 알 수 없음
- 이로 인해 마지막 승인 단계에서 인간의 개입 및 검토를 반드시 거친다고 설명

### 피처 플래그 방식은 배포 위험성을 줄이지만, 직접 관리의 번거로움이 존재했음

- 문제를 방지하기 위해 과거에 사용한 해법은 변경사항을 '피처 플래그(feature flag)' 뒤에 숨기는 것임
- 이 방법은 새로운 변경이 있을 때 소수 사용자만 먼저 새로운 기능을 경험하게 하고, 문제 발생 시 즉시 해당 기능을 꺼서 리스크를 최소화함
- 그러나 기존 방식에서는 엔지니어가 각 변경마다 직접 플래그를 추가해야 했음
- 반복적으로 수작업이 필요했기 때문에 많은 팀들은 이 방법을 일관되게 사용하지 못했음
- Pull Request가 대량으로 생산되는 시대에, 이런 수동 플래그 설정 및 관리를 따라가기란 더욱 어려워졌음

### Launch Darkly는 배포 위험 관리와 플래그 자동화 기능을 제공함

- Launch Darkly 서비스는 변경사항을 프로덕션에서 '어떻게 동작할지'를 통제하는 도구임
- 최근 'Release Autopilot'이라는 새 기능을 발표, AI 에이전트가 피처 플래그 작업까지 자동 수행하게 됨
- Launch Darkly는 변경 관리의 각 단계를 체계적으로 자동화하여, 대규모 에이전트 운영 환경에서도 배포의 안전을 보장함

### 위험 분류, 성능 지표 설정 등 다단계 자동화 프로세스가 적용됨

- Release Autopilot 사용 시 첫 단계로 각 변경사항의 위험 분류가 자동으로 이뤄짐
- 변경의 위험도에 따라 해당 변경이 피처 플래그로 관리되어야 할지 결정됨
- 이어 프로덕션 환경에서의 성과를 평가하기 위한 성공 지표(success metrics)가 자동 설정됨

### 카나리 릴리스와 실시간 안전 감시로 위험 없는 점진적 배포가 가능함

- 자동화된 릴리스 계획(release plan)은 '카나리 릴리스'로 시작되어 소수의 실제 사용자 집단에만 변경이 적용됨
- 이때 변경이 정해진 안전 기준(guard rails) 안에서 정상적으로 작동하면 점진적으로 더 많은 사용자에게 확장됨
- 라이브(실시간) 프로덕션 지표와 비교해 변경사항을 지속적으로 관찰(feature level observability)함으로써 문제 발생 여부를 감지

### 피처 플래그 정리(cleanup)도 자동화되어, 코드베이스가 정돈됨

- 이미 도입된 플래그가 쌓이면서 코드 복잡도가 증가하는 문제를 방지하기 위해, 사용이 끝난 플래그를 자동으로 평가, 정리(cleanup)하는 기능도 제공됨
- 이로써 소프트웨어의 장기적인 유지관리성도 확보할 수 있음

### 모든 변경 과정에서 인간의 승인 절차는 여전히 필수적으로 남아 있음

- 완전 자동화 방식이 아니라, 모든 피처 플래그와 변경은 Pull Request 단계에서 '제안(Propose)'만 됨
- 실제 적용(배포)까지는 팀원이 직접 변경 사항을 확인·승인해야만 함
- 이 때문에 개발팀은 AI 에이전트에 대한 맹목적 신뢰 없이도 위험을 최소화하며 효율적으로 운영 가능함

### 실사용자 기준의 검증을 거친 뒤에만 전체 배포가 이뤄짐

- 실제 사용자를 대상으로 직접 제한적 배포와 결과 검증을 진행한 후에만 전체 사용자에게 배포가 확장됨
- 덕분에 급격한 장애나 사고로부터 서비스 전체를 보호할 수 있음

### Launch Darkly 서비스와의 협업 및 서비스 링크 안내

- 영상 끝부분에서 제작자는 Launch Darkly와의 협업 사실을 알림
- 서비스에 대한 자세한 안내와 링크를 영상 설명란에 추가함
