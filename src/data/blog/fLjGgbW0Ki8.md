## *Fable 5.2 완벽 가이드: 언제, 어떻게, 얼마만큼 쓸 것인가* 핵심 요약

- Fable 5.2는 Anthropic이 최근 출시한 최신 LLM(대형 언어 모델)로, “자기 인식” 수준이 높아진 것이 가장 큰 특징임.
- 기존 LLM들은 특정 요청(예: 응답하지 말라는 요청)에 항상 답변을 했으나, Fable 5.2는 이런 요청도 순응할 정도로 인간적인 반응을 보임.
- 벤치마크와 실제 테스트 결과 타 LLM(예: Opus 5.5) 대비 복잡하고 개방형인 의사결정 과업에서 월등한 성능을 보임.
- 단, 비용이 매우 높음: Max Reasoning 기준 평균 과업당 $26.54로 Opus 대비 2배 이상 비쌈(High Reasoning 때도 $9 vs. $3.46 수준).
- 비용 대비 효율을 고려하면, 간단하거나 정의된 과업엔 Opus 5.5만으로 충분하며 Fable의 도입은 비효율적임.
- 추천 워크플로우: Fable 5.2로 “계획, 탐색, 의사결정”만 수행하고, 상세 실행은 Opus 5.5로 위임하는 것이 최적.
- 다양한 오케스트레이션 예시(플러그인, 모니터링, 아키텍처 등)와 연구 결과를 통해 플래너-일꾼 모델 분리 사용이 강조됨.
- 각 모델-임무에 맞는 “effort level” 및 프롬프트 설계법에 대한 구체적 지침 제공: Fable 5.2는 High Reasoning, Opus 5.5는 Medium~High 권장.
- 프롬프트 팁(‘코드베이스의 주인임을 명확히 하기’, 하위 에이전트에는 Fable 대신 Opus/Sonnet 사용 등) 및 불필요한 규칙/지침 제거 필요성 언급.
- 실 사례(플러그인, 모니터 등)를 통해 실제로 Fable과 Opus를 병행하는 최적 워크플로우를 보여줌.

## 세부 요약 - 주제별 정리

### Fable 5.2는 기존 LLM과 달리 ‘자기 인식’ 성능이 크게 향상됨을 즉시 체감할 수 있음

- Fable 5.2는 Anthropic이 발표한 최신 대형 언어 모델임(출시일: 영상 기준 몇일 전).
- 기존 LLM들은 항상 어떤 형태로든 응답을 돌려주는 “기계식 한계”를 보였으나, Fable 5.2는 “응답하지 말라”는 프롬프트에 실제로 아무런 답을 내놓지 않는 새로운 수준의 자연스러움을 보임.
- 일반적 예시로는 실용적이지 않지만, LLM의 한계를 넘어서는 굉장히 중요한 진전으로 평가됨.
- Fable 5.2의 사용 경험은 더 이상 ‘멍청한 기계’에 업무를 맡기는 느낌에서 벗어나 ‘스스로 사고하는’ 느낌이 강해짐.
- 이 점이 본 영상에서 반복적으로 강조되는 핵심 논지임.

### 벤치마크와 직접 실험 결과 Fable 5.2는 복잡한/열린 과업에서 확실히 성능이 앞서나감

- 벤치마크 결과(Fable vs. Opus 5.5 vs. 기타 최상위 LLM)에서 Fable 5.2는 복잡하고 구조화되지 않은 문제에서 압도적으로 우수한 성적을 기록.
- 실제 예시: 애플리케이션 아키텍처 설계 등 복합적 결정을 요구하는 업무에서 Opus 5.5는 항상 약간 불충분한(구멍이 있거나, 반대로 질문하는) 답을 내놓으나, Fable 5.2는 완전한 솔루션을 10분만에 제공해줌.
- 직접 사용자 테스트 및 외부 벤치마크(Artificial Analysis 등) 모두 대체로 동일한 결과를 보임.
- 특히 오픈엔디드 질문, 장기 목표, 복잡한 의사결정이 필요한 과업에서 체감 차이가 크다고 반복 언급됨.

### Fable 5.2의 가장 큰 약점은 ‘비용’이며, 효율은 오히려 Opus보다 낮을 수 있음

- Fable 5.2 Max Reasoning 모드의 평균 과업당 비용: $26.54(벤치마크 기준)
- Opus 5.5 Max Reasoning은 이보다 절반도 안 되는 가격임.
- High Reasoning 시에도 차이는 여전: Fable $9, Opus $3.46(평균)
- 단순히 더 비싼 모델이더라도 처리 속도나 효율이 향상돼서 총 비용은 비슷할 수 있으나, Fable 5.2는 Opus 대비 실질 비용도 더 큼.
- 데이터 포인트 대부분에서 Fable 5.2가 Opus 5.5에 비해 업무 단가가 2배 이상 높음.
- 실제 사용자 체험: Cloud Code 플랜(월 $100)에서 5시간 분량을 Fable로 20분 만에 소진하는 사례 등 비용 이슈 반복 발생.

### 단순/명확한 과업에서는 Fable 5.2 대신 Opus 5.5로도 충분하며, 대부분 손해를 보지 않음

- Anthropic 공식 문서 및 여러 블로그, 연구, 사용자 경험 모두 공통적으로 “과업-모델 분리” 필요성을 강조.
- 명확하게 하달된 간단한 과업(클라우드 코드 등)에서는 Fable 특유의 고성능이 드러나지 않으며, 오히려 과도한 리소스 소진만 초래함.
- 복잡한 과업이 아니라면 Fable을 사용해도 효율 및 품질 상승 효과가 거의 없음.
- 실제 부담 및 실험 사례를 통해서 “필요한 곳에만 Fable, 그 외엔 Opus”로 스위칭할 것을 권장.
- 예시: Fable 5.2가 Cloud Code에서 너무 많은 리소스를 써서 수 분 내에 전체 한도를 소진한 실례.

### ‘계획-실행’ 분리 패턴이 워크플로우에서 가장 효율적임이 여러 연구와 현업 경험으로 검증됨

- Fable 5.2: “계획(Plan), 검색(Search), 의사결정(Decide)”에 집중 투입.
- Opus 5.5: 위에서 수립한 잘 정의된 단계 및 단순 반복 작업을 실제 실행(Execute).
- 플래너(Planner)-일꾼(Executor) 구조가 Anthropic 오피셜 자료, 인플루언서 경험, 논문, 블로그 등에서 모두 같은 결론에 도달함.
- 실제 사례: 긴 호라이즌 에이전트 실행, 아키텍처 결정 등에는 Fable 투입 → 이후 각 스텝은 Opus로 이관.
- 이 패턴은 이미 점진적으로 확립되어왔으나, Fable 5.2의 높은 비용과 성능 덕에 완전히 구분함이 더더욱 중요해짐.
- 오픈소스 워크플로우 빌더(Archon 등), Firecrawl 플러그인, Cloud Code 내 어드바이저 도구 등 다양한 구현 방안 소개.

### 실제 워크플로우(예: 클라우드 에이전트, 플러그인 통합 등)에서 모델 분리는 자연스럽게 적용 가능함

- 최초 세션은 Fable 5.2로 컨텍스트 수집, 구조 설계, 아키텍처 계획 등을 담은 handoff 문서(plan.md 등) 생성으로 종료.
- 새로운 세션에서 Opus 5.5를 모델로 지정, 해당 문서를 읽게 하여 실제 코딩, 검증, 반복 작업을 맡김.
- 이렇게 하면 실제 실행부는 “이미 충분히 정의된 과업”이 되므로 Opus 5.5로도 성능 저하 없이 효율적으로 리소스 소모 가능.
- Firecrawl 예시: Cloud Code 플러그인과 연동해 GitHub 버그 모니터링 자동화, 적합 과업 자동 분배 등도 실현.
- 오케스트레이션 옵션: 어드바이저 모델(advisor 기능) 사용, 하위 에이전트 분리 등 다양한 패턴 제시.

### 모델마다 권장되는 ‘Effort Level’(추론 강도)이 다르며, 비용 대비 효율을 반드시 고려해야 함

- Fable 5.2의 경우, Medium → High Reasoning으로 올릴 때 점수(벤치마크 기준) 상승이 크며 추가 비용도 크지만 가치 있음(예: 56점→62점).
- High → X High, Max Reasoning으로 올릴 때는 점수 상승폭이 미미하며(3점 내외), 비용은 급증(High $9 vs. Max $26.54). 따라서 Max는 추천하지 않음.
- Opus 5.5는 단순 과업(정의된 과업) 기준으로 Medium Effort에서 이미 92.8% 성능이며 High, X High로 올릴 때 소폭 상승(몇 %p)이지만 비용은 많이 증가. Medium~High가 적절.
- 결론: Fable 5.2는 High Reasoning, Opus 5.5는 Medium 또는 High 권장(특히 Fable로 사전 계획 수립 시 Medium으로 충분).
- Max Effort, Low Effort는 실제로 거의 비효율적인 선택임.

### 여러 벤치마크 및 코드 예시에서 플래너-일꾼 패턴은 퍼포먼스와 비용 모두에서 최적임이 입증됨

- 다양한 실험(벤치마크 그래프, Frontier Code 2.0 등)에서 “계획-실행 분리”가 가장 좋은 결과를 보임.
- 오픈엔디드, 비정형 문제는 Fable 5.2가 월등하나, 단계가 명확한 과업에서는 Opus나 그 이하 모델도 확실한 품질을 달성함.
- Anthropic의 공식 코드 없는 요리책(Cookbook)에서도 플래너-일꾼 분리 구조 적극 권장.

### 효과적인 Fable 5.2 프롬프트 설계법: 역할 명확화, 하위 에이전트 모델 설정 등이 매우 중요함

- Fable 5.2에게 “당신이 코드베이스의 소유자이자 장기 관리자(Owner & Long-term maintainer)”임을 명시적으로 가이드하면 훨씬 더 품질이 좋고 체계적인 결과가 나옴.
    - 실제 연구 데이터: 이 프롬프트를 넣으면 코드 중복이 70% 자동 정리, 안 넣으면 10% 미만.
- 코딩 세션(‘Opus 빌드 세션’)에서는 이 문구를 굳이 넣지 않아도 됨. 각 역할에 맞게 프롬프트를 분리해야 함.
- 하위 에이전트가 자동으로 Fable을 상속해 불필요하게 리소스를 낭비하는 구조 방지 필요: 별도 모델(Sonnet/Opus) 지정.
    - Custom subagent의 경우 YAML 프론트매터로 지정하거나, Cloud Code에 대화 중 모델 지정 요청 가능.
    - 실수로 하위 에이전트도 계속 Fable을 쓰면 사용 한도 초과가 너무 빨리 일어남.
- 개방형 LLM일수록 너무 구체적 단계 지시보다는 “최종 결과(Outcome)”만 정의하여 프롬프트하는 것이 더 좋을 때가 많음.
    - 정의가 명확하지 않다면 단계를 일일이 지정하기보다는 원하는 목표 자체를 서술하는 것이 능동적 해결에 적합.
- 불필요한 지시나 컨텍스트(예: claw.md 등 context files의 과거 규칙)는 가능한 한 정기적으로 “가지치기/축소(Ablate)” 필요.
    - LLM 발전으로 예전 규칙들이 오히려 성능을 제약하는 경우 존재.
    - Ablate AI Layer Skill 등 툴로 규칙 감축 진행 권장.

### 다양한 실사례 및 툴(Archon, Firecrawl, Cloud Code 등)을 통해 병합 워크플로우가 손쉽게 구현됨

- Archon 오픈소스 워크플로우 내에서 “1단계: Fable 계획, 2단계: Opus 실행” 구조의 구체적 예시 제공.
- Cloud Code의 /advisor 명령을 활용, 실행은 Opus, 어려운 결정 순간만 Fable을 어드바이저로 호출하는 하이브리드 패턴 소개.
- Firecrawl 플러그인 활용해 100만 인덱스, 400개 데이터 제공자와 연결, 코드베이스 모니터링 등 자동화 업무 실행 가능.
- 각 세션마다 모델 분리, 손쉬운 플러그인 설치/연동, 알림 자동화 등 실제 제품 환경 적용법에 대한 상세 설명 포함.

### 결론적으로, Fable 5.2와 Opus 5.5의 조합 운영법과 ‘적정 Effort Level’, 효과적 프롬프트 전략, 비용 관리법을 모두 실증적으로 안내함

- 권장: Fable 5.2 → High Reasoning, Opus 5.5 → Medium/High, Max/Low 레벨은 비추천.
- Fable은 반드시 계획, 의사결정, 탐색 등에만 할당하고 실제 실행은 Opus와 같은 효율적 모델로 배분.
- 모든 모델 신규 적용 시마다 context/rule audit(아블레이트) 반드시 필요.
- 모든 데이터와 권고, 워크플로우, 프롬프트 전략은 실제 수치, 사례, 벤치마크로 뒷받침됨.
